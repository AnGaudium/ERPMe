# ADR-0058: Configurable workflows

Status: accepted (2026-11-15) under ADR-0005, reviewed by Claude Fable 5.2 (builder Claude Opus 5.5) after six review rounds. Design items: DS-28 (configuration part), DS-13 and DS-04 (the causation chain). Implements spec 16 levels 1 and 3. Related decisions: D2, D12, D14. Principles 2, 3, 7, 8, 10, 12, 13. ADR-0004, ADR-0005, ADR-0007, ADR-0008, ADR-0009, ADR-0013, ADR-0017, ADR-0022, ADR-0027, ADR-0029, ADR-0038, ADR-0042, ADR-0043, ADR-0048, ADR-0050, ADR-0051, ADR-0053, ADR-0054, ADR-0055, [ADR-0059](0059-ai-tuning-and-development-of-deterministic-functions.md); spec 03, 10, 14, 16.

## Decision

A capability check (2026-11-15) found that only approvals are configurable: the policy table (ADR-0043) and approval pools and stages (ADR-0055) are company data, while everything else that makes up a workflow is code. This ADR adds the configuration that spec 16 calls levels 1 and 3, inside the deterministic core, following the 2026-11-15 survey (recommendations W1 to W8).

**Three tiers, no more.** A company configures (a) parameters: typed, registered settings, and the versioned parameter sets of [ADR-0059](0059-ai-tuning-and-development-of-deterministic-functions.md); (b) typed decision tables; (c) event-condition-action automation rules. An automation rule's actions are only: create a draft through a registered command marked automation-allowed, raise a work item, send an internal notification, start a registered agent type that declares the trigger, and set a hold through a registered interface. The vocabulary (event types, condition fields, commands, holds, agent triggers) is code in the registry. The composition is company data. There is no scripting, expression language or SQL in Phase 1.

**No workflow engine.** Approvals stay in policy rules and pools, waiting stays in the work queue, and asynchrony stays in the outbox. Document lifecycles and agent workflow steps stay code. No rule can approve, submit, post, issue, send, change master data, change settings or rights, or change another rule.

**Versioned and proven before use.** Every decision table and automation rule is versioned, immutable once out of draft, effective-dated and activated through a change proposal after validation, its stored tests and a replay over recorded events have run. The replay is shown as a diff against the active version. Every evaluation records the version it used, and every rule execution leaves a record that agents can read within their own rights.

**Order-independent by construction.** Decision tables use only the hit policies `unique` (overlaps refused) and `monotone` (outputs combined by an order-free aggregator). A table need not cover its whole domain: an input no row matches is the typed outcome `decision_no_match`, which every rule that uses the table must handle. Rules triggered by one event all see the same facts and never see each other's effects within one dispatch.

**Loop guards live in the dispatcher.** Every command and event carries a causation chain and an automation depth, capped at 3, which the database also holds. The same rule never acts twice on the same target within one chain. Triggers fire on declared field changes, never on any write. Activation, enabling, rollback and demotion refuse cycles and over-deep chains in the rule graph, under a company lock. A circuit breaker disables a failing rule and raises a work item. Idempotency keys derive from the rule version and the event.

**The owner answers for the rule, and sees no more through it.** Rules run as `system` on behalf of an owner who consented, whose rights, record scope and field classes cover every field the rule reads and every value it carries, checked at validation and again at each execution. Subjects outside the owner's scope are not evaluated, counted per day, and a narrowed scope raises a work item. Execution records, replays and evidence show each reader only what that reader may see: hidden values are omitted, never shown as a plain hash. Actions inherit the taint of the triggering subject, so on outside content a rule can only draft, raise work items and notices, or start an agent type that accepts outside content. Agent triggers become configuration where the agent type declares a trigger configurable.

### Rules

**Modules, tables and registrations**

1. Ownership and the DDL draft:
   - **`configuration`** (layer 2, ADR-0022 rule 2) owns the tables `automation_rule`, `automation_rule_version`, `automation_execution`, `decision_table`, `decision_table_version`, `decision_table_row`, `automation_scope_skip` and `configuration_state`, and the tables of [ADR-0059](0059-ai-tuning-and-development-of-deterministic-functions.md) rule 2. Its contract holds the pure evaluators (`evaluate_conditions`, `evaluate_decision_table`), the pure validators (rule validity, the graph check of rule 15, the table check of rule 19) and the write functions. It imports the `registry` contract (read-only declarations) and `work`.
   - **`automation`** (layer 5) owns the consumer `automation_dispatch` (rule 10), the replay (rule 23), the upgrade check (rule 25), evidence and the monitor (ADR-0059), and the commands of rule 27 that read layer 3–4 data. It imports `registry` (dispatch), the `configuration`, `work` and `permissions` contracts, and the contracts of the layer 3–4 modules whose deterministic functions it evaluates; none of its layer-5 peers.
   - **Hooks** (ADR-0022 rule 2's pattern): `configuration` declares the hook `artifact_checks`, which `automation` registers and `app` wires, for the parts of a check that read layer 3–5 data (the condition source's permission and scope for the owner, the replay at execution). `configuration`'s commands `SetArtifactVersionState`, `SetArtifactCurrentVersion` and `EnableAutomationRule` call their pure validators directly and the hook for the rest, so no import goes up.
   - **The DDL draft** is [DS-28-34-configuration-artifacts.sql](../design/DS-28-34-configuration-artifacts.sql), a new file, so the configuration tables load and change apart from the 1,400-line platform file and from the drafts other design items are writing; it writes out their row-level security in DS-05-platform.sql's pattern. The platform file only gains the causation columns of rule 12 on `outbox_event` and `audit_record`, and ADR-0059 rule 6's columns on `bank_statement_line`. ADRs win if the DDL disagrees.
2. Three configuration tiers (the 2026-11-15 survey, W1):
   - **(a) Parameters.** Registered company settings (typed, bounded, change-tracked, as today) and, for the constants of a deterministic function that decide outcomes on business data, the versioned parameter sets of ADR-0059 rules 3–4.
   - **(b) Decision tables** (rules 18–20).
   - **(c) Automation rules** (rules 8–17).
   - **Vocabulary is code, composition is configuration.** Event types, condition fields, commands, decision points, hold interfaces, scheduled jobs and agent triggers are registry items with versions (rules 4–7). A company composes them in rows. A need that the vocabulary cannot express is a code change in the core or in a package, reviewed like code (ADR-0059 rule 24).
   - **No scripts.** No artifact holds code, an expression, a template language or SQL. Conditions are structured triples (rule 8).
3. What stays code (W2):
   - **Approvals** are configured only by policy rules (ADR-0043) and approval pools and stages (ADR-0055). An automation rule never routes an approval, approves or rejects.
   - **Waiting** is a work item (ADR-0042), **asynchrony** the outbox (ADR-0013). There is no BPMN, no orchestration engine and no long-running process instance in Phase 1.
   - **Document lifecycles** (ADR-0009) and **agent workflow steps** (ADR-0051) stay code, changed only by a new release or agent type version.
   - **What a rule can never do:** submit, approve, reject, post, issue, reverse or send; change master data, settings, roles, policy or another artifact; widen an agent's tool list; relax a hard floor of spec 03.

   Note ([ADR-0065](0065-deterministic-auto-post-gateway.md), 2026-11-16 (proposed)): unchanged by the auto-post gateway. The gateway is a policy decision at the policy point of `Post<Type>`, evaluated by core code with settings and a decision table at a module decision point; it is not an automation rule, so this rule needs no exception, and no automation rule posts ([ADR-0065](0065-deterministic-auto-post-gateway.md) rule 13).

**Registry vocabulary**

4. Trigger event types (ADR-0008 rule 1 note; ADR-0013 rule 1 note). An event type is usable as a trigger only when its registration declares:
   - **`is_automation_trigger`** and its **condition source**: a registered query that takes the subject's ID, and its version for documents, and returns the condition fields; its permission, record scope and owner scope are the owner's test in rule 9;
   - **condition fields**: name, type (`amount`, `quantity`, `percent`, `integer`, `date`, `boolean`, `code`, `reference`), data label and field class. Only fields that the registry declares `is_gate_field` may be condition fields: an allowlist of deterministic fields, never a field fed by an LLM step's output directly or through computation ([ADR-0059](0059-ai-tuning-and-development-of-deterministic-functions.md) rule 20). A field marked `is_untrusted` (ADR-0029 rule 10) or labelled `sensitive_personal` is never declared one, so outside text and model output never steer a rule;
   - optionally a **discriminator** field (such as a work item's `kind`), which makes (event type, value) a node of the rule graph (rule 15);
   - for an update event, its **watchable fields**, which the payload reports in `changed_fields` by name only (rule 14);
   - **`is_replayable`**: the condition source reads an immutable version, so the replay of rule 23 sees the facts as they were.
5. Automation-allowed commands (ADR-0008 rule 1 note):
   - **`is_automation_allowed`** is a new registry attribute. A command so registered is a `Create<Type>` that creates a draft (never an update or delete of one), is also `is_draft_only` (ADR-0050 rule 26), is never of effect class `posting`, `master_data_change` or `outbound_send`, never `human_only` or `is_proposal_bound`, and never a command of `configuration` or `automation` other than `RaiseAutomationWorkItem`. `CreateChangeProposal` is not automation-allowed: a rule never proposes master data changes. CI checks this. `StartAgentRun` and hold commands are reached only through their own action kinds (rules 6–7).
   - **Emitted events.** Every command declares the event types it may emit and, for an event type with a discriminator, the discriminator values; a declaration without values counts as able to emit every value, which reaches every discriminated trigger of that type (conservative). Registered consumers and scheduled jobs declare the same for the commands they run. A registry check compares the declarations with the handlers' emits in tests. The graph check of rule 15 reads them.
   - **Payloads.** An action's payload is built from the rule's payload template: each field is a literal, a condition field of the trigger, or an output of a pinned decision table version (rule 20). Validation type-checks it against the command's schema at the registry version, so an action never carries a free string from outside content.
6. Hold interfaces (ADR-0008 rule 1 note). A module may register a command `is_hold` for a subject table: effect class `other`, it only sets a block that a later step respects (a delivery or payment block), it never releases one, and a person releases it with the module's own release command. Phase 1 registers none yet; the open item payment block of DS-25 and a delivery block on sales orders are the first candidates. Until a module registers one, the action `set_hold` has no vocabulary.
7. Agent triggers (decision 9 of the author's decisions of 2026-11-15; ADR-0050 rule 12 note):
   - **Declaration.** Each claimable work item kind an agent type version declares carries `wake_up`: `always` (the hard-wired wake-up of ADR-0050 rule 16) or `configurable`. An agent type version may also declare `configurable_triggers`: pairs of (trigger event type, subject table) on which a company may start it. The subject tables it accepts (ADR-0050 rule 15) say whether outside content may start it.
   - **Configurable means configured.** `agent_wake_up` skips a kind declared `configurable`. A company starts the agent on it, or on a configurable trigger, only by an automation rule whose action is `start_agent`, with its own conditions. Without such a rule the item stays with people (Principle 12).
   - **Interim, flagged for the author.** Every kind the six agent types of ADR-0051 declare stays `always` in their current versions, and none declares a configurable trigger, so behavior does not change. Which triggers become configurable is the author's (open question); making one configurable is a new agent type version (ADR-0050 rule 12).

   Note ([ADR-0063](0063-configurable-policy-settings.md), proposed 2026-11-15): "configurable" now means that the company chooses the wake-up mode, `always` by default; "configurable means configured" applies under the mode `by_rule` (rule 11).

**Automation rules**

8. Shape (company data; DDL `automation_rule`, `automation_rule_version`):
   - **The rule:** `code`, `name`, `owner_user_id` (required), `owner_confirmed_at` (rule 9), the pointer `current_version_id` to the version in force, `shadow_version_id` (ADR-0059 rule 12), and `disabled_at` with `disabled_reason` (`circuit_breaker`, `owner_inactive`, `upgrade_invalid`, `person`).
   - **A version:** `trigger_event_type`, an optional `trigger_discriminator`, `watched_fields`, `conditions`, one to five `actions`, `tests`, the pinned decision table versions it uses, and the lifecycle columns of ADR-0059 rule 12.
   - **Conditions** are triples (`field`, `operator`, `value`), all of which must hold. Operators by type: `eq`, `ne`, `in`, `not_in` for codes, references and booleans; `lt`, `le`, `gt`, `ge` and `between` (half-open, as ADR-0043 rule 3) for numbers and dates; `is_null`, `is_not_null` for any type; `decision` names a pinned decision table version, a boolean output and the handling of `decision_no_match` (rule 20). An alternative is a second rule.
   - **Actions:**

     | Kind | What it runs | Permission checked for the owner (rule 9) | Notes |
     | --- | --- | --- | --- |
     | `create_draft` | An `is_automation_allowed` command, with its payload template (rule 5) | The command's own permission | The draft carries the rule version as its origin |
     | `raise_work_item` | `RaiseAutomationWorkItem`, kind `automation_task` | Read permission on the subject: its `Get` or `List` query, with record and owner scope | Owner: a user, a role template, `document_owner` of the subject, or a decision table output; due in N business days; text from the rule |
     | `notify` | `RaiseAutomationWorkItem`, kind `automation_notice` | The same read permission | An in-app notice in the recipients' work queue; e-mail and push stay after Phase 1 (ADR-0040 rule 14) |
     | `start_agent` | `StartAgentRun` with the triggering work item or subject | `start_agent:<agent_type>` | Only an agent type that declares the trigger (rule 7) |
     | `set_hold` | A registered `is_hold` command on the subject (rule 6) | The command's own permission | Released only by a person |

     `RaiseAutomationWorkItem` stays `is_internal_only`, so no role holds it; its check is the owner's read right on the subject, which the dispatcher applies to it in place of a permission of its own.

   Note ([ADR-0066](0066-work-cases.md), 2026-11-16 (proposed)): a further action kind, `open_work_case`: `CreateWorkCase` for a case kind whose company mode is `by_rule` or `auto`, with the triggering subject as origin and the owner by `named_by_raiser`. The owner needs `CreateWorkCase` and the read permission on the subject (rule 9). It drafts, posts and sends nothing ([ADR-0066](0066-work-cases.md) rule 7).
9. Owner, rights, scope and taint (the survey's open question 1):
   - **Actor.** Each action runs as actor `system` on behalf of the rule's owner (ADR-0013 rule 9's exception, like `agent_wake_up`), except the agent run that `start_agent` starts, which acts for the agent setting's `workflow_owner_id` as ADR-0050 rule 15 requires; the rule's owner also needs `start_agent:<agent_type>`, so neither person extends the other's reach.
   - **What the owner must hold, at validation and again at each execution:** the permission of each action (the table of rule 8); the permission of the trigger's condition source query; the field class of every condition field and of every value an action carries (payload fields and decision table outputs, ADR-0017 rule 10). A missing permission or field class refuses the action with `automation_owner_scope_insufficient` or `permission_denied`, recorded as `refused`, which counts toward the breaker (rule 16). So no rule is an oracle on data its owner cannot read.
   - **Owner's record scope: a non-match, counted.** At execution the consumer reads the facts with the owner's record and owner scope (ADR-0017 rule 9; ADR-0054 rules 13–15). A subject outside them is not evaluated, as a non-match: the right behaviour for a branch manager's rule. It is not silent: the consumer adds it to a value-free daily count per rule, `automation_scope_skip` (rule, business date, count); validation, the replay and its diff return the check result `automation_owner_scope_limited` with the owner's scope and the number of window events outside it, shown in the activation proposal; and when the record or owner scope of the owner of a rule in force narrows, `automation_owner_scope_narrowed` is raised for the rule's owner by the daily check below.
   - **Consent.** An owner is set only with their consent: the owner is the submitter of the activation proposal, or confirms ownership with `ConfirmAutomationRuleOwnership`, their own command; `owner_confirmed_at` and `owner_confirmed_user_id` record it, the database requires that user to be the current owner while a version is in force, and activation without it is refused (`automation_owner_not_confirmed`). Changing the owner of a rule that has a version in force runs through a change proposal (`UpdateAutomationRule` is `is_proposal_bound` for that field), re-checks the new owner's rights and scope, and needs the new owner's consent; the old owner stays in force until the change executes. Every owner change clears the recorded consent (`owner_confirmed_at` and `owner_confirmed_user_id`), so consent never carries over to another person.
   - **The daily owner check.** `automation_rule.owner_scope` (jsonb) stores, per rule, the owner's effective scope for that rule as a set of cells (ADR-0054 rule 15: scopes combine per assignment, and a row is visible when any assignment that grants the permission allows it). There is one cell per assignment in force whose role grants the permission of the rule's condition source, split to single values: (branch ID or `all`, warehouse ID or `all`, the read owner scope level, and for `team` and `department` the resolved unit IDs with the employee IDs the organisation resolver yields). Branch, warehouse and employee IDs are not hidden values. The set is stored at activation, at an owner change and when an `automation_owner_scope_narrowed` item is resolved. The system job `RunAutomationOwnerScopeCheck` (`automation`, `is_internal_only`, daily, actor `system`) recomputes it for every rule with a version in force, from the assignments, their roles and their validity dates read through the `permissions` contract, so an assignment that lapses by date, a role edit or a reorganisation is caught without an event:
     - when the owner's account is disabled, or the owner has no assignment in force in the company (its `valid_to` passed), it disables the owner's rules with reason `owner_inactive` and raises `automation_rule_disabled` for `company_owner`, who reassigns them by the change above; this is the only case that involves `company_owner`;
     - a stored cell is **covered** when some new cell has the same or `all` branch, the same or `all` warehouse, a level at least as high, and, for `team` and `department`, all of the stored cell's employee IDs. The scope **narrowed** when a stored cell is not covered. The job then raises `automation_owner_scope_narrowed` for the rule's owner, naming the uncovered cells. With levels `team` and `department`, every colleague who leaves the owner's team or department uncovers a cell, so such items are frequent and expected. While the item is open for the rule (its open key is the rule), no second item is raised and the stored set is not changed, so the item keeps showing the difference; resolving it stores the new set;
     - anything else that differs (wider cells, or an equal reach from reshuffled assignments, which splitting to single values keeps silent) only updates the stored set, and raises nothing.
   - **Writers.** A draft made by a rule counts as its writers, for segregation of duties (ADR-0055 rule 7 condition 5), the rule's owner, the version's drafter (or the human its drafting run acted for), and the triggering event's human. None of them approves what the rule drafted.
   - **Taint, decided before acting.** Actions inherit taint from the triggering event and subject. On a tainted event, or a subject whose effective version is tainted or which is outside content (ADR-0050 rule 15's subject tables), the consumer runs drafts, work items and notices tainted, and `start_agent` when the agent type accepts that subject table (the run starts tainted, ADR-0050 rules 15–16); it skips `set_hold`. On an event that carries an origin agent run it skips `start_agent`, so no agent wakes an agent (ADR-0050 rule 16). Skips are decided before any action runs, recorded per action as `skipped` with the reason, and never count toward the breaker (rule 16). A notice reaches only people inside the company (flagged).
   - **Agent chains.** A rule triggered by an event that carries an origin agent run acts under ADR-0029 rule 12's intersection.
10. Execution, by the transactional consumer `automation_dispatch` (queue `events`):
    - **Subscription:** every event type registered `is_automation_trigger`. For each event it takes the company's rules whose current or shadow version has that trigger and is not disabled. The version used is the one in force on the event's business date: the current version when the date is on or after its `effective_from`, otherwise the version the transition log shows in force that day if it is still eligible; when none was, the event is not evaluated and leaves no record.
    - **Facts first.** It reads each rule's condition source once per event, with the owner's rights and scope (rule 9): a document subject at the version the event names (an immutable `document_version`), any other subject as it is now, with the hash of what it read. It evaluates every matching rule's conditions on those facts before running any action, so no rule sees another's effects in the same dispatch (W4).
    - **Guards,** per matched rule in rule-ID order (the results do not depend on the order): the event's depth below 3 (rule 12), the same-target guard (rule 13), the rule not disabled, and the skips of rule 9.
    - **Actions are independent.** The consumer allocates the execution's ID first, so a raised work item can name it as subject. Each action runs in its own savepoint through the dispatcher, with idempotency key `automation:<rule version id>:<event id>:<n>` (rule 17), and gets its own outcome in `action_results`: `done`, `skipped` (by design, rule 9), `refused` (permission, scope, field class) or `failed` (anything else). A non-retryable error rolls back only that action's savepoint. A retryable error (`concurrent_update`, `timeout`) rolls back the delivery and it is retried (ADR-0013 rule 8). So one failing action or rule never holds the delivery for the others.
    - **The execution's outcome** follows from its actions: `acted` (at least one `done`, none `refused` or `failed`), `partial` (some `done`, some `refused` or `failed`), `skipped` (every action skipped by design), `failed` (no `done` and at least one `failed`), `refused` (no `done`, at least one `refused` and none `failed`); and, before any action, `skipped_same_target` or `depth_exceeded`.
    - **Shadow versions** are evaluated the same way and record their would-be actions with outcome `would_act`; nothing runs.
    - **Record.** `RecordAutomationExecution` (internal, rule 11) writes one row per matched rule version, after its actions.
    - **Same trigger, same target.** Activation returns the check result `automation_same_target_warning` when another active rule has the same trigger and an action on the same target kind, so a person sees that both will act.
11. Execution records (W7), `automation_execution`:
    - **Columns:** rule and version, `mode` (`live`, `shadow`), event ID and type, the event's business date, subject and the version read, the subject's scope dimensions (branch, warehouse, document) for readers' scope, causation chain and depth, `outcome`, the condition results (field, operator, field class, data label, value read, result; a personal value is stored as a keyed hash, HMAC-SHA-256 under the company's secret `automation.value_hmac_key`, or omitted, never as a plain hash), the input hash, each action's kind, command, key, outcome and audit record or error, taint, origin agent run and the owner acted for.
    - **Not recorded per event:** events where a rule's conditions did not match, and subjects outside the owner's scope, which only the daily count of rule 9 records. `GetAutomationReplay` answers "why did my rule not act on this order" for one event.
    - **Filtered by the reader.** `ListAutomationExecution`, the agent view `automation_execution_overview` (ADR-0050 rule 51 note), `GetAutomationReplay` and the frozen replay diffs of rule 23 return a row only when the subject is inside the reader's record and owner scope. For a field class the reader lacks they omit the value and that condition's result, and set the marker `is_class_filtered` on it (ADR-0017 rule 10's omission); they never show a hash in its place, because the few possible amounts, percents and codes would be found by trying them. The residue is stated: an `acted` outcome still tells such a reader that the conditions held. The HMAC key lives in the deployment's secret store, is never in a view or a prompt, and keyed hashes are compared only inside the system. Keys are versioned and never rotated in place: a new key version hashes new values, every stored hash names its key version, old key versions are kept for verification only, and stored values are never re-hashed. An agent run reads with its intersection of rights (ADR-0050 rule 31); the view has no partner column and so is closed to tainted runs; a drafting agent type never has it on its tool list ([ADR-0059](0059-ai-tuning-and-development-of-deterministic-functions.md) rule 16).
    - **Kept** as decision records under ADR-0059 rule 23.

**Loop guards**

12. Causation chain (W5; ADR-0013 rule 2 note; ADR-0038 rule 2 note):
    - **Columns.** Every `outbox_event` and `audit_record` carries `causation_chain_id`, `causation_depth` (no default; the writer always sets it) and `automation_rule_version_id`; the database requires a depth of at least 1 where a rule version is named.
    - **Assignment, by the dispatcher, never by the request:** a command from a transport, a person or a scheduled job starts a chain (a new UUIDv7, depth 0); a consumer command inherits its event's chain and depth (ADR-0013 rule 9); an automation action inherits the triggering event's chain with depth plus one and names its rule version; an agent run started from an event (a wake-up, or `start_agent`) inherits that event's chain and depth, and every tool call of the run and every event of its drafts carries them; a run a person starts begins a chain, also on an item a rule raised, which is intended: a person is in the loop.
    - **The cap is 3.** The dispatcher refuses an automation action whose depth would exceed 3 with `automation_depth_exceeded` (DS-04 check order, step 2), and the consumer records `depth_exceeded` without trying. The database holds it too: a check keeps `causation_depth` between 0 and 3 on both tables. The cap is a core constant, not a setting.
13. Same rule, same target: a rule acts at most once per (chain, subject). A unique index on `automation_execution` (rule, chain, subject) over live executions with outcome `acted` or `partial` holds it; a second match in the chain is recorded `skipped_same_target`.
14. Field-change triggers:
    - **Transitions** (`SalesOrderApproved`, ADR-0009 rule 22) are changes by nature.
    - **Update events** (`PartnerUpdated`, `SalesOrderChanged`) trigger a rule only through its `watched_fields`, which must be non-empty and among the event type's watchable fields; the rule fires only when the event's `changed_fields` intersect them. A rule on an update event without watched fields is invalid (`artifact_invalid`, reason `trigger_unwatched`). There is no "on any write".
15. The graph check:
    - **The graph.** Nodes are event types, split by discriminator value where declared. Each rule (active, disabled or the candidate) adds edges from its trigger node to every node its actions' commands may emit (rule 5); an emit declared without values reaches every discriminated node of its type. Each registered consumer adds edges from its subscribed events to the events of the commands it may run.
    - **Scheduled jobs are sources.** A scheduled job starts a chain at depth 0 and adds edges from itself to the events of its commands; nothing leads into it. A loop through a scheduled job can therefore repeat once per schedule run, each time at depth 0; activation returns the check result `automation_schedule_feedback` when the candidate's actions emit an event type on a table that a scheduled job declares it reads and that job's events reach the candidate's trigger, so a person sees it.
    - **Cycles.** A cycle through the candidate is refused with `automation_rule_cycle`, naming the path. Cycles of consumers alone are the core's concern (ADR-0013) and are not reported.
    - **Depth.** The depth at which a rule can act is 1 plus the largest number of rule edges on any path that leads to its trigger. A candidate that could act beyond depth 3, or that would push another rule beyond it, is refused with `automation_depth_exceeded`.
    - **When.** At the evidence (rule 23), at the creation of an activation proposal, again at its execution, at `EnableAutomationRule`, at every rollback (`SetArtifactCurrentVersion`) and automatic demotion (ADR-0059 rule 21), and at every upgrade (rule 25), each time with validity (rules 4–5, 9) against the current registry and over the whole set. Disabled rules stay in the graph, so enabling one cannot close a cycle. A failing target is refused with `artifact_invalid`; the monitor's demotion then falls back to the core defaults or to none.
    - **One at a time.** Every activation, enable, rollback and demotion first locks the company's `configuration_state` row (ADR-0027 rule 10, class 3 note), so two approvals executing in parallel cannot together form a cycle that each alone does not.
    - **The runtime cap of rule 12** remains the backstop for paths no declaration shows.
16. Circuit breaker:
    - **Trip.** The consumer runs `DisableAutomationRule` with reason `circuit_breaker` when a rule's live executions record, among outcomes `refused`, `failed` or `partial`, either `automation.breaker_failures` within `automation.breaker_window_minutes` (company settings, defaults 5 and 60, flagged), or 20 in a row at any rate. Skips by design and outcomes `skipped_same_target` and `depth_exceeded` do not count. The window is counted on the executions' business date and recorded instant, declared a technical timer of the breaker (ADR-0007 rule 10, as ADR-0013 rule 7 declares the delivery timers); the count in a row needs no clock.
    - **Who.** `DisableAutomationRule` runs under the consumer's registered permission, not the owner's, because the owner may be the one who lost a right. It raises `automation_rule_disabled` for the owner, or for `company_owner` when the owner can no longer open the company.
    - **Back.** A person runs `EnableAutomationRule`, which re-enables the same current version after the checks of rule 15; it never changes the version.

    Note ([ADR-0063](0063-configurable-policy-settings.md), proposed 2026-11-15): the three thresholds are the settings `automation.breaker_failures` (1 to 50), `automation.breaker_window_minutes` (5 to 1,440) and `automation.breaker_consecutive` (3 to 200, at least the failures), each with an override in a rule version's content; the flood guard `automation.max_executions_per_rule_per_hour` (500) records `rate_limited`, which never counts (rule 21).
17. Idempotency: one execution per (rule version, event, mode), a unique key of `automation_execution`; every action's command key is `automation:<rule version id>:<event id>:<n>`, so a retried delivery replays the stored responses (ADR-0008 rule 16) and never duplicates a draft or an item.

**Decision tables**

18. Shape (company data; DDL `decision_table`, `decision_table_version`, `decision_table_row`):
    - **Inputs** are declared with a type and a domain: `code` inputs list their allowed values (a registry enumeration, or a company list copied into the version); numeric inputs (`amount`, `quantity`, `percent`, `integer`) a half-open range, unbounded where empty; `boolean` inputs true and false.
    - **Outputs** are typed (`code`, `amount`, `integer`, `boolean`, `role_template`, `user`), and for the monotone policy each names its aggregator.
    - **Rows** hold one cell per input: a set of values, a half-open range, a boolean, or nothing (any), and one value per output.
    - **Limits:** at most 200 rows and 6 inputs per version.
    - **Where used.** In automation rules (the `decision` operator, payload fields, the owner and due days of a work item) and at decision points that modules declare in the registry with their input and output schema and a code default for `decision_no_match`. The core declares no module decision point in Phase 1; candidates are work item owner routing per kind and putaway rules (ADR-0023 rule 21).
19. Hit policies and validation (W4):
    - **`unique`:** at most one row matches any input. Validation compares every pair of rows exactly (two boxes overlap when every input's cells intersect) and refuses an overlap with `decision_table_overlap`, naming the two rows and a point they share.
    - **`monotone`:** every matching row contributes, and each output combines by an aggregator that is commutative, associative and idempotent: `max`, `min`, `any`, `all`, `union`, `intersection`. `sum`, `first` and priorities are not offered, so the result never depends on row order or on duplicate rows.
    - **Completeness is not required.** An input that no row matches is the typed outcome `decision_no_match`. Validation may prove completeness by box subtraction: it subtracts each row's box from the declared domain and stops at the first uncovered box, under a work cap of 100,000 box operations. It returns the check result `decision_table_gap` with a witness point when it finds one, and `decision_table_completeness_not_proven` when the cap is reached; it never reports a gap it did not find, and neither result refuses the version.
    - **Out of domain.** A null input, a code value not in the version's list (a value added to the company list after the version froze) or a number outside the declared range is `decision_input_out_of_domain`.
20. Binding and evaluation records:
    - **Pinned.** A rule names the decision table versions it uses, by ID, as part of its content (and so of its content hash, rule 21). It may pin only versions of the company's tables in state `active` or `assisted`, checked at validation, again when the rule version leaves draft (a database trigger) and at each execution. A pinned version cannot be retired or demoted to `shadow` while a current or shadow rule version pins it: `decision_table_version_in_use`. A table's pointer, its rollback or a new table version never changes a rule: a rule that should use a new table version needs a new version of its own, with its own replay. A table's pointer serves module decision points only.
    - **Handled.** Every use of a table in a rule states its handling of `decision_no_match`: `no_match: false` (a condition fails, or the action is skipped as by design) or a typed default value; validation refuses a use without one. `decision_input_out_of_domain` makes that rule's execution `failed` with the code, which counts toward the breaker, because the table's domain needs the owner's attention. A module decision point uses its code default for `decision_no_match`.
    - **Recorded.** Every evaluation records (table code, version, input hash, matched rows, output or outcome). An automation rule stores it in its execution's condition results; a module's decision point stores it in its own record or derivation trace (ADR-0027 rule 3), with the version as `rule_version`.

    Note (Final simulation review, 2026-11-15): the pin check splits by move. A rule version leaves draft (for `backtested`) only when every pinned table version exists in the company and is frozen: `backtested`, `shadow`, `assisted` or `active`, never `draft` or `retired`; so the rule's replay (rule 23) is stored against a table version that is not yet in force. A rule version becomes `active` only when every pinned version is `assisted` or `active`, so a rule in force never pins anything else; a shadow rule version may pin a `backtested` or `shadow` table version, since it only records what it would do. The trigger `automation_rule_version_check_pins` holds both moves, and validation and each execution apply the same split; `decision_table_version_in_use` still protects a pinned version from retirement and demotion while a current or shadow rule version pins it. Lab check `t22_workflows.py` D30g to D30l.

**Versions, tests, replay and activation**

21. Versions (W3), with the lifecycle of ADR-0059 rule 12:
    - **Ladder.** Decision tables and automation rules use draft → backtested → active, with an optional shadow stage and no assisted stage for rules. `backtested` here means: valid, tests passing, replay frozen as evidence (rule 23). A version leaves draft only to `backtested`.
    - **Immutable.** A version is inserted only as a draft and is editable only in `draft`. From `backtested` on, its content never changes; a trigger refuses it (`artifact_version_immutable`). A change is a new version.
    - **Content hash.** `content_hash` is the SHA-256 of the canonical JSON (ADR-0006 rule 13 forms) of the version's content: for a rule, its trigger, discriminator, watched fields, conditions, actions with their payload templates, tests and the IDs and content hashes of the decision table versions it pins; for a table, its hit policy, inputs, outputs, tests and its rows sorted by row number; for a parameter set, ADR-0059 rule 4's. Lifecycle columns, IDs of the version itself, drafter and timestamps are outside it.
    - **Effective-dated.** Activation sets `effective_from`, never before the business date of the activation; the consumer uses the version in force on the event's business date (rule 10), so backdating selects nothing old (ADR-0043 rule 6's reasoning).
    - **One in force.** The rule's `current_version_id` names it; rollback moves the pointer (ADR-0059 rule 13).
22. Stored tests (W6): each version carries its tests: for a rule, an event with the subject's field values and the expected match and actions; for a table, inputs and expected outputs or outcomes. Validation runs them, and a failing test refuses evidence (`artifact_tests_failed`). A person may save an evaluation shown by `GetAutomationReplay` as a test of a new draft.
23. The replay diff (W6), the evidence of stage `backtest` for these kinds:
    - **Window.** By default the last 30 days of retained events of the trigger type (ADR-0013 rule 15 keeps 400). The window is recorded in the evidence, like every backtest window (ADR-0059 rule 15).
    - **Run.** The candidate and the current version (or none) are evaluated on each event's facts as rule 10 reads them, with the owner's scope; the replay never runs an action.
    - **Diff.** The subjects where the outcome differs, each with both outcomes and the actions that would differ, the amounts of the subjects' amount fields, and counts. Events whose trigger is not `is_replayable` are evaluated on current state and counted as `replay_not_reconstructable` (a check result). Events whose subject lies outside the owner's scope are counted, not evaluated, and returned as `automation_owner_scope_limited` (rule 9). Whoever reads the diff sees it filtered by their own scope and classes (rule 11).
    - **Frozen.** `CreateArtifactEvidence` stores it in `artifact_promotion_evidence` with the hashes of ADR-0059 rule 14. There is no pass threshold beyond the minimum count of events: the person who submits the activation reads the diff and vouches for it.
24. Activation through a change proposal (ADR-0029 rule 5 note):
    - **Command.** `SetArtifactVersionState` (ADR-0059 rule 13) to `active` or `shadow` is `is_proposal_bound` and runs only from an approved change proposal; the proposal names the evidence.
    - **Validation on creation:** the version is valid against the current registry and for the owner (rule 9), its tests pass, the graph check of rule 15 passes, the owner has consented, and its evidence is sufficient; anything else is refused.
    - **Who.** A person submits; a person who is neither the submitter (`approver_is_submitter`) nor the version's drafter nor the human its drafting run acted for (`segregation_of_duties`) approves.
    - **Execution,** under the company's `configuration_state` lock, checks that the version's content hash, the registry version and the current version still equal the evidence's (`artifact_evidence_stale`), repeats validity and the graph check (rule 15), then moves the pointer and sets `effective_from`.

    Note (Final simulation review, 2026-11-15): one change proposal may activate a decision table version and the rule version that pins it. Its items are one `SetArtifactVersionState` per version, the table versions first, each naming its own evidence. Validation on creation accepts a pinned version that is not `assisted` or `active` only when an earlier item of the same proposal raises it to one of them. Execution runs every item in one transaction under the company's `configuration_state` lock, so both versions come into force or neither: a rule item that would run before its table is refused with `artifact_invalid` and the whole execution rolls back (rule 20 note). The approver holds the target permissions of every item ([ADR-0043](0043-policy-and-approval.md) rule 12). Who, with the role templates of [ADR-0054](0054-users-roles-and-authorizations.md) rule 11's note of this review: the owner, the chief accountant and the sales, purchasing and production managers draft and submit; the owner and the chief accountant approve, never an activation they submitted or drafted, so the owner's drafts go to the chief accountant and hers to the owner. Lab check `t22_workflows.py` D30k and D30l; `t12_access.py` G54 and G55.
25. Upgrade safety (W8):
    - **References** in configuration are registry items with a version and a deprecation status. A deprecated item stays usable for at least one minor release.
    - **At every core or package upgrade** the system job `RunArtifactUpgradeCheck` re-validates every current, shadow and still-eligible earlier version of every artifact, runs its tests and a 7-day replay, and repeats the graph check.
    - **On failure** the artifact is deactivated, never left to fail at run time: a rule is disabled (`upgrade_invalid`); a rule that pins an invalid decision table version is disabled with it; a table's pointer for decision points is cleared; a parameter set's pointer falls back to the core defaults (ADR-0059 rule 4). Each writes a transition `invalidated` and raises `artifact_invalidated` for the owner, with the findings.
    - **Deprecated references** write a transition `deprecation_found` with no state change and raise `artifact_reference_deprecated` for the owner, without deactivation.

### Worked examples

**A rule: approved large sales orders alert the warehouse.** The company wants the warehouse to prepare when a sales order of more than 500,000,000 in company currency is approved. The sales manager drafts the rule `large_order_warehouse_alert` and is its owner:
- trigger `SalesOrderApproved`, a transition, so no watched fields;
- condition (`amount_company`, `gt`, 500000000) on the event type's condition source, which reads the order at the approved version; `amount_company` is a gate field with no field class;
- action `raise_work_item`: owner `role:warehouse_keeper`, due in 1 business day, text "Prepare stock for a large approved order".

Activation: `CreateArtifactEvidence` validates the version (the field exists, is a gate field and is visible to the owner; the owner may read sales orders of every branch; `RaiseAutomationWorkItem` is automation-allowed; no cycle; depth 1), runs its two stored tests (an order of 600,000,000 raises one item; one of 400,000,000 raises none) and replays 30 days: 412 approvals, of which 9 would have raised an item. The sales manager submits the activation, which is her consent as owner; another person approves. On 2026-11-20 order SO-1043 of 620,000,000 is approved: the consumer reads version 2 of the order within the owner's scope, the condition holds, and it runs `RaiseAutomationWorkItem` with key `automation:<rule version>:<event>:1` at depth 1; the action is `done` and the execution `acted`. Had anything in the same chain made the order emit a second matching event (a consumer reacting to the work item, say), the rule's second match would be recorded `skipped_same_target`: the warehouse gets one item per order and chain. Neither the sales manager, nor the person whose approval triggered the rule, may approve the purchase requests another of her rules drafts from such orders, because both count as their writers.

**A loop the cycle check catches.** A warehouse lead drafts `notify_on_any_task`: on `WorkItemRaised` with discriminator `automation_task`, raise an `automation_task` for the warehouse manager. Its action emits `WorkItemRaised` with discriminator `automation_task`, its own trigger node, so activation is refused with `automation_rule_cycle` (path `WorkItemRaised[automation_task]` → `notify_on_any_task` → `WorkItemRaised[automation_task]`). Changing the action to `notify` emits `WorkItemRaised[automation_notice]`, a different node, and the rule passes. A two-rule loop is found the same way: rule A on `PurchaseRequestCreated` raises an `automation_task`, and rule B on `WorkItemRaised[automation_task]` drafts a purchase request; activating B is refused with the path A → B → A. So is a single rule on `WorkItemRaised[automation_task]` that drafts a purchase request when a consumer of `PurchaseRequestCreated` raises work items without declaring their kinds: an undeclared value reaches every discriminated trigger.

**The depth cap.** Three active rules form a chain: R1 drafts a purchase request when a large sales order is approved (`SalesOrderApproved` → `PurchaseRequestCreated`, depth 1); R2 drafts a purchase order from it (→ `PurchaseOrderCreated`, depth 2); R3 raises an `automation_task` for the buyer (→ `WorkItemRaised[automation_task]`, depth 3). R4, which would notify the purchasing manager on that task, would act at depth 4, so its activation is refused with `automation_depth_exceeded`. At run time the same chain carries depth 3 on R3's work item event; if a consumer path that no registration declared reached a rule again, the consumer would record `depth_exceeded`, the dispatcher would refuse the action, and the database would refuse an event at depth 4.

**A decision table with a unique hit policy.** `warehouse_alert_owner` gives the owner and due days of the alert by warehouse and amount: inputs `warehouse_code` (`NORTH`, `SOUTH`, `EAST`) and `amount_company` (from 0, unbounded); outputs `owner_role` and `due_days`. Draft rows:

| Row | warehouse_code | amount_company | owner_role | due_days |
| --- | --- | --- | --- | --- |
| 1 | NORTH, SOUTH | [500,000,000, 2,000,000,000) | warehouse_keeper | 1 |
| 2 | NORTH, SOUTH | [1,500,000,000, ∞) | warehouse_manager | 1 |
| 3 | EAST | [500,000,000, ∞) | warehouse_keeper | 2 |

The pairwise check finds rows 1 and 2 overlapping at (NORTH, 1,500,000,000) and refuses the draft with `decision_table_overlap`. Setting row 1's upper bound to 1,500,000,000 fixes it. The completeness proof then subtracts the three boxes from the domain and returns `decision_table_gap` with the witness (EAST, 0): no row covers amounts below 500,000,000. The version is accepted all the same, because the rule that uses it only acts above 500,000,000 and states `no_match: false`; an input in the gap would skip the action as by design. (SOUTH, 1,600,000,000) gives the warehouse manager in 1 day. The rule pins this table version; a later table version changes nothing until the rule gets a version of its own.

**The replay diff at activation.** Version 3 of `large_order_warehouse_alert` lowers the threshold to 200,000,000. The replay over 30 days shows the current version acting on 9 approvals and the candidate on 23: 14 new work items, each listed with the order number and amount (sum 4,210,000,000), none removed, and 2 events counted `replay_not_reconstructable` because their orders' approved versions were in a deleted draft's history. The submitter reads the 14 orders and decides that the warehouse can take them. An approver without the `SOUTH` branch sees only the orders of the other branches in the same diff. Had the owner covered only `NORTH`, the diff would also have returned `automation_owner_scope_limited` with the count of approvals outside her scope, which are not evaluated.

**An upgrade that invalidates a rule.** Core 1.4 deprecates the condition field `amount_company` of `SalesOrderApproved` in favour of `total_amount_company`. At the 1.4 upgrade the check writes a `deprecation_found` transition and raises `artifact_reference_deprecated`, and the rule keeps working. At 1.5 the field is removed: `RunArtifactUpgradeCheck` finds the reference unknown, disables the rule (`upgrade_invalid`), writes an `invalidated` transition and raises `artifact_invalidated` for the sales manager with the finding. She drafts version 4 with the new field; its tests and replay match version 3's, and the activation follows the normal path. Nothing failed silently between the upgrade and her fix: the rule simply did not run, and the item said so.

## Context

Spec 16 describes five customization levels and puts the whole of it after Phase 1. The author's decisions of 2026-11-15 split the capability gap into this ADR (configuration) and ADR-0059 (AI tuning), and asked for configuration in the core now, because the first customers need "when X then Y" without code changes. Spec 16's rule "every customization is additive and never modifies core source code" holds: rules are rows over a published vocabulary.

How others do it, concepts only (the 2026-11-15 survey): SAP's flexible workflow and BRF+, Dynamics 365's workflow editor and business events, ServiceNow's flows, Salesforce flows and Odoo's automation rules all let key users compose conditions and actions over a vendor-owned vocabulary, and draw the code line in the same place. Their documented failures are self-triggering loops, unspecified ordering between rules, "latest" version binding, silent breakage on upgrade, scripts in configuration, short execution history and error floods. Each guard above answers one of them: the depth cap and same-target guard (ServiceNow caps indirect recursion at 3; Odoo keeps a per-chain set), evaluate-then-act, pinned versions per evaluation, upgrade re-validation, no scripts, kept execution records, and the breaker (Zapier's auto-off).

Review round 2 added that an out-of-scope subject must not be silent, that a hash of a hidden value gives it away, and that a pinned table version must be in force. Review round 1 found that a rule could read, store and show what its owner and readers may not see, that drafts made by a rule had fewer writers than ordinary consumer drafts, and that the graph check missed undeclared discriminator values and parallel activations. The owner's scope and consent, reader filtering, the three writers, conservative emits and the activation lock answer them.

A closed vocabulary is also what makes the configuration easy for agents to read, draft and check (ADR-0005), which is the project's first goal.

## Options considered

| Option | For | Against |
| --- | --- | --- |
| Three tiers over a registry vocabulary (chosen) | Verifiable; agents can draft and check rules; no code in data | Some requests become small code changes |
| A BPMN or orchestration engine | Long processes, waits, compensation | Versioning of running instances dominates the cost; approvals and hand-offs are already covered |
| Scripts or Python in configuration (Odoo server actions) | Unlimited | Bypasses review, static analysis and upgrade tests; a direct path for injection |
| An expression language now | Fewer duplicate rules | A new surface to secure before structured conditions are shown to be too weak |
| Rules act as a dedicated automation actor kind | Clear in policy tables | A new actor kind in every policy, permission and audit path; the owner's rights would still be needed |
| Rules act as `system` on behalf of a consenting owner whose rights and scope cover the rule (chosen) | One accountable person, rights re-checked each time, no oracle | A lost right stops the rule (by design, through the breaker) |
| Readers see stored values as recorded | Simple | An execution record would leak fields and records the reader may not read |
| Hashes in place of hidden values | The reader sees that a value exists | A hash of one of a few thousand amounts is found by trying them |
| Reader filtering with omission and a marker; personal values under a keyed hash (chosen) | ADR-0017 holds for stored records too; nothing to invert | An `acted` outcome still tells the reader that the conditions held |
| Depth cap in the dispatcher and database (chosen) | Holds whatever rules authors write | One more pair of columns on events and audit records |
| Depth left to rule authors | Simpler | Loops are the commonest failure in every surveyed platform |
| Hit policies `unique` and `monotone` only (chosen) | Results never depend on row order; checkable | Less intuitive than "first match" |
| Completeness required | Every input decided | The exact check is intractable at useful sizes; gaps are often intended |
| `decision_no_match` handled by each use, completeness proved when cheap (chosen) | Tractable; no silent default | Each rule states a handling |
| Rules bound to a table's version in force | One edit changes many rules | A rule's behavior changes without its own replay |
| Rules pin table versions (chosen) | A rule changes only with its own version | A new table version needs new rule versions |
| A new design file for the DDL (chosen) | Loads and changes apart from the platform file and parallel drafts | One more file in `load_all.py`'s set (it takes every `design/*.sql`) |

## Constraints that come with the decision

- **ADR notes:**
  - ADR-0008 rule 1: `is_automation_allowed`, emitted events with discriminator values, trigger declarations, gate fields, hold commands, decision points; rule 5: the causation chain is assigned by the dispatcher;
  - ADR-0013 rule 2: the causation columns; rule 9: consumer commands inherit chain and depth, and `automation_dispatch` acts for the rule owner; rule 12: configurable agent triggers start through automation rules;
  - ADR-0022 rule 2: modules `configuration` (layer 2) and `automation` (layer 5), their imports, and the hook `artifact_checks`;
  - ADR-0027 rule 10: the `configuration_state` row in class 3;
  - ADR-0029 rule 5: activation and promotion of configuration artifacts use the carrier;
  - ADR-0038 rule 2: the causation columns on `audit_record`;
  - ADR-0042 rule 7: the kind rules `named_by_raiser`; rule 18: the new kinds;
  - ADR-0050 rule 12: claimable kinds declare `wake_up` and agent types may declare configurable triggers; rule 16: `agent_wake_up` skips configurable kinds, and runs started from events inherit the chain; rule 51: the view `automation_execution_overview`, filtered by the reader.
- **DDL:** [DS-28-34-configuration-artifacts.sql](../design/DS-28-34-configuration-artifacts.sql) (new, with its row-level security); [DS-05-platform.sql](../design/DS-05-platform.sql): the causation columns on `outbox_event` and `audit_record`.
- **DS-04:** the check order (steps 1 and 2), the registry vocabulary section, the errors and check results of rule 28.
- **Catalogs:** the work item kinds, INV-670 to INV-676, INV-686 and INV-687, EC-156 to EC-162 and EC-167, the leaves `configuration` and `automation`.
- **Other design items:** DS-16 (the invariants; a property test that rule evaluation is independent of rule order); DS-17 (setup events for drafted artifacts and upgrades; the edge cases); DS-30 (the rule and table editors, the replay diff screen); DS-33 (the view and its reader filter); DS-37 (`RunArtifactUpgradeCheck` in the upgrade procedure).
- **Author decisions (open questions):**
  - which agent triggers become configurable (rule 7; interim: none);
  - out-of-scope subjects as counted non-matches, hidden values omitted at read with personal values under a keyed hash, and a loop through a scheduled job only as a check result (rules 9, 11, 15);
  - the breaker's defaults (rule 16) and the reading that notices are allowed on tainted subjects (rule 9);
  - spec 16 says its levels are after Phase 1, and spec 10 says Phase 1 has "no rule language yet"; this ADR puts levels 1 and 3 in Phase 1 as structured rules without a language, as the author asked; the author-owned text needs the update;
  - build placement (interim): the tables and automation rules with the work queue at step 5, parameter sets with the bank cascade at step 6, because build order is the author's (ADR-0005 item 2).

## Revisit when

- Structured conditions force companies into many near-duplicate rules (W9).
- Two concrete long-running processes need waits and compensation across documents (W10).
- A module declares its first decision point or hold interface.
- The author answers which agent triggers become configurable.
