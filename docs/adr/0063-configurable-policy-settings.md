# ADR-0063: Configurable policy settings

Status: accepted (2026-11-15) under ADR-0005, reviewed by Claude Fable 5.2 (builder Claude Opus 5.5) after five review rounds.
Design items: DS-28 (settings and configuration), DS-04 (errors), DS-32 and DS-34 (agent settings), DS-36 (data processing), DS-20, DS-25 and DS-42 (master data, cash and barcode settings). Related decisions: D2, D12, D14. Principles 2, 3, 7, 12, 13. ADR-0004, ADR-0005, ADR-0016, ADR-0020, ADR-0021, ADR-0029, ADR-0043, ADR-0044, ADR-0048, ADR-0050, ADR-0051, ADR-0053, ADR-0054, ADR-0055, ADR-0056, ADR-0057, ADR-0058, ADR-0059, ADR-0060, ADR-0061, ADR-0062; spec 03, 10, 16, 17.

## Decision

The author's direction of 2026-11-15: survey best practice and follow it, keep hard locks to a minimum, and make policy configurable so that each customer sets it at implementation. Country packages fill neutral settings later; this ADR names no country's law, example or value. The chief architect's decisions on the four 2026-11-15 surveys (autonomy, data processing, extensibility, master data and narrative) are applied here.

**One registry, extended rather than doubled.** The core already registers every regime setting key it reads (ADR-0016 rule 10), stores a company's regime options as dated company rows (ADR-0016 rule 11), and names company settings such as `automation.breaker_failures` under the leaf `company_setting`. This ADR turns that key registration into the one settings registry for every scope: each definition states its scope, type, core default or fail-closed, hard bounds, which direction is tighter, the leaf whose holder changes it, when a change takes effect, and which evidence a loosening outdates. Company-held values of every scope live in one append-only table, `setting_value`. Agent type settings, data-processing permissions, parameter sets and package rows keep their own tables; the registry points at them.

**Tightening is immediate; loosening is a proposal.** Following EU AI Act Article 14, NIST AI RMF MANAGE 2.4 and SOX change control: one person holding the leaf tightens a setting at once (the stop button); loosening goes through a change proposal approved by a second person, takes effect from approval (or from the next period start where declared), and marks dependent auto-post or promotion evidence outdated. Every change is a row with old value, new value, actor, reason and, for a loosening, the proposal and approver.

**Few hard locks, each with its reason** (rule 6). Everything else in the policy areas the surveys covered becomes a bounded, registered setting with a safe core default: extraction trust, LLM-originated bank rules, bank charges, promotion and demotion thresholds, agent wake-ups and drift, analysis promotion, personal data per request, tainted catalog reads, analysis questions, the data-processing policy schema, extension points, automation limits and the breaker, product codes, unit names, purchase return value, narrative mode, barcode interpretation and near-duplicate invoices.

**Nothing changes silently.** A company starts on safe defaults; a new setting's default reproduces today's behavior unless that behavior was unsafe, and then this ADR says so and the upgrade raises a work item.

### Rules

**The registry and the change path**

1. One settings registry (extends ADR-0016 rule 10):
   - **Definition.** Every setting the core reads is registered in code with: `key` (lowercase dotted segments; a segment in angle brackets, such as `<agent_type>`, is a declared placeholder whose values the registry lists), `area` (the setup group), `scope` (one or more of `installation`, `regime`, `company`, `product_category`, `money_account`, `scanner_profile`, `agent_type`, `rule_version`), `storage` (where the key's non-company values live; company-held values of every key live in `setting_value`, rule 2), `value_type`, `core_default` (a value, `unset` for "no value, no limit", or `fail_closed`), hard `bounds`, `direction` (rule 3), `leaf` (an authorization leaf of ADR-0054 rule 7, or `package` for package rows and `operator` for deployment values), `change_effect` (`immediate`, `period_start`, `package_release`, `deployment`) and `outdates` (`auto_post`, `promotion` or `none`, rule 3).
   - **Fail closed where ADR-0053 requires it.** A key whose content is a regime's law or accounting rule has no core default (`fail_closed`): reading it without a value fails with `regime_configuration_missing` (ADR-0016 rule 10), as `data_processing.policy` and the purchase return keys do. Every other key has a core default that a company can run on.
   - **Effective value.** `registry.contract.get_setting(company, key, scope_ref, date)` returns the value in force on the date by the key's date rule: the narrowest declared scope that holds a row (product category, money account, scanner profile or agent type before company), then the regime's row, then the core default; an installation value, where declared, is a maximum that narrower scopes may only tighten. Installation rows stay visible only under the setting value `installation` (ADR-0017 rule 19); company sessions read an installation maximum only through the security-definer function `setting_installation_value`, in the pattern of `nativeflows_claim`, which returns the key, the value and its effective date and nothing else (the roles step revokes EXECUTE on it from PUBLIC and grants it to the application roles); `get_setting` applies the maximum at read time, and the insert trigger also refuses a company value looser than the installation value in force. It returns the value with its source (`core_default`, `regime`, `company`, or the narrow scope), so every decision records which value it used.
   - **The catalog.** [settings.csv](../catalogs/settings.csv) (owner DS-28) lists every setting this ADR registers or touches, one row per definition, with the columns above plus `source`, `added_in` and `meaning`. It is seeded now and generated from the registry once `registry` exists, like the work item kinds. The lab checks it (rule 30).
   - **Reference data.** Definitions are installation data: the registry writes one `setting_definition` row per key at startup, nobody edits them, and agents read them through `ListSettingDefinition` as reference data (ADR-0050 rule 27, item 4).

   Note ([ADR-0069](0069-business-unit-dimension.md), proposed 2026-11-17): value type `code`: one code of the table the bounds name, checked by the command. First used by `ledger.business_unit.default`.
2. Where values live:
   - **`setting_value`** (owner `registry`, company data, append-only, [DS-28-settings.sql](../design/DS-28-settings.sql)) holds every company-held value of scope `company`, `product_category`, `money_account`, `scanner_profile` or `agent_type`, and the installation values (company null, readable only under the setting value `installation`, ADR-0017 rule 19). A row carries the key, scope, scope reference and placeholder values, the value, `effective_from`, the replaced value (the value in force it replaces: the row for the same company, key, scope, scope reference and placeholder values, else the company row for a narrower scope, else the core default), `change_kind` (`tighten`, `loosen`, `neutral`), the reason, the human who made the change, and for a loosening the change proposal and its approver. It copies the definition's type, bounds, allowed values and direction. A `BEFORE INSERT` trigger ties every copy to `setting_definition`, checks the scope and that the placeholder values name exactly the key's placeholders, refuses a value looser than the installation value in force, derives the replaced value itself (filling it when absent and refusing a different one, JSON null included) after taking a transaction-level advisory lock on (company, key), so changes of one key in a company are serialized, and derives `change_kind` from the direction and that value; the database then refuses a value outside the bounds, a loosening without a proposal (whatever label or replaced value the row carries, a first value looser than the core default included), and a loosening approved by the person who proposed it. Left to the command and the invariants: that the proposal was approved and executed (INV-701), that the date is valid (INV-702), and that a scope reference names a record of the company.
   - **Company regime options** (ADR-0016 rule 11) are `setting_value` rows of scope `company`; `UpdateCompanyRegimeOption` writes them under this rule's checks and rule 3's path.
   - **Safe functions.** The trigger and the read function name every table with the schema and pin `search_path = nativeflows, pg_temp`, so a temporary table cannot stand in for `setting_definition` or `setting_value`; application roles get no `TEMPORARY` privilege on the database and SELECT only on `setting_definition` (ADR-0017 rule 18 note); the advisory lock is transaction-level, allowed on trigger paths (ADR-0022 rule 13 note).
   - **Kept in their own tables,** with the registry's `storage` naming them: package rows (`regime_setting`, ADR-0016 rule 9), agent type settings (`agent_type_setting`, ADR-0050 rule 14), data-processing permissions (`data_processing_permission`, ADR-0057 rule 20), the parameter sets of tunable functions (ADR-0059 rule 4), per-rule overrides inside an automation rule version's content (ADR-0058, hashed with the version), and installation values from the deployment configuration (DS-37), which the startup step records as `setting_value` rows when they change: `changed_by_user_id` is the operator account named in the deployment change and, for a loosening, `approved_by_user_id` a second operator account that approved it.
   - **History is the audit trail.** Rows are never updated or deleted; the value in force on a date, for a key, scope, scope reference and placeholder values, is the row with the latest `effective_from` on or before it (the latest recorded among equals). Each change is also an audit record of its command (ADR-0038).
3. The asymmetric change path:
   - **Direction.** Each definition declares `higher_tighter`, `lower_tighter`, `true_tighter`, `false_tighter`, `subset_tighter`, `superset_tighter`, an order from loosest to tightest (`order:a<b<c`), or `neutral`. A change is a tightening, a loosening or neutral by comparing the new value with the effective value it replaces at that scope.
   - **Tightening** is immediate, by one person holding `edit` on the definition's leaf, through `UpdateCompanySetting` (rule 28). It never waits for an approval, so reducing autonomy is always one person's act.
   - **Loosening** is accepted only from the execution of an approved change proposal (ADR-0029, ADR-0043 rule 12): a person with `edit` on the leaf submits it with a reason and, where the definition asks for it, evidence; a person holding the leaf at `full` who is neither the submitter (`approver_is_submitter`) nor a writer of the proposal (ADR-0055 rule 7, condition 5) approves it. A direct loosening returns `proposal_required`. As for agent promotions (ADR-0050 rule 14), the small-company mode does not lift `approver_is_submitter` here, so a one-person company cannot loosen any setting, the first raise of `cash.bank_charge.auto_post_ceiling` from 0 included; it runs on the core defaults or tighter.
   - **When it takes effect.** From the execution of the approval, or from the first day of the next posting period where the definition says `period_start`; never backdated. A date that breaks this returns `setting_effective_date_invalid`.
   - **What a loosening outdates.** A definition with `outdates: auto_post` makes the executing transaction mark the stored evidence of every enabled auto-post rule version of the company that depends on the key as outdated: `policy_rule_version.shadow_evidence_outdated_by` names the new `setting_value` row (ADR-0059 rule 6's marker). Re-arming needs a new rule version with new evidence. With `outdates: promotion`, evidence is judged under the thresholds in force when its promotion executes, and stored evidence that was insufficient never becomes sufficient by a later loosening: the promotion needs new evidence.
   - **Neutral** changes are made directly by a person holding `edit` on the leaf, with a reason, from the date the definition allows.
   - **Never by agents or rules.** `UpdateCompanySetting` is `human_only` and on no agent tool list (ADR-0050 rule 30); an automation rule never changes a setting (ADR-0058 rule 3).

   Note (Final simulation review, 2026-11-15): the dependency is declared, not inferred. `EnablePolicyRule` stores with the evidence the registered keys with `outdates: auto_post` that the evidence hook read when it judged the evidence, in `policy_rule_version.evidence_setting_keys` (set once with `shadow_evidence`, never empty), and their values in force in `shadow_evidence.settings`; the hook returns both ([ADR-0043](0043-policy-and-approval.md) rule 14 note). The executing transaction of a loosening of a key marks `shadow_evidence_outdated_by` on the company's enabled rule versions whose evidence is not yet outdated and whose `evidence_setting_keys` contain the key, and on no other. A cascade rule lists `auto_post.max_error_rate` and the `cash.auto_post.*` keys it read; a `bank_charge` rule also lists the `cash.bank_charge.*` keys; an import rule of [ADR-0064](0064-production-agent.md) lists the `production.confirmation.*` and `production.mes_import.*` keys. The dependency is per key: a loosening at one scope of a scoped key, such as one money account's `cash.bank_charge.codes`, marks every rule version that lists the key, the safe side. DS-05 states the marker's statement on the column; lab check `t15_platform_ddl.py` L06 to L08.

   Note ([ADR-0067](0067-quickflows-operating-presets.md), 2026-11-17 (proposed)): before go-live (no journal entry outside the migration fiscal year: `company.first_operating_posting_at` is null), a loosening of a key whose `outdates` is `none` is accepted without a proposal from the implementer an owner acknowledged (`AcknowledgeCompanySetup`), and the `setting_value` row records the acknowledgement instead of a proposal and approver. So a one-person company can set its policy at implementation. After go-live this rule applies in full again, and `setup_loosening_review` lists the setup loosenings for the owner ([ADR-0067](0067-quickflows-operating-presets.md) rules 7–10).
4. Bounds and scopes:
   - **Hard bounds** are part of the definition: a closed numeric range, an open range (`0..`, at least 0), the allowed values of an enumeration, or a schema. A value outside them, a fractional value of an integer type, or a value that breaks an order between settings the registry declares (such as `automation.breaker_consecutive` at least `automation.breaker_failures`) returns `setting_out_of_bounds`. No bound includes a value that switches off a hard lock (rule 6).
   - **Scopes.** A key accepts values only at its declared scopes; an unknown key, an undeclared scope or a scope reference that names no record of the company returns `setting_scope_invalid`. A narrower scope changes the value for its records through the same path: overriding a company value with a looser category value is a loosening.
   - **Placeholders.** A key with a placeholder exists only for the values the registry lists for it (document types and fields that declare trust settings, agent types and their kinds, extension points, the date AIs of rule 26).
5. Setup and upgrades:
   - **At implementation.** The setup flow shows the registry grouped by `area`, each setting with its core default, bounds, direction and meaning; a company starts on the core defaults, which are the safe values. Setting a value during setup follows rules 3 and 4: a first value is compared with the core default it replaces, so it is direct for a tightening or a neutral value and a proposal for a loosening, as later.
   - **Nothing silent on upgrade.** A new setting's core default reproduces the behavior before it, unless that behavior was unsafe. Then the ADR that adds it says so, and the upgrade step `RunSettingUpgradeCheck` raises `setting_review_required` for `company_owner` in every company the change affects, naming the key, the old behavior and the new default.
   - **This ADR's behavior changes** against the accepted ADRs, each marked:
     - **Tightening:** personal values on every request need a permission (rule 15); a near-duplicate invoice holds payment until a person reviews it (rule 27); an OCR confidence floor of 0.90 for trusted fields (rule 7; ADR-0057 rule 17 had none); at most 500 executions of one rule per hour (rule 21) and at most 200 active rules (rule 20; ADR-0058 had neither); analysis questions are pseudonymized before a model call (rule 17).
     - **Loosening:** demotion is judged only over at least 30 decisions (rule 10; ADR-0059 rule 21 had no floor), because fewer decisions demote on noise, as decision A4 says; declared projections are read by tainted runs by default (rule 16; ADR-0050 rule 27 and ADR-0062 rule 17 kept the literal scope), by the author's direction and open for the author's confirmation; the best-before date no longer fills a lot's expiry date (rule 26), so fewer lots are blocked by expiry, because a quality date is not a safety date.
     - **New behavior, off or unchanged by default:** the `bank_charge` class (rule 9) and LLM-originated rules (rule 8), both off; wake-up modes (`always`), drift actions (`signal`), the breaker settings (5, 60, 20), product codes, unit names, the purchase return options and the narrative mode keep today's behavior.
     - The designs of rules 15, 21 and 26 are not built yet, so no installation changes; `setting_review_required` is raised for any company that exists when a change is built.

   Note ([ADR-0067](0067-quickflows-operating-presets.md), 2026-11-17 (proposed)): "a proposal for a loosening, as later" now reads "a proposal for a loosening, except on the setup path before go-live". Operating presets apply a named, versioned set of values through this rule's checks, each value recorded with the preset's code and version; the preset `standard` reproduces the core defaults ([ADR-0067](0067-quickflows-operating-presets.md) rules 2–6, 9).
6. Hard locks, kept few, each with its reason:

   | Hard lock | Reason |
   | --- | --- |
   | Numbers come only from code (Principle 13); analysis prose is dropped on any unbacked number (rule 25) | A wrong figure in an ERP is a booking or a decision; model text is not a source of figures |
   | The audit trail, and the processing log written before every model call (ADR-0050 rule 10) | Accountability and the processing record cannot depend on a setting |
   | Agents never submit, post, send or approve on their own authority; auto-post only on the evidence-gated deterministic paths (ADR-0043 rule 9) | Spec 03 rules 1, 5 and 6; segregation of duties |
   | Taint persists, and a tainted run writes drafts only (ADR-0029, ADR-0050 rule 25) | The prompt-injection containment; no setting may open an exit for outside content |
   | Labels from the schema are never lowered; an unknown kind counts as personal; sensitive personal values are never sent in Phase 1 (ADR-0050 rule 9) | Detection-based masking misses data; the schema knows |
   | The automation circuit breaker cannot be turned off, its failure definition is fixed, and the depth cap stays 3 (rule 21) | Termination and bounded side effects |
   | No AI-written code runs without a human review of its source and a reproducible build (rule 19; ADR-0059 rule 24) | Code is reviewed before it runs; a model cannot ship code |
   | Check digits and other integrity checks of standards (GS1, IBAN, tax ID rules) | They are the standard, not a preference |
   | Every learned or probabilistic matching path that auto-posts (the scored matches of the bank cascade and of matching rules, tuned parameter sets) needs evidence of N proposals with at least (1 − `auto_post.max_error_rate`) posted unchanged, N ≥ 3 ÷ `auto_post.max_error_rate`, the rate never above 2% (rule 10); a confirmed wrong auto-post suspends auto-post at once | A threshold without an evidence floor is not a control an audit can rely on |
   | An `llm_suggestion` draft is never auto-posted (rule 8) | Spec 03 rule 1 at run time |

   A deterministic `bank_charge` rule (rule 9: a configured bank transaction code on that money account, a debit, no counterparty account, an amount cap, period-end confirmation) is not a learned or probabilistic path; it is governed by its determinism, its cap and the confirmation.

   The table is the cross-cutting set. The "Hard:" bullets of rules 7–27 are scope limits of each setting: no value of that setting relaxes them.

**Autonomy**

7. Extraction value trust (ADR-0057 rule 17):
   - **The interim reading is the default.** Rule 17's computed trust stands, with one addition: the OCR confidence floor below (a tightening, rule 5).
   - **Settings,** company scope: `intake.trust.<document_type>.<field>.require_confirmation` (default false: a person must confirm the field before it is trusted), `intake.trust.<document_type>.min_passed_rules` (default 1, bounds 1 to 10) and `intake.trust.ocr_min_confidence` (default 0.90, bounds 0.80 to 0.99, applied where the OCR engine reports a confidence; below it the field is untrusted). The trust view reads them.
   - **Loosening,** also below the core default down to the lower bound, is a proposal that names `extraction_mapping` evidence of at least 95% field agreement over at least 50 documents (ADR-0059 rule 18). Nothing loosens past the bounds or the shape table.
   - **Hard:** free text, URLs, e-mails and phones are never trusted; vision values are never trusted before a person confirms them; nothing is trusted from an extraction with a failed or mismatched signature or suspected hidden text; trust alone never posts or changes master data.
8. LLM-originated bank matching rules (ADR-0048 rule 9; ADR-0051 rules 18–19; ADR-0059 rule 10):
   - **Setting** `cash.auto_post.accept_llm_originated_rules`, company, default false. Its bound is false until the author rewords spec 03 rule 1 (ADR-0029 rule 14), as `extensions.wasm_enabled` is bounded while no runtime exists: no company can enable it before then.
   - **When true,** the human approval of a matching rule version ends the LLM's contribution to the rule's later matches only if all of these hold: the token is a whole, reference-shaped token of the description, not generated; the rule went live on independent evidence (at least 10 suggest-mode drafts, at least 99% posted unchanged, ADR-0059 rule 18); its approver is neither its proposer nor the human the drafting run acted for; the version records `origin` `llm_proposed`; and the auto-post rule's own evidence (rule 10) counts proposals of that basis. Otherwise its drafts get `human_post`.
   - **Hard:** `llm_suggestion` drafts never auto-post; an LLM-proposed rule is never approved by its proposer; the counterparty caps of ADR-0048 rule 9 still apply.
   - **Partly answered by the author's direction:** the setting exists, bounded false until spec 03 rule 1 is reworded; enabling it before then returns `setting_out_of_bounds`. The wording of spec 03 rule 1 is the author's; it should say "unless the company enables approved LLM-originated rules under ADR-0063" (open question).

   Note ([ADR-0065](0065-deterministic-auto-post-gateway.md), 2026-11-16 (proposed)): the bound is lifted under the author's decision of 2026-11-16 on tainted auto-post: the setting's bounds are true and false, its default stays false, and enabling it is a loosening by proposal. The five conditions and the hard bullet above stay. The new wording of spec 03 rule 1 is the author's (open question) ([ADR-0065](0065-deterministic-auto-post-gateway.md) rule 12).
9. Bank charges, a new account-rule class `bank_charge` (ADR-0059 rule 10):
   - **Counterparty check.** A `bank_charge` rule passes ADR-0048 rule 9's counterparty check, instead of drafting under the unverified cap, when the line is a debit of the money account, carries a bank transaction code (`bank_statement_line.bank_transaction_code`, from the statement reader) listed in the money account's setting `cash.bank_charge.codes`, and names no counterparty account at all (`counterparty_account_number` is null). Its draft has match basis `bank_charge_rule` and is not flagged `counterparty_unverified`.
   - **Auto-post per rule,** default off. A rule version may enable it only with an `amount_max` at or below the company setting `cash.bank_charge.auto_post_ceiling` (default 0, which disables the class; no other core value, because an amount is currency-dependent). As a deterministic rule it is outside rule 10's floor; its evidence is at least `cash.bank_charge.min_evidence_lines` lines (default 6, bounds 3 to 50) over at least `cash.bank_charge.min_statement_months` statement months (default 3, bounds 1 to 12), every one posted unchanged to the rule's account. The owner still confirms auto-posts in batches before close (spec 03 rule 6; ADR-0043 rule 14).
   - **Hard:** never when open items also match the line; never when two rules match it; never above `amount_max`; never from the LLM's purpose classification (`suggested_purpose` `bank_charge`).
   - **Answered:** bank fees may auto-post, configurable, off by default.
10. Promotion, demotion and the acting error ceiling (ADR-0059 rule 18; ADR-0051 rule 18):
    - **The acting ceiling.** `auto_post.max_error_rate`, company, default 1%, bounds 0.1% to 2%. The evidence of an auto-post rule on a learned or probabilistic matching path needs N proposals with at least (1 − rate) posted unchanged, N ≥ 3 ÷ rate, over at least two statement months, and none posted to another partner. This is an observed error rate at most the ceiling over N cases; it is not a 95% bound, which holds only when none was changed. The default gives ADR-0051 rule 18's 300 proposals at 99% exactly, so nothing changes on upgrade; 2% gives 150, 0.1% gives 3,000.
    - **Windows, not lower bars.** `artifacts.<function_or_kind>.max_window_days` (default 90, bounds 28 to 365) lets a small company collect evidence over a longer window; the minimums never fall below the declaration's small-company minimum, and they never lower the acting ceiling. The suggest-mode minimums of the bank cascade are settings with bounds: `artifacts.cash.match_bank_line.min_backtest_cases` (200, bounds 50 to 5,000) and `artifacts.cash.match_bank_line.min_live_cases` (100, bounds 30 to 5,000); other functions declare theirs the same way. The precision targets, the held-out golden-case threshold, the demotion formula and the held-out share stay ADR-0059's declared values for now, not settings (open question).
    - **Demotion** stays as ADR-0059 rule 21 defines it, judged only over at least 30 decisions (a loosening, rule 5), the window widened as for re-evaluation (ADR-0059 rule 4) until 30 are reached.
    - **Hard:** any auto-post that a person reverses, or records as wrong when confirming (ADR-0043 rule 14), marks its rule version's evidence outdated in the same transaction and raises `auto_post_suspended` for the rule's owner; the rule's later postings get `human_post` until a new rule version brings new evidence.
11. Agent wake-up modes (ADR-0058 rule 7; ADR-0050 rules 12, 16):
    - **Setting** `agents.<agent_type>.wake_up_mode.<kind>`, scope `agent_type`, values `always`, `by_rule`, `off`, default `always`: today's behavior, so an upgrade changes nothing.
    - **Meaning.** `always`: `agent_wake_up` starts the agent as today. `by_rule`: `agent_wake_up` skips the kind, and only an automation rule with action `start_agent` and its own conditions starts the agent; items no rule starts stay with people. `off`: every item goes to people.
    - **Which kinds.** Only kinds an agent type version declares `configurable` accept the setting. The first two are the quotation agent's `inbound_message_matched` and the purchase invoice agent's `supplier_invoice_received`, declared in their next versions. "Configurable" now means that the company chooses the mode, with `always` as the default; ADR-0058 rule 7's "configurable means configured" applies only under `by_rule`.
    - **Conditions** of such rules read trusted metadata only: the receiving mailbox or channel, the partner matched by address (never by a model), whether the partner is known, branch, document source and attachment type.
    - **Change path.** Narrowing (`by_rule`, `off`) is one person with `edit` on `agent`; widening is a proposal.
    - **Hard:** no agent wakes an agent; a rule never widens tools, scope, budget or taint handling; no trigger on approval, posting or send events.
12. Drift action for agent types (ADR-0051 rule 5; ADR-0059 rule 21):
    - **Setting** `agents.<agent_type>.drift_action`, scope `agent_type`, values `signal`, `pause_new_runs`, `demote_to_shadow`, default `signal` (today's behavior). When the quality monitor raises `agent_quality_below_threshold`, `pause_new_runs` also makes the effective mode `off` for new runs until a person resolves the item, and `demote_to_shadow` makes it `shadow` until the type is promoted again (ADR-0050 rule 14).
    - **Hard:** drift that outdates auto-post evidence always suspends auto-post (rule 10); artifacts keep their automatic demotion (ADR-0059 rule 21).
13. Analysis agent examples (ADR-0060 rule 25):
    - **Settings** `artifacts.analysis.min_verified_examples` (default 30, bounds 0 to 500) and `artifacts.analysis.allow_synthetic_only_promotion` (default true), company.
    - **Below the minimum,** with synthetic-only promotion allowed, the evidence is the synthetic CI report and every answer shows "evaluated on the synthetic suite only". **Data processing**

14. The personal vision seat and the provider registry (ADR-0057 rules 20–21):
    - **Allowed by permission.** A company may permit the installation's cloud provider for `extraction_vision_personal` through a `data_processing_permission` row (company, data class, seat class, provider, region, optional `purposes` from `supplier_invoice`, `contact_card`, `inquiry_lines`, `product_source`). Default: no row, so the seat is off.
    - **Provider registry** (DS-37 adapter configuration) gains, per provider endpoint: `retention_days` (0 for zero retention), `abuse_review` (`human`, `automated`, `none`), `is_training_on_customer_data` (must be false; an endpoint that says true is refused at startup) and `terms_ref` (the data-processing terms in force). A permission records the terms reference and retention it was approved under.
    - **Leaf.** A new leaf `data_processing` under `agent` (module `agents`) holds `SetDataProcessingPermission` and `EndDataProcessingPermission`, so a data-protection role can approve without the right to manage agents. Changes stay four-eyes proposals (ADR-0057 rule 20).
    - **Suspension.** When the registry changes an endpoint's region or terms reference under an active permission, `RunDataProcessingProviderCheck` (at startup and daily) sets the permission's `suspended_at` and raises `data_processing_permission_suspended` for `company_owner`; a suspended permission covers nothing until a new one is approved.
    - **Hard:** the seat has no tools; `routing_switch` stays the company's kill switch; no sensitive personal data class in Phase 1; images are sent or refused whole.
    - **Answered:** the seat may use the cloud provider under a permission; adding it to spec 17's seat list stays the author's (open question of ADR-0057 rule 21).
15. One gate for personal values (ADR-0050 rule 9; ADR-0057 rule 20):
    - **Every request.** The gateway applies the regime policy and the company's permissions to every request that carries a `personal` value, field values included, not only to whole attachments and the vision seat.
    - **Without a permission** covering the data class, seat class, provider and region, personal values become typed placeholders or shape masks, as with the switch on today; a step whose template marks the value required is not sent and the run ends `routing_blocked`. With `routing_switch` on, everything personal is stripped whatever the permissions say.
    - **Never send.** `data_processing.never_send_fields`, company, a list of `table.field` paths, default empty, can only narrow: listed fields are stripped even where permitted.
    - **Upgrade.** Before this rule, field-level personal values went to personal seats with the switch off. A company that relied on that needs its permissions approved; the upgrade raises `setting_review_required` (rule 5).
    - **Hard:** labels from the schema are never lowered; the exact-text residual scan; the log is written before the call.
16. Tainted reads of declared projections (ADR-0050 rule 27; ADR-0062 rule 17; ADR-0029 rule 14):
    - **Registry attribute** `tainted_projection` on a query's result model: the columns a tainted run receives. CI accepts only closed shapes (ID, code, unit, status, category, date, quantity) and `internal` names, never prices, costs, stock, partner columns, `personal` columns or free text.
    - **First instance:** `ListItemCandidate`, the query ADR-0062 rule 17 called `ResolveItemCandidates` (ADR-0004 rule 21 allows only `Get`, `List`, `Evaluate` and `Render` as query verbs): id, code, name, unit, category and status of items, by typed match keys (code, barcode, normalized name), at most 20 rows per call and at most 10 calls per run; rows restricted to another partner are excluded. Beyond the call cap it returns `tainted_projection_cap_reached`.
    - **Setting** `agents.tainted_reference_reads`, company with an optional per-agent-type value, `literal` or `declared_projections`, default `declared_projections`. An agent type version uses a projection only when it names the query on its tool list.
    - **The reading.** Under the author's direction, declared projections join the reference data of the literal scope (ADR-0050 rule 27, item 4) as this ADR's reading of spec 03 rule 1; the setting only narrows that reading back to the literal scope, so no setting widens the floor (ADR-0029 rule 14). The run stays tainted; projected calls are recorded in the step's `context_refs` with the projection version and the row count.
    - **Partly answered:** the tainted catalog read for matching, open for the author's confirmation of the reading (ADR-0005 item 7).
17. Analysis questions (ADR-0060 rule 21):
    - **The label stays `personal`.** A question may name a person; a pseudonymized question is still personal.
    - **Setting** `analysis.pseudonymize_known_subjects`, company, default true: before the gateway call, code replaces each match of the company's own personal records that the asker may read (individual and sole-proprietor partners, contacts, employees) with a handle such as `[partner:<id>]`, which the planner may use as a filter value and code dereferences. The processing log records the handles substituted, never the values.
    - **Under rule 15,** the question reaches the router and planner seats when a permission covers them; otherwise placeholders apply, and with the switch on nothing is sent.
    - **Answered:** the label question.
18. The data-processing policy schema (ADR-0057 rule 20; ADR-0053 rule 1):
    - **Widened core schema** of the regime setting `data_processing.policy`, per data class: `model_processing` (`allowed`, `forbidden`, `company_option`), `cross_border` (`allowed`, `requires_assessment`, `forbidden`, `company_option`), `assessment_kind` (a package code), `assessment_deadline_days` (from the first transfer), `allowed_countries` (an optional list of ISO codes), `max_provider_retention_days`, `requires_no_training`, and `exemptions` (package-declared conditions of core-registered condition types, as ADR-0053 rule 3's deductibility conditions).

**Extensibility and automation**

19. Extension points (ADR-0059 rule 24):
    - **Phase 1 ships the registry only.** A module may declare an `extension_point` (installation data written at startup): code, module, typed input and output schemas, a code default, ceilings for fuel, memory and deadline, the decision kind (`score`, `classification`, `derivation`, `validation`) and `is_gate_feeding`, whether its output may feed a gate (default false). No runtime ships in Phase 1, and ADR-0059 rule 24 stands.
    - **After Phase 1:** WebAssembly with deterministic fuel metering, under `extensions.wasm_enabled` (installation, default false; its bound is false while no runtime exists) and per company and point `extensions.<point>.max_fuel` (10,000,000 instructions, bounds 100,000 to 50,000,000 and the point's ceiling), `extensions.<point>.max_memory_bytes` (8 MiB, bounds 1 to 16 MiB) and `extensions.<point>.deadline_ms` (50, bounds 5 to 250). A module follows ADR-0059's lifecycle, pinned by content hash, tests approved first, a reproducible build from reviewed source, and approval by a person with a technical role. A trap, exhausted fuel or a timeout returns the code default.

The spec texts are the author's: spec 16 should split level 1 into 1a (Phase 1: settings, parameter sets, policy thresholds, approval pools, decision tables) and 1b (after Phase 1: user-defined fields and tables), and say level 3 is "structured rules over a registry vocabulary, no rule language", controlled by stored tests, a replay diff and a change proposal; spec 10 should say "no rule language; structured decision tables and automation rules (ADR-0058)" (open question).

    - **Export and import as draft** (flagged): `GetArtifactVersionContent` returns a version's canonical JSON and content hash; another deployment of the same customer imports it only as a new draft through the kind's draft command, recording the source hash, and the draft then runs its own tests, replay and proposal on that deployment's data.
21. Circuit breaker and flood guard (ADR-0058 rule 16):
    - **Breaker settings,** company, each with an optional override in a rule version's content (hashed with it): `automation.breaker_failures` (5, bounds 1 to 50), `automation.breaker_window_minutes` (60, bounds 5 to 1,440) and `automation.breaker_consecutive` (20, bounds 3 to 200, and at least `automation.breaker_failures`).

It raises `automation_rule_rate_limited` for the rule's owner, one per rule and business date.

Lab check `t24_settings.py` ([validation lab](../reviews/2026-11-14-design-validation/README.md)): the catalog is checkable (every row has scope, a default or fail-closed, bounds, a direction and a known leaf; the default lies within its bounds; every key this ADR names is in the catalog and the reverse); the change path as a pure function (tightening immediate, loosening only by an approved proposal from another person, outdating evidence) and in the database (the derived change kind, a first value looser than the core default, copies tied to the definition, the installation maximum); bounds as a property test over random values; the gates of rules 8 and 9; rule 11's default reproducing today's wake-ups; rule 21's bounds, breaker and flood guard; rule 24's period-start rule; rule 26's default; and, with `--load`, the DDL: definitions loaded from the catalog under their checks, values outside bounds refused by the database, loosening without a proposal or approved by its proposer refused, rows append-only, installation rows only under the installation setting, extension point ceilings and decision kinds, suspension pairs, and the new columns and values.

## Context

The author asked on 2026-11-15 for best practice, few hard locks and policy each customer sets at implementation, with no country content in this work. Four surveys of 2026-11-15 covered autonomy controls for AI and automation in finance ERPs, data processing for LLMs and prompt-injection containment, customer extensibility, and master-data conventions with generated narrative. Their shared findings:

- **Asymmetry is the governance rule.** Reducing autonomy (stop, demote, pause) is immediate and open to the responsible person alone; increasing it needs evidence, a second person and a change record (EU AI Act Article 14, NIST AI RMF MANAGE 2.4, ISO/IEC 42001 Annex A.9, SOX and PCAOB AS 2201 change control).
- **Vendors expose policy as bounded settings.** SAP Cash Application's confidence bands, Rossum's per-field thresholds, Business Central's text-to-account mapping for bank fees, Power Automate's bounded concurrency, Zapier's flood protection, GS1 parser options in Dynamics 365, duplicate-invoice checks in SAP and Oracle, and the narrative toggles of Tableau and Power BI are all customer settings inside vendor bounds, defaulting off for generative features.
- **Small companies get time, not a lower bar.** With n error-free cases, the 95% upper bound of the error rate is about 3/n, so 300 cases bound it at 1%.
- **Data processing is a permission per provider and region,** with masking by schema stronger than detection, and read-only projections acceptable for tainted runs when their information is bounded (FIDES, CaMeL, OWASP LLM01).

NativeFlows already has the pieces: regime settings registered by the core with dated rows (ADR-0016 rules 9–11), company settings named in many ADRs under the leaf `company_setting`, agent type settings with a promotion ladder (ADR-0050 rule 14), data-processing permissions by four-eyes proposal (ADR-0057 rule 20), parameter sets with bounds and safety caps (ADR-0059 rules 3–4), and the outdated-evidence marker (ADR-0059 rule 6). What was missing is one registry across scopes with direction, bounds and a stored change history, which this ADR adds by extending ADR-0016 rule 10 instead of inventing a second mechanism. SAP keeps such choices in Customizing tables with transport-based change control; this design keeps them as data with an in-system proposal, which an agent can read and reason about.

Several open questions were answered by the author's direction to make the policy configurable; others remain the author's because they change author-owned spec text (spec 03 rule 1, spec 10, spec 16) or because the core cannot decide them.

## Options considered

| Option | For | Against |
| --- | --- | --- |
| Extend ADR-0016's key registration to one registry over every scope, with one append-only value table (chosen) | One mechanism for agents and auditors; regime options and company settings share storage, checks and history | Every existing setting must be registered over time |
| A second, company-settings mechanism beside regime settings | Smaller change now | Two ways to read a setting; the decisions forbid it |
| Store each setting as a column of a module table (as `planning_setting`) | Typed columns | No common direction, bounds or history; every new setting is a migration |
| Symmetric change control (everything by proposal) | Simple | Slows the stop button; contradicts Article 14 and MANAGE 2.4 |
| Symmetric direct changes (everything by one person) | Fast | No segregation of duties on raising autonomy; fails SOX change control |
| Statistical acting ceiling with a bounded rate (chosen) | Small companies wait longer instead of lowering the bar; the default reproduces ADR-0051 rule 18 | Larger companies cannot go below 150 cases |
| Fixed 300 proposals for every acting path | Already designed | Cannot express a stricter or a bounded-exposure path |
| Bank charges by the unverified cap (status quo) | No new class | Fees never auto-post; every vendor surveyed posts them by rule |
| Wake-up mode with default `always` (chosen) | An upgrade changes nothing; companies narrow by rule | "Configurable" changes meaning from ADR-0058 rule 7 |
| "Configurable means configured" (ADR-0058 rule 7 as written) | Strict | Making a kind configurable would silently stop the agent in every company |
| Declared projections as reference data, narrowable by setting (chosen) | Useful matching under taint with bounded information; no setting widens the floor | A reading of a hard floor that the author must confirm |
| A setting that widens the tainted scope | Flexible | Spec 03 says no setting relaxes a hard floor (ADR-0029 rule 14) |
| Purchase return valuation as a new core setting with a core default | Simple | Accounting rules belong to the regime (ADR-0020 rule 5, ADR-0053) |

## Consequences

- **For companies:** every policy choice the surveys covered is a setting a key user sees at setup, with a safe default, bounds, a direction and a meaning; tightening is always available at once.
- **For agents:** settings are reference data with one read path and a source for every value; agents never change them.
- **For auditors:** the `setting_value` history gives old, new, actor, reason, proposal and approver for every change; loosening an acting setting outdates the evidence it touched.
- **For the build:** `registry` gains the settings registry, the value table, `UpdateCompanySetting` and the upgrade check at step 1 (platform); the agent, cash, intake, automation and barcode settings land with their modules' steps.
- **Upgrade behavior changes** are listed in rule 5, each marked a tightening, a loosening or new behavior; each raises `setting_review_required` where a company exists.
- **Interpretations for the author to confirm:** the LLM-originated rule reading (rule 8, bounded false until then), the declared-projection reading (rule 16), and the spec wording of rules 8 and 20.
- **Revisit when:** a company asks to loosen a setting past a hard bound; a second package declares settings this registry cannot express; the extension runtime is decided; evidence shows a default too strict or too loose for small companies.

## Edge cases and invariants

**Invariants** (block INV-700 to INV-729; INV-700 to INV-718 taken):

- **INV-700** `settings_registered` (platform): every `setting_value` names a registered key at a scope its definition declares, and its type, bounds, allowed values and direction equal its definition's and its value lies within them (a database check).
- **INV-701** `setting_loosening_approved` (safety): every `setting_value` with `change_kind` `loosen` names an executed, approved change proposal whose approver is neither its submitter nor a writer of it.
- **INV-702** `setting_effective_dates` (platform): no `setting_value` takes effect before it was recorded, and every value of a `period_start` key takes effect on the first day of a posting period.
- **INV-703** `setting_loosening_outdates_evidence` (safety): every loosening of a key with `outdates: auto_post` marked the evidence of every dependent enabled auto-post rule version of the company outdated in its own transaction.
- **INV-704** `auto_post_error_ceiling` (safety): every enabled auto-post rule version of a learned or probabilistic matching path has evidence of N proposals, N ≥ 3 ÷ rate, at least (1 − rate) posted unchanged, for the `auto_post.max_error_rate` in force at enabling, and that rate is at most 2%.
- **INV-705** `bank_charge_auto_post_gated` (cash): every document posted by `system` from a `bank_charge` rule has a debit line with a code listed for its money account, no counterparty account, no open item matched, one matching rule, and an amount at most the rule's `amount_max`, itself at most the company ceiling on the posting date.
- **INV-706** `llm_originated_rules_gated` (safety): no document posted by `system` has match basis `llm_suggestion`, and none comes from a rule version of origin `llm_proposed` unless `cash.auto_post.accept_llm_originated_rules` was true on that date and rule 8's conditions held.
- **INV-707** `wrong_auto_post_suspends` (safety): every reversal of a `system` posting, and every confirmation recording one wrong, marked its rule version's evidence outdated in the same transaction.
- **INV-708** `personal_values_permitted` (safety): every model call that carried a `personal` value had an active, unsuspended permission covering its data class, seat class, provider and region, carried no field listed in `data_processing.never_send_fields`, and was logged before it was sent.
- **INV-709** `data_processing_terms_current` (safety): every active, unsuspended permission's provider terms reference, region and retention equal the provider registry's, and no permitted endpoint trains on customer data.
- **INV-710** `tainted_projection_columns` (safety): every response a tainted run received from a declared projection held only the projection's columns, at most 20 rows, and within the run's call cap.
- **INV-711** `wake_up_mode_respected` (platform): no `agent_wake_up` start happened for a kind whose company mode was `by_rule` or `off` on that business date.
- **INV-712** `automation_flood_guard` (platform): no rule has more live executions other than `rate_limited` in a clock hour than its hourly limit in force, and no `rate_limited` execution ran an action or counted toward the breaker.
- **INV-713** `extension_points_bounded` (platform): every extension point's ceilings are within the core maxima, its decision kind is not an approval, posting, rights or settings decision, and no extension ran while `extensions.wasm_enabled` was false.
- **INV-714** `product_codes_stable` (master_data): product codes are unique per company, never reused after deletion, and unchanged once any document refers to them.
- **INV-715** `purchase_return_option_stamped` (inventory): every purchase return movement records the value source, costing role and landed-cost choice in force on its posting date, and those options change only at period starts.
- **INV-716** `narrative_mode_bounded` (platform): no analysis answer was rendered in a narrative mode looser than the installation maximum or the company's value on that date, and none as `free_prose` in Phase 1.
- **INV-717** `barcode_policy_stamped` (master_data): every parse result records the day 00, unknown-AI and separator values it used, and no lot's expiry date was filled from (15) while `barcode.gs1.best_before_fills_expiry` read false for its category.
- **INV-718** `duplicate_review_holds_payment` (safety): every purchase invoice ran the exact duplicate key on its channel, and every posted one suspected at level 3 under outcome `review` had its open item blocked for payment until the review was resolved.

**Edge cases** (block EC-180 to EC-199; EC-180 to EC-193 taken):

- **EC-180** `setting_tighten_then_loosen`: a controller lowers `cash.bank_charge.auto_post_ceiling` at once; raising it again directly returns `proposal_required`; a proposal approved by a second person takes effect and marks the dependent auto-post rule's evidence outdated.
- **EC-181** `setting_out_of_bounds`: `automation.breaker_failures` 0 and `automation.breaker_consecutive` below the failures setting are refused with `setting_out_of_bounds`; a self-approved loosening is refused with `approver_is_submitter`.
- **EC-182** `bank_charge_auto_post`: monthly fee lines with the configured code reach six over three months, a rule's auto-post is enabled, the next fee posts by `system`; a fee above `amount_max` gets `human_post`; a fee line that also matches an open item is not auto-posted.
- **EC-183** `llm_originated_rule_opt_in`: with the setting false, a confirm-mode match of an LLM-proposed rule gets `human_post`; a proposal to enable it is refused with `setting_out_of_bounds` while its bound is false, and the match stays `human_post`; an `llm_suggestion` draft never posts by `system`.
- **EC-184** `wrong_auto_post_suspends`: a person reverses a document posted by `system`; the rule version's evidence is marked outdated, `auto_post_suspended` is raised, and the next match gets `human_post`.
- **EC-185** `wake_up_by_rule`: the quotation agent's `inbound_message_matched` is set to `by_rule` with a rule on one mailbox; a matched message to that mailbox starts the agent, one to another mailbox stays with people.
  Note ([ADR-0078](0078-agent-simplification-for-phase-1.md), proposed 2026-11-21): the quotation agent is a Phase 2 agent type; in Phase 1 EC-185 is re-hosted on the `purchase_invoice` agent's `supplier_invoice_received`, set to `by_rule` with a rule on one supplier, and the catalog row says so (ADR-0078 rule 9a).
- **EC-186** `personal_values_without_permission`: with the switch off and no permission, a drafting step receives placeholders and a step that needs the value ends `routing_blocked`; the upgrade raised `setting_review_required`.
- **EC-187** `provider_terms_change`: the provider registry changes an endpoint's terms reference; the permission is suspended, vision runs end `routing_blocked`, and `data_processing_permission_suspended` is raised.
- **EC-188** `tainted_projection_read`: a tainted purchase invoice run lists item candidates through the projection (at most 20 rows, no prices); its eleventh call returns `tainted_projection_cap_reached`; with `agents.tainted_reference_reads` set to `literal` the call returns `tainted_read_out_of_scope`.
- **EC-189** `automation_flood_guard`: a mass import fires a rule 600 times in one hour; 500 executions act, 100 are `rate_limited`, one `automation_rule_rate_limited` item is raised, and the breaker does not trip.
- **EC-190** `purchase_return_option_from_period_start`: a company switches the purchase return option mid-period and is refused with `setting_effective_date_invalid`; from the next period start it succeeds, and a return in that period is valued at the preliminary price with the difference to the price difference key.
- **EC-191** `day00_reject_category`: a category set to `reject` refuses a (17) with day 00 as `gs1_invalid` (`date`), while another category reads it as the month's last day.
- **EC-192** `near_duplicate_payment_held`: a second invoice of the same seller, one minor unit apart and three days later, posts with its open item blocked for payment and a `duplicate_document_review`; resolving it as not a duplicate releases the block.
- **EC-193** `product_code_manual_category`: a category with manual codes refuses a duplicate code with `product_code_taken`, and once a sales order refers to its item a code change returns `product_code_immutable`.
