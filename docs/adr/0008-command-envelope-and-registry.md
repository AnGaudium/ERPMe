# ADR-0008: Command envelope and registry

Status: accepted (2026-11-14) under ADR-0005, reviewed by Claude Fable 5.2. [ADR-0013](0013-outbox-and-events.md) rule 9: internal calls from consumers and system jobs run in execute mode inside the caller's transaction without `expected_plan_hash` (an exception to rule 13). [ADR-0017](0017-permission-envelope.md) rule 4: the registry also declares capabilities, permissions that are not command names. Design item: DS-04. Related decisions: D2, D4, D13, D14. Principles 1, 2, 3, 4, 9, 10, 12, 13. Build principles B3, B7. ADR-0004, ADR-0005, ADR-0006, ADR-0007. Rule 4 annotated by [ADR-0022](0022-repository-and-engineering-conventions.md) (posting interfaces).

## Decision

Every write goes through one command registry. A command is a pydantic payload wrapped in one envelope (`command_type`, `schema_version`, `company_id`, `idempotency_key`, `mode`, `expected_plan_hash`, `payload`). The actor, and for agents, integrations and system jobs the accountable human (`on_behalf_of`), come from the credential, never from the envelope. The same envelope is sent twice: first with `mode: simulate`, which runs the real handler in a transaction that is rolled back and returns the plan and its `plan_hash`; then with `mode: execute` and the `expected_plan_hash`, which runs it again and commits only if the hash is equal. An execution claims its idempotency key first and stores its response in the same transaction; a retry returns the stored response. Command batches use the same envelope around an ordered list of items. Queries use the envelope without the write fields. Handlers are deterministic and touch only the database. Errors have one shape on every transport. REST and MCP are generated from the registry. The field-level specification is [DS-04-command-envelope.md](../design/DS-04-command-envelope.md).

### Rules

**Registry**

1. Each command type is registered once with: `command_type` (ADR-0004 rule 17), `schema_version` (semver), scope (`company` or `installation`), payload model, result model, handler, the error codes it can return, the permission it needs (DS-15) and `human_only`. Queries (`Get<Noun>`, `List<Noun>`, ADR-0004 rule 21) are registered the same way, with a result model and no handler effects, idempotency key or plan. Each command type also declares `effect_class` (`posting`, `master_data_change`, `outbound_send`, `other`), required with no default; CI fails when a `Post<Type>` or `Reverse<Type>` command is not `posting` ([ADR-0027](0027-cross-cutting-ownership.md) rule 17). Commands may also be registered `is_proposal_bound`: agents reach them only through change proposals ([ADR-0029](0029-proposals-and-agent-safety.md) rules 2, 4). A command whose policy inputs are read under locks is registered `is_policy_in_handler` ([ADR-0030](0030-commercial-seams-and-imports.md) rule 7). Each command also declares its `subject_table` and `allowed_states`, read by `invalid_state_transition` and `ListAllowedCommand`, and each check code `is_hashed` ([ADR-0040](0040-ui-architecture.md) rules 8, 10). Work item kinds are registered the same way ([ADR-0042](0042-work-queue.md) rule 1), and commands may be registered `is_consequence_posting` ([ADR-0043](0043-policy-and-approval.md) rule 5).

   Commands may be registered `is_draft_only`: the only commands a tainted agent run may run ([ADR-0050](0050-agent-runtime-and-query-layer.md) rule 26).

   Note: each command, query and capability also declares its authorization leaf, and a command may declare a minimum level above its verb's; a query that totals over documents without returning them declares `is_owner_scoped: false` ([ADR-0054](0054-users-roles-and-authorizations.md) rules 7, 8, 15).

   Note: commands may be registered `is_internal_only`: only a consumer or system job runs them, in process (rule 13). They get no REST endpoint, MCP tool or tool definition (rule 6), a request or batch item that names one over a transport returns `unknown_command_type`, and the level expansion skips them, so no role holds them at any level; the job holds them by registration ([ADR-0017](0017-permission-envelope.md) rule 13; [ADR-0054](0054-users-roles-and-authorizations.md) rule 8 note; [DS-04](../design/DS-04-command-envelope.md)).

   Note ([ADR-0058](0058-configurable-workflows.md), proposed 2026-11-15): commands may be registered `is_automation_allowed`: the `Create<Type>` commands of drafts an automation rule may create. Each is also `is_draft_only`, and never `posting`, `master_data_change`, `outbound_send`, `human_only`, `is_proposal_bound`, `CreateChangeProposal`, or a `Submit`, `Post`, `Issue`, `Approve`, `Reject` or `Reverse` (a CI check). Every command, consumer and scheduled job declares the event types it may emit, with discriminator values where the type has a discriminator; a declaration without values counts as every value. Event types may be registered `is_automation_trigger`, with a condition source query, typed condition fields taken only from the fields registered `is_gate_field`, an optional discriminator, watchable fields for update events and `is_replayable`. Commands may be registered `is_hold`, and modules may declare decision points with input and output schemas and a code default for no match (rules 4–6, 18).

   Note ([ADR-0059](0059-ai-tuning-and-development-of-deterministic-functions.md), proposed 2026-11-15): a deterministic function may declare tunable parameters: function code and version, authorization leaf, case tables, each parameter's type, default, bounds, `is_nullable` and `is_safety_cap`, order constraints between parameters, its stages and thresholds with small-company minimums, and its golden set. Fields may be registered `is_gate_field`, an allowlist of deterministic fields; CI refuses it on any field with LLM lineage. Tables that backtests read declare their as-of date column. The function and each L2 kind declare their case tables and case-reference columns, and queries may be registered held-out filtered; a drafting agent type's tool list holds only such queries (a CI check) (rules 3, 15, 16, 18, 20).
2. `human_only` marks actions the spec says agents may not take (closing periods, reversing posted documents; [14-agent-workflows.md](../spec/14-agent-workflows.md)). The dispatcher refuses to execute such a command when the actor is an agent; agents may simulate it to prepare a human's decision. Whether integrations may execute `human_only` commands is an open question for the author; until answered they are refused too. System jobs act as the spec defines (e.g. closing entries by actor `system` on behalf of the human who triggered the close, [07](../spec/07-shared-foundation.md#document-lifecycle-numbering-and-posting-periods)).

   Note: "agents may simulate it" is struck. Every agent actor runs under a fixed tool list, which never holds a `human_only` command ([ADR-0050](0050-agent-runtime-and-query-layer.md) rules 29–30), and the tool list is checked before `human_only`, so an agent run gets `tool_not_allowed` in both modes ([DS-04](../design/DS-04-command-envelope.md#dispatcher-check-order)).
3. Payload and result models are pydantic models with unknown fields rejected (`extra="forbid"`), using the `nativeflows.numeric` and `nativeflows.clock` types (ADR-0006 rule 13, ADR-0007 rule 3) and references by `id` only (ADR-0006 rule 5).

   Note ([ADR-0061](0061-barcodes.md), proposed 2026-11-15): a scan command carries each scanned field as a `scan` object (`raw` up to 512 characters, `symbology_identifier`, `source`: `wedge`, `camera` or `manual`, `decoder` for camera scans, `confirmed_as_read`) next to the field it fills. The handler parses and resolves `raw` again with the business date and the step's context and never trusts the client's own parse; `raw` and the free-text GS1 elements are untrusted text (rule 16).
4. A handler is a function `handle(context, payload) -> result`. It reads and writes only through the database connection, ID generator, clock and lock helpers in `context`. It makes no network call, reads no file, calls no LLM and starts no job directly; anything outside the database happens after commit through the outbox (DS-13). So a handler gives the same result for the same database state, payload and business date (D2, Principle 13). Queries it runs whose order affects the plan use `ORDER BY` on stable keys. Posting interfaces of other modules (e.g. `ledger.contract.write_journal_entry`) take this `context` and run inside the handler's transaction and plan, with no permission or idempotency step of their own ([ADR-0022](0022-repository-and-engineering-conventions.md) rule 4).
5. For every command and every query, before anything else runs (including an idempotent replay), the dispatcher checks permissions, record visibility and `human_only` (DS-15). Before a handler that posts runs, it also asks the policy engine (DS-28; until then a stub that allows). Handlers never do these checks themselves. A record the actor may not see is reported as `record_not_found`. The sentence "Before a handler that posts runs, it also asks the policy engine" is replaced by the policy points of [ADR-0029](0029-proposals-and-agent-safety.md) rule 6; allowed-target commands from agents are rejected with `proposal_required` (rule 4).

   Note: the checks run in one order ([DS-04](../design/DS-04-command-envelope.md#dispatcher-check-order)): (1) credential and actor context; (2) run gates that need no subject state: `tool_not_allowed`, then `tainted_run_not_allowed`, then the tainted reference scope; (3) `human_only` and `proposal_required`, by actor kind and origin agent run; (4) permission, with the `direct_master_data_change` deny; (5) record visibility: company, record scope, owner scope; (6) the idempotency replay lookup, which returns a stored response with no further check, otherwise the insert of rule 16; (7) the work item claim, skipped for shadow runs and at the same position in simulate mode; (8) state-dependent authorization ([ADR-0017](0017-permission-envelope.md) rule 16, [ADR-0054](0054-users-roles-and-authorizations.md) rule 19, [ADR-0055](0055-approval-pools-and-stages.md) rule 7); (9) the policy point and floors, inside the handler for `is_policy_in_handler`; (10) handler, audit and events. "Before anything else runs (including an idempotent replay)" covers steps 1 to 5; a replay skips steps 7 to 10.

   Note ([ADR-0058](0058-configurable-workflows.md), proposed 2026-11-15): before these checks the dispatcher assigns the causation chain and depth, from the caller and never from the request, and it refuses an automation action above depth 3, one that is not automation-allowed, and an agent start on an agent's chain ([DS-04](../design/DS-04-command-envelope.md#dispatcher-check-order), steps 1–2; rule 12).
6. REST endpoints, MCP tools, JSON Schema and TypeScript types are generated from the registry (Principle 10). Nothing is hand-written per command. MCP tool names are the `snake_case` form of the command type or query (ADR-0004 rule 19). Which tools each agent type sees is a fixed list (DS-32, [03-agent-safety.md](../spec/03-agent-safety.md) rule 2). One exception: the attachment upload endpoint, which streams bytes and then dispatches `CreateAttachment` ([ADR-0038](0038-audit-and-observability.md) rule 13). Transport endpoints for sessions and the live stream are the other hand-written exceptions ([ADR-0040](0040-ui-architecture.md) rule 12).

   Tool lists are fixed per agent type version, and their definitions are generated from the registry like the MCP tools; LLM steps get queries only, and commands are run by workflow code after simulation ([ADR-0050](0050-agent-runtime-and-query-layer.md) rules 29–32).

**Envelope and actor**

7. The command envelope fields are `command_type`, `schema_version` (the major version the client was built for, an integer), `company_id` (required for company-scoped commands, absent for installation-scoped ones), `idempotency_key`, `mode` (`simulate` or `execute`), `expected_plan_hash` (required when `mode` is `execute`) and `payload`. No other field is accepted. Also accepted: `include_canonical_plan`, which, like `mode`, is not part of the request hash ([ADR-0040](0040-ui-architecture.md) rule 9).

   Note (Design hardening, 2026-11-16): the envelope also accepts `as_of_date` (optional, a `BusinessDate`): the business date that every `clock.today(company)` read of the run returns ([ADR-0007](0007-time-model.md) rule 15 note). It is part of the request hash (rule 15). Every command response returns `as_of_date`, the date the run used. A client that executes after reviewing a simulation sends the simulation's `as_of_date` with `expected_plan_hash`, so rule 14's "changes only `mode`" reads "changes `mode` and adds `expected_plan_hash` and `as_of_date`". In a batch it covers every item. Field-level: [DS-04](../design/DS-04-command-envelope.md).
8. The dispatcher builds the actor context from the authenticated credential: actor kind (human, agent, integration, system) and `id`; for agents, integrations and system jobs, `on_behalf_of` (the accountable human bound to the credential, agent run or job when it was started); for agents, also `agent_run_id` ([03-agent-safety.md](../spec/03-agent-safety.md) rules 3, 7). None of these can be sent by a client, so text an agent has read cannot change whom it acts for. Whether that actor may act for that human is checked by DS-15. It also derives an agent run's work item from the run, never from the request, and checks its claim ([ADR-0042](0042-work-queue.md) rule 11).

**Simulation and `plan_hash`**

9. `mode: simulate` runs the same dispatcher and handler as `execute` in a transaction that is always rolled back (Principle 2; [10-roadmap.md](../spec/10-roadmap.md#lean-scope-for-phases-0-and-1), "built thin"). There is no separate simulation code in handlers. In both modes, `SET CONSTRAINTS ALL IMMEDIATE` runs before the plan is hashed, so deferred constraints fail in simulation as they would at commit. Handler and trigger paths use no sequence, no session-level advisory lock and no non-`LOCAL` `SET`, because these survive a rollback. A denial record is the one effect of a simulation that persists ([ADR-0038](0038-audit-and-observability.md) rule 5).
10. Simulation takes no lock on serialized rows (stock balance per item and warehouse, numbering counters) and consumes no document number. These tables are read and written only through the lock helpers in `context`; no other SQL, trigger or constraint reads them (CI check, DS-18). In simulate mode the helpers take no row lock and keep new values in memory for the rest of the run, and numbering returns a placeholder number unique within the run. Other writes still take ordinary row and unique-index locks until the rollback, so a simulation can briefly delay a real execution that touches the same document; it never holds stock or numbering locks. `open_item` is such a table ([ADR-0026](0026-open-item-core.md) rule 3).
11. Both modes run with `transaction_timeout` and `lock_timeout` (values in DS-18); exceeding them returns a retryable error.
12. The plan of a command is its journal lines and stock movements, in the order the handler produced them, plus its result; a command with no journal or stock effect has a plan of its result only. `plan_hash` is the lowercase hexadecimal SHA-256 of the canonical JSON of the plan: keys sorted, no whitespace, UTF-8, numbers and dates in their canonical string forms (ADR-0006 rule 13, ADR-0007 rule 3). Before hashing: every ID created through `context.new_id(table)` during the run (the only way a handler creates IDs) is replaced by a token `new:<table>:<n>` in creation order; values of the types `DocumentNumber` and `SystemInstant` (system-set `_at` fields) are removed. Rows that appear in a plan never get their `id` from a trigger or column default (ADR-0006 rule 2 allows those only for rows outside plans); a test checks this. IDs of rows that existed before the run, client-supplied IDs and client-supplied instants stay (ADR-0007 rule 11). The hash is computed over the full plan; the plan returned to the client is filtered by the actor's field permissions (DS-15). Warehouse task proposals (target and source bins) are listed like events and never hashed ([ADR-0023](0023-warehouse-management.md) rule 11). Planning run results (hashes, planned orders, messages, exceptions) are listed the same way ([ADR-0024](0024-planning.md) rule 17). The plan also contains the canonical content of the document versions and records the command writes ([ADR-0031](0031-design-simplifications.md) rule 1). The canonical plan also has a key `checks`, the sorted `[code, field]` pairs of check results whose code is hashed; `include_canonical_plan` returns the canonical plan to the client ([ADR-0040](0040-ui-architecture.md) rules 9, 10).

    Note (Design hardening, 2026-11-16): the canonical plan also has a key `as_of_date`, the business date the run used. A simulation and an execution pinned to its date hash equally across midnight, and an execution without the pin on another business date returns `plan_hash_mismatch` with the new plan ([DS-04](../design/DS-04-command-envelope.md), Canonical plan for hashing).
13. `mode: execute` requires `expected_plan_hash`, except for internal callers (consumers and system jobs calling the dispatcher in process, never over REST or MCP), which execute inside their own transaction under the same checks ([ADR-0013](0013-outbox-and-events.md) rule 9). The command runs again; if its `plan_hash` differs, the transaction is rolled back and `plan_hash_mismatch` returns the new plan and hash, so the client can review and resend. A human using the UI and an agent follow the same two calls.

    Note (Design hardening, 2026-11-16): who executes without a simulation: only internal callers, that is consumers and system jobs calling the dispatcher in process ([ADR-0013](0013-outbox-and-events.md) rule 9), the change-proposal executor among them with its stored plan hash. Every other actor (people through the UI, agents, integrations and MCP clients) simulates first and executes with `expected_plan_hash` (Principle 2). An `as_of_date` more than one day from the business date returns `as_of_date_out_of_range`; the dispatcher checks it after step 6 of the check order, so a replay of a committed execution still returns its stored response.

**Idempotency**

14. `idempotency_key` is required in both modes; a client builds one envelope and changes only `mode`. It is a string of 1–128 characters from `A-Z a-z 0-9 _ - . :`; a UUID version 7 is recommended. Its scope is (actor, command type), and `command_batch` for batches (Principle 9).
15. The request hash is the SHA-256 of the canonical JSON of the validated request (envelope without `mode` and `expected_plan_hash`, plus the validated payload), so `"1.50"` and `"1.5"` give the same hash.
16. An execution's first statement, after the checks of rule 5, is `INSERT … ON CONFLICT DO NOTHING` of (actor, scope, key, request hash) into `idempotency_record`, which has a unique constraint on (actor, scope, key). If the row is inserted, the command runs and the response is written into that row before commit; if the command fails, the whole transaction, row included, rolls back, so a retry runs again. If a concurrent request holds the key, the insert waits (bounded by `lock_timeout`). If a committed row exists: same request hash → the stored response is returned; different hash → `idempotency_key_reused`. `idempotency_record` also carries `company_id` (null for installation scope), compared null-safely by INV-89 ([ADR-0038](0038-audit-and-observability.md) rule 8).
17. A simulation never writes `idempotency_record`. If the key already has a committed row with the same request hash, a simulation returns that stored response instead of running.
18. A replayed response is the stored response with `replayed: true`; everything else, including `mode: execute`, is as stored. The DS-16 invariant compares responses ignoring `replayed`.
19. `idempotency_record` is not partitioned. A daily job deletes rows older than the retention (`retention_days` in installation settings, default 90); rows are kept at least that long. These rows are not the audit log, which is never deleted (DS-36). Every executed command's record has an audit record (INV-89, [ADR-0038](0038-audit-and-observability.md) rule 8).

**Command batches**

20. A command batch has the envelope with `command_type` and `schema_version` replaced by `items`, an ordered list of `{command_type, schema_version, payload}`, all for the same company and actor. Its REST endpoint is `POST /api/command-batches` and its MCP tool is `command_batch`. All items are validated first and every validation error is reported (field paths `items[<n>].payload.<field>`); then the items run in order in one transaction, all or nothing, stopping at the first handler error, which names its item. Its plan is the list of item plans, hashed as one; one `expected_plan_hash` and one idempotency key cover the batch. An item refers to a record created by an earlier item through the client-supplied `id` (ADR-0006 rule 3). A batch is not a command type, so no verb is needed.
21. A batch response returns, per item, its index, command type, result, number of journal lines, number of stock movements and the sum of its debit amounts in company currency (debit as DS-06 defines it), plus the batch `plan_hash`; the full plan is returned only when the request sets `include_plan: true`. The idempotency record stores the same summary, and a batch `plan_hash_mismatch` carries the same summary in `details` unless `include_plan` is true. The maximum number of items is an installation setting, default 1,000. Each item also carries `audit_record_id`, null in simulate mode ([ADR-0038](0038-audit-and-observability.md) rule 1). Command responses and batch items also carry `checks` (code, message, rule, field, details), stored with the response and summary ([ADR-0040](0040-ui-architecture.md) rule 10).

**Queries**

22. A query is sent as `POST /api/queries/<snake_case query>` (or its MCP tool) with `schema_version`, `company_id` and `payload` (the filters); it has no `idempotency_key`, `mode` or `expected_plan_hash`. Filters travel in the body, never in the URL, so personal data does not reach access logs. `List<Noun>` returns at most `limit` rows (default 100, maximum 1,000), ordered by `id` unless the query defines another stable order, with a cursor for the next page. Queries read the same database as commands, so a committed execution is visible to the next query.

**Schema versioning**

23. Each command type's and query's schema has a semver version. A change that only adds optional fields or new error codes is a minor version. Any other change is a new major version. `schema_version` names the major version; the registry serves the current major and the previous one until the next LTS release (DS-37), then removes the old one. A request for a major version that is not served is rejected with `schema_version_unsupported`, naming the versions served.

**Errors**

24. Every error, on every transport, is a response `{"errors": [ … ]}` where each item has `code` (a stable `snake_case` identifier from the registry's error catalog), `message` (English; the UI translates by `code`), `rule` (the reference that failed, e.g. `ADR-0007 rule 22`), `field` (path in the request, or null), `fix` (what the client should do), `retryable` (true or false, fixed per code in the catalog) and `details` (an object, may be empty, filtered by field permissions). Validation reports every field error it finds at once.
25. Each error code belongs to one category with a fixed HTTP status: `malformed` 400, `unauthenticated` 401, `permission` 403, `not_found` 404, `conflict` 409, `too_large` 413, `validation` 422, `precondition` 422 (a business rule failed), `rate_limited` 429, `internal` 500, `unavailable` 503. Over MCP the same body is returned as a tool error. An `internal` error never exposes stack traces or SQL. Rate limits themselves are set by DS-18 and DS-32.

    Agent budgets are set per run, per company and agent type per day, per company and per installation, and are reserved before each LLM call ([ADR-0050](0050-agent-runtime-and-query-layer.md) rules 22–24); the rate limits of ADR-0022 rule 9 still apply.

## Context

DS-04 is the contract every module, client and agent uses ([04-architecture.md](../spec/04-architecture.md); Principles 1, 2, 9, 10). Constraints:

- Commands are pydantic schemas, the single source for JSON Schema, REST, MCP and TypeScript types (ADR-0001, ADR-0002, [10-roadmap.md](../spec/10-roadmap.md)).
- Simulation runs the real command and rolls back; `plan_hash` hashes the resulting journal lines and stock movements; execute is rejected if the hash differs; simulation must not hold stock locks (Principle 2, 10-roadmap "built thin", backlog DS-04).
- Idempotency key per (actor, command type) with retention; the same key with a different payload is rejected (Principle 9). Imports are simulated command batches (D16, step 2). Imports above 1,000 rows are staged and posted as a sequence of batches ([ADR-0030](0030-commercial-seams-and-imports.md) rule 9).
- `actor` and `on_behalf_of` on every command; actor kinds human, agent, integration, system; untrusted content must not widen what an agent run can do ([03-agent-safety.md](../spec/03-agent-safety.md) rules 1, 3, 5).
- The command layer asks the policy engine before posting ([04-architecture.md](../spec/04-architecture.md)). Command schemas are a versioned public API ([07-shared-foundation.md](../spec/07-shared-foundation.md#extensibility-and-upgrades)).
- ADR-0005: among correct options, the one easiest for AI agents wins.

## Options considered

| Option | For | Against |
| --- | --- | --- |
| One envelope, sent twice with `mode` (chosen) | One request shape for both calls; agents change one field | Every write runs twice |
| `expected_plan_hash` optional | Faster for simple writes | Two behaviors; an agent could skip the review step Principle 2 requires |
| Separate simulation code per handler | Simulation could be cheaper | Two code paths that drift; the spec says run and roll back |
| Simulation takes row locks like execution | No special helpers | A simulation would block real stock postings, against Principle 2 |
| Actor or `on_behalf_of` sent in the envelope | Simpler credentials | A prompt-injected agent could pick another human to act for |
| Write the idempotency record at the end | One statement fewer | A concurrent duplicate runs the handler and fails instead of replaying |
| Partition `idempotency_record` by month | Drop old rows cheaply | PostgreSQL cannot enforce a unique key without the partition key in it |
| Store failed executions under the key too | Retries of failures are instant | A failure caused by state (a locked period) could never succeed on retry |
| Batch as a command type (`RunCommandBatch`) | Fits the verb list | A command containing commands; separate idempotency and plan rules anyway |
| Queries as `GET` with URL filters | Cacheable | No room for the envelope fields; personal data in access logs |
| One generic MCP tool `run_command` | Few tools | Agents get no schema per command; fixed tool lists per agent type become impossible |

## Constraints that come with the decision

- DS-05, DS-09: numbering and stock posting use the lock helpers in `context`; their tables are not read by other SQL (rule 10).
- DS-06: journal lines and stock movements expose their canonical form, with `DocumentNumber` and `SystemInstant` types (rule 12).
- DS-13: anything outside the database runs after commit from the outbox (rule 4).
- DS-15: permission and visibility checks for every command and query, field filtering of plans and error details, `human_only`, `on_behalf_of` binding in credentials and agent runs (rules 2, 5, 8, 12).
- DS-16: invariants for idempotent retry and simulated equals executed (rules 13, 18).
- DS-18: `transaction_timeout` and `lock_timeout` values; rate limits; CI checks for rules 4, 9, 10; generation of REST, MCP, JSON Schema and TypeScript from the registry.
- DS-28: the policy engine call before posting handlers (rule 5).
- DS-30: forms are generated from the same JSON Schemas.
- DS-32: agent runs bind `on_behalf_of` and `agent_run_id` (rule 8).
- DS-36: the audit log is separate from idempotency records (rule 19).

## Revisit when

- Running every write twice costs more than 30% of measured throughput on the medium replay: allow execute-only for command types with no journal or stock effect.
- A client needs a retry window longer than 90 days.
- More than 10% of executions fail with `plan_hash_mismatch` in normal use: look at what changes between the two calls.
