# ADR-0059: AI tuning and development of deterministic functions

Status: accepted (2026-11-15) under ADR-0005, reviewed by Claude Fable 5.2 (builder Claude Opus 5.5) after six review rounds. Design items: DS-34 (artifact evidence and promotion), DS-32 (the evaluation harness), DS-25 (the bank cascade's parameters). Related decisions: D2, D12, D16. Principles 2, 3, 6, 9, 11, 12, 13. ADR-0003, ADR-0005, ADR-0006, ADR-0008, ADR-0022, ADR-0029, ADR-0038, ADR-0043, ADR-0048, ADR-0049, ADR-0050, ADR-0051, ADR-0052, ADR-0053, ADR-0054, ADR-0055, [ADR-0058](0058-configurable-workflows.md); spec 03, 14, 16, 17.

## Decision

The capability check of 2026-11-15 found that AI can propose some rules (bank matching rules, item mappings, planning parameters) but has no general path to tune the constants of the deterministic core, no backtest for a proposed rule, and no lifecycle between a data row and a code change. This ADR adds that path, following the 2026-11-15 survey (recommendations A1 to A7, and X1 to X10 with X5).

**Three levels.** L1: parameter sets, versioned per company, for the thresholds, scores and windows of deterministic functions that declare tunable parameters with bounds. L2: rules as data: decision tables, matching rule sets, pricing and validation rules, report and analysis definitions, extraction mapping rules. L3: new code functions. AI may draft L1 and L2 artifacts. AI does not write L3 code for the running system in Phase 1: AI-written code is only ever proposed as a source change through the normal repository review, outside the running system.

**One lifecycle.** Every L1 and L2 artifact, whoever drafted it, moves draft → backtested → shadow → assisted → active, and can be retired. The version in force is a pointer, and rollback moves the pointer back. Each kind, and each tunable function, declares which of the middle stages it needs. The agent-type ladder of ADR-0050 is the same pattern.

**Evidence decides promotion.** A promotion names a frozen evidence bundle: a backtest on a later time window than the one the artifact was drafted from, with at least the declared number of cases, a comparison with the version in force, results on held-out golden cases the generator never saw, and a sample of changed decisions for a person to inspect. Every evaluation window used is recorded, and earlier use of the same window is shown. Thresholds belong to each tunable function, with small-company minimums; companies set them as settings, and the values are flagged for the author. A person submits, and another person who neither drafted nor submitted approves.

**Rules compute, models do not.** Matching runs deterministic rule passes, each marked confirm or suggest; ambiguity always suggests, and a tied match never acts. Every scorer has two calibrated thresholds, show and act, and acting is off by default. Gates read only fields the registry declares deterministic; an LLM's self-reported confidence is never a gate. Report and analysis definitions are declarative specs over the query and analysis layers, never SQL.

**Watched after promotion.** The override rate and outcome drift of every active artifact are measured daily; beyond a threshold the artifact is demoted to shadow automatically, with a work item, and an acting path re-arms only on evidence newer than the demotion.

**Kept as evidence.** Golden cases are labelled by people who hold the area's approve permission; labels are company data, and the core ships synthetic golden sets only. Decision and evaluation records follow the audit retention of ADR-0038; a regime may only lengthen it, as package configuration.

**Two accepted commands change.** `CreateReportDefinition` and `UpdateReportDefinition` (ADR-0049 rule 11) change from effect class `master_data_change`, reached by agents through change proposals, to draft-only commands that write a draft version, which a change proposal then raises (rule 11). Bank matching rules (ADR-0048 rule 9) change from proposal-bound rows to draft versions raised the same way (rule 10). Both are changes to accepted commands, made by notes, and are listed for the step log at acceptance.

### Rules

**Levels and modules**

1. Three levels (decision 11 of the author's decisions of 2026-11-15):
   - **L1, parameter sets** (rules 3–8).
   - **L2, rules as data** (rules 9–11): decision tables (ADR-0058 rules 18–20), matching rules, pricing and validation rules, report definitions (ADR-0049 rule 11), analysis definitions (artifact kind `analysis_definition`, a declarative spec over the analysis layer that its own ADR designs), and extraction mapping rules (artifact kind `extraction_mapping`, for the intake design).
   - **L3, code** (rule 24).
   - **Who drafts.** People; deterministic proposal consumers (such as ADR-0051 rule 19's); and agent runs whose agent type version declares the draft commands (`Create<Kind>Version`, `is_draft_only`) on its tool list, called drafting agent types here. The first agent type that drafts parameter sets is designed by its own ADR, as ADR-0051 rule 29 does for later agents.
   - **The model chooses, code computes.** Candidate values, tolerances and rule rows are computed by code (a grid search over the declared bounds and order constraints, a token count, a replay) on the drafting window without the held-out cases (rule 16); an LLM step only chooses among code's candidates and writes the explanation (ADR-0051 rule 1; Principle 13). Its explanation passes the number check of ADR-0050 rule 36.
   - **Outside the lifecycle,** for now: item mappings (`partner_item`), planning parameters and lead times (ADR-0024 rule 23), putaway rules and count plans (ADR-0023 rule 21). Each changes one record through a change proposal carrying that case's evidence (ADR-0051 rules 21, 24), a person sees its effect on that record, and a wrong one is corrected per record; they join when their owners add versions. Partner matching (the duplicate search of ADR-0052 rule 17) is a setting unless a company opts in (rule 8), and item matching's fuzzy constants stay agent type version constants (rule 7).

   Note ([ADR-0078](0078-agent-simplification-for-phase-1.md), proposed 2026-11-19): in Phase 1 people draft parameter sets, decision tables and rule sets; AI drafting of L1 and L2 artifacts moves to Phase 2. The deterministic lifecycle stays, because the bank cascade uses it. The stored-resolution proposals of `bank_matching` and `purchase_invoice` (bank matching rules, item mappings) stay as change proposals (ADR-0078 rule 8).
2. Modules (ADR-0022 rule 2 note):
   - **`configuration`** (layer 2) owns `parameter_set`, `parameter_set_version`, `parameter_set_value`, `artifact_transition`, `artifact_promotion_evidence`, `artifact_shadow_outcome`, `golden_case_label` and `artifact_monitor_snapshot` (DDL in [DS-28-34-configuration-artifacts.sql](../design/DS-28-34-configuration-artifacts.sql)), the contract function `get_parameters`, and the pure lifecycle and parameter checks.
   - **`automation`** (layer 5, [ADR-0058](0058-configurable-workflows.md) rule 1) owns `CreateArtifactEvidence`, `RunArtifactMonitor` and the queries of rule 27 that read layer 3–4 data; the commands of `configuration` that need its checks call them through ADR-0058 rule 1's hook `artifact_checks`.
   - **Owning modules.** The module that owns a tunable function or an L2 kind registers, with its declaration, three pure functions in its contract: `backtest` (the function under two parameter sets, or two rule versions, over a window of its own resolved history, inputs as of decision time), `compare` (an outcome against a person's final result) and `monitor` (decisions and overrides over a window). `automation` calls them; for the bank cascade they live in `cash`, as `GetAutoPostShadowEvaluation` already does (ADR-0051 rule 18).
   - **The auto-post hook.** `policy`'s evidence hook of ADR-0043 rule 14 gains a second function, `auto_post_eligibility`, which `cash` registers and `app` wires: for a `system` posting of a cascade draft it answers whether the draft's line meets rule 6, and the policy floor gives `human_post` when it does not. So `policy` imports no layer-4 module.
   - **The outdated marker's writer.** `policy`'s contract gains `mark_auto_post_evidence_outdated(company, function_code, by_id)`, which sets `shadow_evidence_outdated_by` on every enabled rule version whose stored evidence names that function (`EnablePolicyRule` stores the function code with the hash). `configuration` declares the hook `artifact_in_force_changed`, which `policy` registers and `app` wires (ADR-0022 rule 2's pattern); `configuration` calls it inside the transaction of every pointer move, retirement and failed re-evaluation of a parameter set (`automation` reaches it through `configuration`'s contract), so no module imports `policy` sideways or up.
   - **No new table per kind** for lifecycle or evidence: one transition log, one evidence table and one shadow table serve every kind. A generic `artifact_promotion_evidence` is used rather than `agent_promotion_evidence`, whose columns (agent type, behavior hash, seat models) belong to agent types; the agent table stays as it is.

**L1: parameter sets**

3. Tunable parameter declarations (ADR-0008 rule 1 note). A deterministic function may declare in the registry:
   - its `function_code` (such as `cash.match_bank_line`), `function_version` (semver, bumped by any change of its code or declaration), its authorization leaf (for golden labels, rule 22), its case tables (the rows its decisions are about) and its case-reference paths (columns of other tables that point at a case directly, or through a declared path of foreign keys, such as a payment line through its payment to the bank statement line), both for held-out filtering (rule 16); a CI check derived from the schema refuses a foreign key to a declared case table that is not a declared case-reference column, and a property test checks that a filtered query returns no row tied to a held-out case; each L2 kind declares the same;
   - each parameter: `code`, type (`integer`, `decimal`, `score`, `percent`, `days`), core default, minimum and maximum, `is_nullable` (null means off), and `is_safety_cap`: a cap whose maximum is the core default, which is never off and can only be lowered;
   - **order constraints** between parameters (`a > b`), checked with the bounds (`parameter_order_violated`);
   - its **stages and thresholds** (rule 18), with the small-company minimums below which no company may set them;
   - its synthetic golden set (ADR-0050 rule 39), which every parameter set version must pass at the function's threshold.
   Not tunable: hard floors, guards and shapes (the reference-token shape of ADR-0048 rule 9, the routing switch, taint, the rule that a tied match never acts), and anything spec 03 fixes. Bounds and constraints are part of the declaration and change only by a release.
4. Parameter sets (company data):
   - **Shape.** One `parameter_set` per company and function, with `owner_user_id`, `current_version_id` and `shadow_version_id`. A `parameter_set_version` carries the lifecycle columns of rule 12 and `function_version`; its `parameter_set_value` rows copy each declared parameter's type, default and bounds at that function version, and the database refuses a value outside them (`parameter_out_of_bounds`), a safety cap above its default, or an empty safety cap.
   - **Hashes.** `parameters_hash` is the SHA-256 of the canonical JSON (ADR-0006 rule 13) of (function code, the values sorted by code); it does not include the function version, which every decision records beside it. A version's `content_hash` covers its values with their copied types, defaults and bounds, sorted by code, and its function version.
   - **Effective values.** `configuration.contract.get_parameters(company, function_code)` returns the current version's values, or the core defaults when there is none, with `parameters_hash`, the function version, the parameter set version and its state (`core_default`, `assisted`, `active`). Every decision the function makes records all four (in its own row, or its derivation trace), so each outcome names the parameters behind it and whether they could act.
   - **Only through the lifecycle.** Values change only by a new version that passes rules 12–19.
   - **A function release** (a new `function_version`) leaves the parameters hash, and so the auto-post binding of rule 6, unchanged. `RunArtifactMonitor` writes a re-evaluation for every company that uses the function: the parameters in force, a version or the core defaults, under the new function version over the window of their last evidence (for core defaults, the window of the auto-post rule's evidence, else the function's declared `reevaluation_window_days`, 60 for `cash.match_bank_line`, two statement months as ADR-0051 rule 18 counts), stored as evidence of stage `reevaluation`; for core defaults that row names the function code and the company and no version. It raises `artifact_function_changed`, one item per owner with the owner in its key, for the parameter set's owner (`company_owner` under core defaults) and for the owner of each auto-post rule that depends on it, with the re-evaluation as subject. The re-evaluation passes on the acting figure only: of the proposals at or above the auto-post rule's floor and below its maximum, at least ADR-0051 rule 18's 99% equal people's final results, and none was drafted to another partner. A pass leaves auto-post as it is; a failure marks the dependent rule's evidence outdated (rule 6). The function declares `reevaluation_min_cases` (50 for `cash.match_bank_line`), counted on acting proposals only; with fewer the result is `too_few_cases` and the evidence is left unmarked. The monitor then widens the window in one step to the smallest window that holds `reevaluation_min_cases` acting proposals, capped at the function's declared `reevaluation_max_window_days` (180 for the cascade), and judges on it, so a small company's release is still judged; while the cap holds too few it repeats the attempt daily until a verdict is possible or newer evidence replaces it. If the maximum window still holds too few acting proposals, the evidence stays unmarked and the owner's `artifact_function_changed` item records that the release could not be judged and stays open for a person. A changed core default changes the core defaults' hash, which ADR-0058 rule 25's upgrade check reports.

   Note ([ADR-0063](0063-configurable-policy-settings.md), proposed 2026-11-15): a small company's evidence window may reach `artifacts.<function_or_kind>.max_window_days` (default 90, at most 365), never a lower bar (rule 10).
5. The bank cascade's parameters (ADR-0048 rule 9 note). `cash.match_bank_line` declares, with the current constants as defaults:

   | Parameter | Default | Bounds | Notes |
   | --- | --- | --- | --- |
   | `already_posted_window_days` | 5 | 0–10 | Step 1 |
   | `subset_search_size` | 6 | 1–8 | Step 4; the upper bound limits the search |
   | `score_already_posted` | 95 | 0–100 | |
   | `score_reference_exact` | 100 | 0–100 | |
   | `score_reference_partial` | 80 | 0–100 | |
   | `score_account_amount` | 90 | 0–100 | |
   | `score_account_amount_tied` | 60 | 0–60 | Safety cap; a tied match never acts whatever its score |
   | `score_account_subset` | 70 | 0–100 | |
   | `cap_company_rule` | 90 | 0–90 | Safety cap on a company rule's match in confirm mode (rule 10) |
   | `cap_counterparty_unverified_exact` | 85 | 0–85 | Safety cap |
   | `cap_counterparty_unverified_partial` | 65 | 0–65 | Safety cap |
   | `cap_paid_by_third_party` | 60 | 0–60 | Safety cap |
   | `show_min_score` | 0 | 0–100 | Below it the cascade drafts nothing and the line stays for a person |

   - **Order constraints:** `score_reference_exact` > `score_reference_partial` > `score_account_subset`, and `score_account_amount` > `score_account_subset`.
   - **Tied matches never act.** A step 3 match among several equal items is marked tied on its line and is never auto-posted, a hard rule of the cascade outside tuning.
   - **Act threshold.** The cascade's act threshold is the score floor of the company's auto-post policy rule (ADR-0043 rule 14), which stays where posting authority lives, and stays off by default.
6. Acting paths depend on the parameters (ADR-0043 rule 14 note; ADR-0051 rule 18 note):
   - **Recorded.** A cascade proposal records on its `bank_statement_line` the `match_parameters_hash`, the `match_function_version`, the `match_parameter_set_version_id` and the `match_parameter_state` in force, and `match_is_tied`. `GetAutoPostShadowEvaluation` counts only proposals made under one hash, which its result names.
   - **Bound.** The evidence that `EnablePolicyRule` stores names that hash and the parameter set's latest transition at that moment (null when it has none). Through the hook `auto_post_eligibility` (rule 2), a `system` posting of a cascade draft gets `human_post` unless its line carries the evidenced hash, was proposed while the state in force was `active` or `core_default` (so assisted never acts, which the line itself shows), and is not tied, and the rule version's evidence is not marked outdated. A function release does not switch it off by itself (rule 4).
   - **Outdated, without comparing times.** A demotion, a rollback or an invalidation of the parameter set, and a re-evaluation below the thresholds (rule 4), mark the stored evidence of every dependent auto-post rule version as outdated, in the same transaction, through the hook of rule 2: `policy_rule_version.shadow_evidence_outdated_by` names the transition or the re-evaluation. A new parameter set version taking force does the same; raising the version already in force from `assisted` to `active` does not, because the pointer does not move. `EnablePolicyRule` refuses evidence that is outdated, or whose recorded latest transition is not the parameter set's latest (`auto_post_evidence_outdated`); because stored evidence is set once, re-arming needs a new rule version with new evidence. So a demotion back to an earlier hash never re-arms auto-post on old evidence.

   Note ([ADR-0065](0065-deterministic-auto-post-gateway.md), 2026-11-16 (proposed)): the auto-post gateway's stored evidence names the checker version and the version of the decision table at its decision point; a change of the table version in force, its demotion or its rollback marks that evidence outdated through `artifact_in_force_changed`, in the same transaction, as for parameter sets ([ADR-0065](0065-deterministic-auto-post-gateway.md) rules 9, 14).
7. Agent constants (ADR-0051 rule 1 note): the fuzzy acceptance constants of `rank_candidates` (92 and 8) stay constants of the agent type version in Phase 1, changed by a new version with an evaluation. A later agent type version may instead declare them as a tunable parameter set; the current version's `parameters_hash` then enters its behavior hash, so a promoted parameter set makes the agent run as `shadow` until it is promoted again (ADR-0050 rule 14).
8. Other tunable functions: the partner duplicate search of ADR-0052 rule 17 stays the company setting `crm.duplicate_name_threshold`. When `crm` registers `backtest`, `compare` and `monitor` for `crm.find_partner_duplicates`, a company may opt in to tuning by creating its parameter set, seeded from the setting's value, after which the parameter set's value is used (ADR-0052 rule 17 note). Planning's forecast and exception parameters (ADR-0024) are candidates for their own declarations.

**L2: rules as data**

9. Kinds and ladders. Each L2 kind declares its stages, evidence function, comparator and thresholds:

   | Kind | Owner | Stages | Backtest evidence | Live comparison |
   | --- | --- | --- | --- | --- |
   | `parameter_set` | the function's module | as the function declares; for `cash.match_bank_line`: draft, backtested, shadow, assisted, active | The function under both sets on a later window; the golden sets | Shadow outcomes against people's final results |
   | `decision_table` | `configuration` | draft, backtested, active; shadow optional | Validation, tests and the replay diff ([ADR-0058](0058-configurable-workflows.md) rule 23) | Shadow outcomes against the current version's |
   | `automation_rule` | `configuration` | draft, backtested, active; shadow optional | The same | Would-be actions against the current version's |
   | `matching_rule` | `cash` (`bank_matching_rule`) | draft, backtested, assisted (suggest), active (confirm); shadow optional | Later lines carrying the token, against people's matches | Suggest-mode drafts posted unchanged |
   | `report_definition`, `analysis_definition` | `reporting`, the analysis layer | draft, backtested, active | A render of the draft version on a closed period, with at least one cell a person checked by hand | None |
   | `extraction_mapping` | the intake module | draft, backtested, shadow, active | Fields on a later window of documents against people's corrections | Shadow extractions against people's corrections |

   Every ladder needs `backtested`: a version leaves draft only to it. Pricing and validation rules that exist as company data (promotions, ADR-0047 rule 17; configuration rules, ADR-0046) adopt the lifecycle when their owners add the version columns; until then they keep their own versioning and change proposals.
10. Matching (the survey's A3; decision 14):
    - **Passes.** Bank, partner and item matching use deterministic rule passes, each marked `confirm` (its match may act when policy allows) or `suggest` (it drafts or proposes for a person, never acts). Ambiguity always suggests: a line that two passes or two rules would give to different partners, a line that also names another partner's reference, or a tied match is drafted without acting.
    - **Bank company rules** (ADR-0048 rule 9 note) become artifacts of kind `matching_rule`: each `bank_matching_rule` version carries the lifecycle columns and `match_mode`. A rule names the partner only; steps 3 and 4 still find and score the items, as today. In `assisted` the rule matches in suggest mode: it drafts with match basis `company_rule` and no score, so it is never auto-posted. In `active` it matches in confirm mode: steps 3–4 score the match, capped by `cap_company_rule`, and the counterparty caps of ADR-0048 rule 9's note apply, because a description token is as untrusted as a reference.
    - **Account rules.** A rule that maps a token to an account (a bank fee to the bank charges account, say) has no open items for steps 3–4. It drafts the document to that account. In confirm mode it scores `cap_company_rule`, under the counterparty caps (with no partner, the unverified cap), only when its token is a whole, reference-shaped token of the description (ADR-0048 rule 9's shape) and the amount's sign matches the account's natural side; otherwise it suggests without a score. Two or more matching rules on one line, whatever their targets, suggest. A draft under the unverified or third-party cap carries ADR-0048 rule 9's flag (`counterparty_unverified`, `paid_by_third_party`) and is never auto-posted, account rules included; so an account rule's draft with no partner owning the paying account is never auto-posted. Where a partner owns the counterparty account, account-rule drafts are auto-posted only when the auto-post rule's evidence of ADR-0051 rule 18 counts proposals of that basis (`company_rule_account`) among its 300; otherwise they get `human_post`. Whether bank fees should ever auto-post is an open question for the author. Their lifecycle is the same, and their evidence is later lines that people posted to that account.
    - **One carrier** (ADR-0051 rule 19 note): the consumer writes the rule as a `bank_matching_rule` version in `draft`, tainted, by the draft-only command `CreateBankMatchingRuleVersion`; no change proposal waits. A person holding `edit` on the leaf `bank_statement` may call it too, for a rule they write themselves (untainted); it is on no agent tool list. The rule's identity, with its owner, is created by `CreateBankMatchingRule` (effect class `master_data_change`) in the same batch. Its drafting window ends at the value date of the second qualifying line; evidence is sufficient once at least the declared minimum of later lines (default 1) carry the token and people matched every one of them to that partner (or posted them to that account). The only proposal is `SetArtifactVersionState`.
    - **AI proposes, people decide.** AI proposes rules and tolerances. The proposer, or the human its run acted for, is never the approver.
    - **For the author.** An approved rule whose token an LLM read can feed a scored match and so an auto-post; spec 03 rule 1 forbids auto-posting "a match an LLM contributed to". The path predates this ADR (ADR-0051 rule 19); it is an open question whether the human approval of the rule ends the LLM's contribution.

    Note ([ADR-0063](0063-configurable-policy-settings.md), proposed 2026-11-15): bank fees may auto-post through the account-rule class `bank_charge` (rule 9), and an LLM-proposed rule feeds auto-post only under `cash.auto_post.accept_llm_originated_rules` (rule 8).
11. Report and analysis definitions (A5; decision 16):
    - **Declarative.** Specs over the query layer (ADR-0050 rules 42–48), the statutory engine (ADR-0049) and the analysis layer; never SQL and never a number an LLM computed.
    - **Draft versions** (ADR-0049 rule 11 note): `CreateReportDefinition` and `UpdateReportDefinition` write a draft version (effect class `other`, `is_draft_only`); activation is `SetArtifactVersionState` through a change proposal.
    - **Evidence on the draft.** `CreateArtifactEvidence` renders the draft version on a fixed closed period and compares it with the cells the person checked by hand, given in the command as (line, column, period, value); at least one cell is required, and evidence is sufficient when every checked cell equals the engine's figure. The person who creates it attests the check.

**One lifecycle**

12. States (A1; decision 12):
    - **`draft`:** editable; validation and tests on demand. Versions are inserted only as drafts.
    - **`backtested`:** content frozen; valid, tests passing, backtest evidence sufficient.
    - **`shadow`:** computed beside the version in force on live cases; its outcomes are recorded in `artifact_shadow_outcome` (automation rules: `automation_execution` in mode `shadow`) and never shown or used.
    - **`assisted`:** in force where a person decides (drafts, proposals, suggestions), never where the system acts without a person (auto-post, confirm-mode matches, unattended actions).
    - **`active`:** in force everywhere, acting paths included, within policy and the hard floors.
    - **`retired`:** final; never in force again.
    - **Pointers.** `current_version_id` names the version in force (state `assisted` or `active`; null means the core defaults, or no artifact); `shadow_version_id` names at most one version in shadow. A version's state says the furthest it was promoted, so several versions may be `active`; the pointer says which is in force.
    - **Allowed moves**, held by triggers: from `draft` only to `backtested`; from there forward to a later state (skipping only stages the kind or function does not require, a command check); `assisted` or `active` back to `shadow` (demotion); any state except `draft` to `retired`; never back to `draft`, never out of `retired`. A version in force is demoted only after the pointer has moved off it. Leaving `shadow` clears the shadow pointer that names the version, and retiring clears both pointers that name it.
    - **Content hash.** As ADR-0058 rule 21 defines it per kind, and for parameter sets as rule 4 does.
    - **The agent-type ladder** of ADR-0050 rule 14 (off, shadow, assisted) is the same pattern for code artifacts (ADR-0050 rule 14 note).
13. Moves and who makes them:
    - **`CreateArtifactEvidence`** (`automation`, effect class `other`, a person's command, on no agent tool list): computes evidence once (rule 14). Stage `backtest` evidence that is sufficient moves a draft to `backtested`; stage `preview` records an attempt that is never sufficient; stage `live` covers a shadow or assisted period.
    - **`SetArtifactVersionState`** (`configuration`, effect class `master_data_change`, change-tracked, `is_proposal_bound`, declared minimum level `full`): raising a version to `shadow`, `assisted` or `active` runs only from an approved change proposal and names evidence (otherwise `proposal_required`, as for `UpdateAgentTypeSetting`); raising to `assisted` or `active` also moves `current_version_id`, and to `shadow` sets `shadow_version_id`. Lowering (demotion to `shadow`, retirement) is direct. Retiring the version in force clears the pointer in the same update (the trigger does it), writes a `retired` transition and, for a parameter set, marks the dependent auto-post evidence outdated (rule 6). Proposals for it expire after `artifacts.proposal_ttl_days` (company setting, default 30) instead of `change_proposal_ttl_days`.
    - **`SetArtifactCurrentVersion`** (`configuration`, effect class `other`, level `full`): rollback. It moves `current_version_id` to a version of the same artifact whose state is `active` or `assisted`, or to null (core defaults, or none), at once, without evidence, because the target was evidenced when promoted; it repeats the target's validity and, for automation rules, ADR-0058 rule 15's graph check, under the company's configuration lock. A version never promoted returns `artifact_version_not_eligible`, an invalid one `artifact_invalid`.
    - **Segregation.** The proposal's submitter vouches for the evidence. Its approver is neither the submitter (`approver_is_submitter`, also in the small-company mode) nor the version's drafter, nor the human its drafting run or consumer acted for (`segregation_of_duties`, ADR-0017 rule 16).
    - **Taint.** A version drafted by a tainted run, or derived from untrusted text such as a bank token, is written tainted (ADR-0029 rules 8, 10); a person submits it, and the approval is the trust boundary.
    - **Log.** Every move writes an immutable `artifact_transition` row: kind, artifact, version, move (`backtested`, `promoted`, `demoted`, `retired`, `rolled_back`, `disabled`, `enabled`, `invalidated`, `deprecation_found`), states, pointers before and after, evidence, proposal, actor and reason.

**Evidence**

14. The evidence bundle (A2; decision 13), `artifact_promotion_evidence`, immutable:
    - **Identity:** kind, artifact, version, stage (`backtest`, `preview`, `live`, `reevaluation`), and `content_hash` of the version. A re-evaluation of core defaults names the function code and the company instead of an artifact and version.
    - **What ran:** `engine_version` (the function version, or the registry version for rules and tables) and the baseline: the version in force at creation and its hash (the core defaults' hash, or the hash of nothing).
    - **Windows:** the version's drafting window and the evaluation window; `case_count` and the declared `min_case_count`; `data_window_hash`, the SHA-256 of the sorted IDs of the cases evaluated; `window_reuse_count`, the number of earlier evidence rows of any stage for the same artifact whose evaluation windows overlap this one, which the proposal shows.
    - **Golden cases and reads:** `golden_set_hash`, the held-out case count, the count of held-out cases found in the drafting run's reads (rule 16), and `drafting_reads_hash`, the SHA-256 of the drafting run's recorded read references, frozen so the check survives the steps' retention.
    - **Figures** against the baseline: for a scorer, precision of acted and of suggested decisions, coverage, abstentions (X5), decisions that change (count and money value), false acted decisions in money terms, and the precision and coverage curve at each candidate threshold; for rules and tables, the replay diff; the comparator's agreement for live evidence; the undated current-state reads, listed.
    - **The changed sample** (rule 17), the thresholds applied (rule 18), `is_sufficient`, `drafted_by_filtered_run` (rule 16), and who created it: a person, or for a re-evaluation the monitor job (`created_by_kind` `system`).
    - **Held by the database:** sufficient evidence has at least `min_case_count` (at least 1) cases, previews and re-evaluations are never sufficient, and a sample holds at most 20 decisions.
15. Time split, no look-ahead:
    - **Every draft has a drafting window.** A drafting run declares it, and every query it calls is bounded by it. A person's draft declares the data window they used, by default everything up to the draft's date. So no version is without one.
    - **Look-ahead in reads.** At evidence creation `automation` checks the drafting run's recorded read references (ADR-0050 rule 19) against each source's declared as-of column and refuses evidence when one is dated after the window (`drafting_window_violated`). Reads of evidence, shadow outcomes and monitor snapshots count by their evaluation window or business date. Undated current-state reads are listed in the bundle. When the drafting run's steps have been dropped (ADR-0050 rule 19's retention), evidence is refused (`drafting_run_steps_missing`).
    - **Out of sample.** A backtest's or preview's evaluation window starts strictly after the drafting window ends (`backtest_window_not_after_drafting`; the database holds it).
    - **Dated sources only.** A `backtest` may read only tables that the registry declares with an as-of date column (`backtest_source_undated` otherwise), and reconstructs each case's inputs as they were when the decision was made: open items as of the line's value date, partner bank accounts by their validity, documents at their version then. A case whose inputs cannot be reconstructed is left out and counted.
    - **Recorded attempts.** Every evaluation window is recorded, previews included (stage `preview`), and `window_reuse_count` shows the approver how often the same window was tried.
16. Held-out golden cases (the survey's P2.8):
    - **Assignment.** A case is held out when the first byte of the SHA-256 of the UTF-8 text `<company ID>:<case ID>` (both UUIDs in canonical lowercase hyphenated form) is below 51, about one case in five; the assignment is deterministic, so nobody chooses it, and the database checks a label's `is_held_out` against it.
    - **Kept from the generator.** For a run of a drafting agent type, the query layer excludes the held-out cases from every row query and aggregate the run calls, whether labelled or not: rows of the declared case tables, and rows of other tables whose declared case-reference columns point at a held-out case (the receipt proposed from a held-out line, its lines and settlements). An aggregate that cannot apply the filter is refused (`held_out_filter_unavailable`). Code that fits or searches candidates uses only cases that are not held out. `ListGoldenCaseLabel` is on no tool list.
    - **A closed tool list.** A registry CI check refuses a drafting agent type version whose tool list holds a query not registered as held-out filtered. Reads of evidence, shadow outcomes, monitor snapshots, automation executions and `GetAutoPostShadowEvaluation` are on no drafting tool list, because they hold per-case results of the later window.
    - **A person's draft.** The query layer does not filter a person's reads. Evidence records whether the version was drafted by a filtered run or by a person (`drafted_by_filtered_run`), so the approver knows what "held-out" means for it.
    - **Checked by ID sets** as the second line: at evidence creation `automation` intersects the held-out case IDs with every row reference the drafting run recorded (`context_refs`, `result_refs`, `request_refs`), each mapped to its case through the case-reference columns; a non-empty intersection makes the evidence insufficient (`held_out_case_seen`), and the database refuses sufficient evidence with a non-zero count.

    Note ([ADR-0065](0065-deterministic-auto-post-gateway.md), 2026-11-16 (proposed)): the `auto_post_advisor` agent type is a drafting agent type: its tools `ListAutoPostCase`, `EvaluateAutoPostBacktest` and `ListAutoPostThresholdCandidate` are held-out filtered, its decision table drafts follow this lifecycle, and its settings proposals carry the backtest as evidence ([ADR-0065](0065-deterministic-auto-post-gateway.md) rules 17, 18).
17. Baseline and changed sample: the figures compare the candidate with the version in force on the same cases. Up to 20 changed decisions are sampled for inspection, chosen by sorting the changed case IDs by SHA-256 of (evidence data window hash, case ID), so the same evidence always shows the same sample. The proposal shows the diff, not only totals (X4).
18. Thresholds per function (decision 13): each tunable function declares its stages and neutral thresholds, and each L2 kind its own; companies set them as settings `artifacts.<function code or kind>.<threshold>`, never below the declaration's small-company minimum. The small-company minimums never lower the evidence of ADR-0051 rule 18 for enabling auto-post (300 proposals over two statement months). The values are proposals, flagged for the author:

    | Function or kind | Backtest | Live (shadow or assisted) | Promote when | Demote when |

    | `cash.match_bank_line` | ≥ 200 cases over ≥ 28 days (small-company minimum 50) | ≥ 100 compared cases over ≥ 10 business days (minimum 30) | Suggested-decision precision not below the baseline's and ≥ 95%; coverage loss ≤ 5 points; held-out golden ≥ 95% over at least 20 held-out cases (minimum 10); acted precision ≥ 99% for an acting path | Over 30 days and ≥ 100 decisions (minimum 30): override rate ≥ the larger of twice the evidenced rate and the evidenced rate plus 5 points; or acted share moved by more than 10 points |

    Note ([ADR-0063](0063-configurable-policy-settings.md), proposed 2026-11-15): the case minimums and the evidence window are registered settings with bounds that never go below the small-company minimum, and acting paths follow `auto_post.max_error_rate` (rule 10); the precision targets, the held-out golden-case threshold, the demotion formula and the held-out share stay the declared values here (open question).

19. Stale evidence: executing a promotion re-reads no figures. It checks that the version's content hash, the engine version and the baseline (the version in force and its hash) still equal the evidence's; otherwise `artifact_evidence_stale`, and new evidence is needed. A function release does not demote a version already in force, because core CI tests the function on its golden sets and the re-evaluation and monitor of rules 4 and 21 watch it, but it makes every pending evidence for that function stale.

**Scorers and gates**

20. Two thresholds, and deterministic gates only (A4, X5; decision 15):
    - **Two thresholds per scorer:** show (a suggestion or draft is made) and act (the system may act without a person). Both are calibrated on the company's own outcomes: the evidence holds the precision and coverage curve, and a promotion picks thresholds that meet the function's precision. Act is null (off) by default. Below show, the case abstains to a person (X5).
    - **Gate fields are an allowlist.** Conditions, decision table inputs, scorer inputs and gates read only fields that the registry declares `is_gate_field`: deterministic fields. CI derives LLM lineage from the output schemas: a field that an LLM step's output fills, directly or through any computation, is never declared a gate field (a registry check). Values that agents draft into documents are covered by taint and by ADR-0029 rule 12, not by this list. An LLM's self-reported confidence is never a gate, and output schemas hold no confidence field (ADR-0050 rule 35).

**Monitoring**

21. Override rate and drift (A7; decision 17):
    - **Daily.** `RunArtifactMonitor` (system job of `automation`) asks the owning module's `monitor` function, for every artifact version in force, for the decisions it made in the trailing 30 days and the overrides: decisions a person changed, reversed or discarded (for the cascade, proposals not posted unchanged). It writes one immutable `artifact_monitor_snapshot` per version and day, with the evidenced rates as the baseline.
    - **Demotion.** Beyond the function's or kind's demotion threshold (rule 18), the job moves the pointer back to the version that was in force before (the promotion's `previous_current_version_id`) when it is still eligible and passes its validity check, otherwise to the core defaults or to none; demotes the version to `shadow` so it keeps being measured; writes the transition; and raises `artifact_demoted` for the artifact's owner with the figures, naming any auto-post rule whose evidence the demotion outdated (rule 6). Promotion back needs new evidence.
    - **Not for agent types.** ADR-0051 rule 5's quality monitor keeps only signalling, because demoting an agent type moves work to people, while demoting an artifact falls back to an evidenced version (ADR-0051 rule 5 note).

    Note ([ADR-0063](0063-configurable-policy-settings.md), proposed 2026-11-15): demotion is judged over at least 30 decisions; agent types follow `agents.<agent_type>.drift_action` (rules 10, 12).

### Worked examples

**L1: the bank cascade's thresholds, tuned, promoted and demoted.** A company imports about 2,400 bank lines a month. Its parameter set for `cash.match_bank_line` has no version, so the core defaults are in force (hash H0), and its auto-post rule (floor 90, maximum 20,000,000, owner the chief accountant) was enabled with evidence under H0.
- **Draft.** On 2026-08-04 a tuning run, under an agent type designed for it, analyses the resolved lines of 2026-05-01 to 2026-07-31 (its declared drafting window), without the held-out cases, which the query layer filters out. Code computes candidates by a grid over the bounds and order constraints; the LLM step picks one and explains it: of 217 proposals with the tied account-and-amount score (60), people changed 176 (81%). Version 1 sets `show_min_score` to 61, everything else at the defaults. The run writes it with `CreateParameterSetVersion` as a draft; it is untainted, because the run read no outside content.
- **Backtest.** On 2026-10-01 the chief accountant runs `CreateArtifactEvidence` for 2026-08-01 to 2026-09-30, after the drafting window; no earlier evidence used that window (`window_reuse_count` 0). Of 4,812 lines, the core defaults propose 3,753 (coverage 78.0%), 3,423 of them as people finally matched (precision 91.2%). Version 1 no longer drafts the 230 proposals scored 60 (all of them tied matches; no draft capped at 60 as paid by a third party fell in this window), of which people had changed 192: it proposes 3,523 (coverage 73.2%, a loss of 4.8 points, inside the 5-point allowance), 3,385 of them right (precision 96.1%, above both 95% and the baseline). The held-out golden cases give 58 of 60 (96.7%); the run's recorded reads hold none of the 60 held-out IDs and no row after 2026-07-31. The bundle E1 is frozen with the version's hash, `cash.match_bank_line` 1.2.0, the baseline H0, the data window hash and 20 of the 230 changed decisions, and the version becomes `backtested`.
- **Shadow.** The accountant submits a proposal to raise version 1 to `shadow` with E1; the finance manager, who neither drafted nor submitted, approves. For 15 business days the cascade computes both sets on each line and records version 1's outcome in `artifact_shadow_outcome`: on 1,630 lines its proposals agree with people's final matches in 96.3% of cases, against 91.0% for H0. Live evidence E2 is frozen.
- **A stale attempt.** The proposal to raise version 1 to `assisted` with E2 is approved on 2026-10-24, but the release of that night upgraded `cash.match_bank_line` to 1.3.0; execution fails with `artifact_evidence_stale`. The release changed nothing in force (H0's hash is unchanged). The re-evaluation of the core defaults under 1.3.0, over the window of the auto-post rule's evidence, found 412 proposals at or above the floor of 90 and below the maximum, 410 of them (99.5%) as people finally posted them and none to another partner: it passed, auto-post continued, and the owners got `artifact_function_changed` with the re-evaluation. New live evidence E3 under 1.3.0 is created over the same days, and the next proposal executes.
- **Assisted, then active.** From 2026-10-27 version 1 is in force for drafting (hash H1, state `assisted` on every line), and auto-post is off: assisted versions never act, and the rule's evidence names H0. After 10 more business days live evidence E4 shows 97.1% of its drafts posted unchanged, and version 1 becomes `active` on 2026-11-10. Auto-post stays off until the chief accountant enables the rule again with evidence under H1: ADR-0051 rule 18's 300 proposals over two statement months.
- **Demotion.** On 2026-12-10 the 30-day snapshot shows 2,350 decisions with 263 overrides (11.2%) against the evidenced 2.9%: a large customer began paying several invoices in one transfer, and the subset step's drafts for it were mostly wrong. The threshold, the larger of 5.8% and 7.9%, is breached. The monitor cannot know the cause; it moves the pointer back to the version in force before (the core defaults), demotes version 1 to `shadow`, writes the transition and raises `artifact_demoted` for the chief accountant, naming the auto-post rule. Proposals are made under H0 again, but the demotion marked the auto-post rule's stored evidence outdated in the same transaction, so auto-post stays off until a new rule version is enabled on new evidence; the accountant meanwhile sees the subset problem in the item and fixes the customer's payment terms. A version 2 starts from a new draft.

**L2: a bank matching rule.** On 2026-09-12 a person matches a line whose agent suggestion carried the stable payer token `ACMEPAY-7781` to partner Acme. The token appears in two of Acme's lines in 90 days (2026-07-02 and 2026-09-12) and in no other partner's, so the `cash` consumer writes a `bank_matching_rule` version in `draft` (token → Acme) with `CreateBankMatchingRuleVersion`, tainted because the token is untrusted text. Its drafting window ends on 2026-09-12. On 2026-10-11 a third line with the token arrives, and the person matches it to Acme; the evidence (1 later line, matched to Acme by people, none elsewhere) is now sufficient and the version becomes `backtested`. The cashier submits a proposal to raise it to `assisted`, and the chief accountant, neither the cashier nor the human the consumer acted for, approves. In suggest mode the rule drafts receipts with match basis `company_rule` and no score, so nothing is auto-posted. After 10 such drafts all posted unchanged, live evidence supports `active`: the rule now names Acme in confirm mode, step 3 finds Acme's one open item of the amount and scores it 90, within `cap_company_rule` 90; had Acme had two equal items, the match would have been tied and never posted automatically. When one line in December carries both the token and an invoice reference of another partner, the ambiguity rule drafts it without a score, and a person decides.

**An account rule.** The company's bank charges a monthly fee, and each fee line's description carries the bank's fee code `BKFEE01` as a whole token. A person writes a rule version mapping `BKFEE01` to the bank charges account with `CreateBankMatchingRuleVersion`. After a later fee line that people posted to that account it is backtested, approved into suggest mode, and after 10 suggest-mode drafts posted unchanged it becomes `active`. An outflow carrying `BKFEE01` now drafts to the bank charges account at 85 (`cap_company_rule` 90 under the unverified-counterparty cap, since no partner owns the paying account); an inflow carrying it (a refunded fee) only suggests, because its sign is against the account's natural side; a line that also matches a customer's token rule suggests. No partner owns the bank's paying account, so every such draft carries `counterparty_unverified` and is posted by a person, whatever the auto-post rule's evidence counts.

**Why L3 stays outside the running system in Phase 1.** A company wants a discount that depends on a customer's purchase history with seasonal exceptions; no decision table expresses it. An AI could write the function in minutes, but the survey's evidence is that generated code has high flaw rates and that reviewers trust it too readily, and a function running inside the core's process can read and write anything its transaction can. Phase 1 has no sandbox, no capability boundary and no review gate inside the running system. So the request becomes a source change: the AI writes the tests first, then the code, in a package or the core; a person reviews it with static analysis; CI runs the invariant harness, the golden sets and the replay suite; and the release ships it. The result is reviewed code with a version, not an artifact a company promotes. When the author decides on sandboxed pure functions (rule 24), such a function will be an L2-like artifact on this ADR's lifecycle, whose output core code consumes only as a proposal.

## Context

Spec 03 rule 9 says what an agent learns must be deterministic data stored in the system, viewable and editable, and Principle 13 says the model never computes a number. ADR-0051 already applies this to mappings and bank token rules, and ADR-0050 has frozen promotion evidence for agent types. What was missing is the same discipline for the constants of the deterministic core and for every rule a company or an AI writes, so that "the AI learned something" always means "a person promoted a versioned artifact on evidence".

How others do it, concepts only (the 2026-11-15 survey): finance matching tools (SAP Cash Application, BlackLine, Oracle Account Reconciliation) separate show and act thresholds and suggested from confirmed rules; model risk practice (SR 11-7) requires out-of-sample backtests, ongoing monitoring and predefined demotion; champion/challenger and alias-based promotion give instant rollback; AlphaEvolve's stated limitation is overfitting to the evaluation set, hence held-out cases the generator never sees and recorded evaluation attempts. LLM verbalized confidence is unreliable as a gate. Generated code has high flaw rates and must not run unsandboxed.

Review round 2 found that held-out cases leaked through rows that point at them and through stored results, that "newer than the demotion" compared times, that a release under core defaults had no subject, and that account rules were undefined; case-reference columns with a closed drafting tool list, an outdated marker set in the same transaction, re-evaluations of core defaults and the account-rule conditions answer them. Review round 1 found holes in the out-of-sample rule (drafts without a window, empty or repeatedly tried windows), held-out cases visible to the generator as ordinary data, a per-field LLM mark nobody could derive, cascade parameters that could lift tied matches and partial references above exact ones, a hash that changed with every release, and acting paths that re-armed after a demotion. Default windows, recorded attempts, query-layer filtering, a gate allowlist with lineage, order constraints and the tied rule, a version-free hash and evidence newer than the last demotion answer them.

## Options considered

| Option | For | Against |
| --- | --- | --- |
| One lifecycle for every L1 and L2 artifact, stages per kind or function (chosen) | One mechanism to build, read and audit; agents learn it once | Ceremony for a one-line change, eased by small bundles and skippable stages |
| A lifecycle per kind | Fitted to each | Several mechanisms with the same gaps |
| Parameters as company settings changed directly | Simple | No evidence, no rollback, no record of which value decided |
| Versioned parameter sets with bounds and order constraints (chosen) | Every decision names its parameters; rollback is a pointer | A registry declaration per function |
| Learned scorers (ML) now | Higher automation | Hidden state, against spec 03 rule 9; after Phase 1 as a versioned artifact (A8) |
| Backtest on a later window than drafting, every draft with a window (chosen) | No look-ahead | Waits for data after drafting, or splits history |
| Backtest on the drafting data | Fast | Rewards overfitting |
| Held-out labels hidden only | Simple | The held-out cases stay ordinary data for the generator |
| Held-out cases filtered from drafting runs' queries (chosen) | The generator cannot fit them | One more filter in the query layer |
| A per-field LLM mark | Fine-grained | Not derivable; misses computed fields |
| A gate-field allowlist with CI lineage (chosen) | Checkable; fails closed | New gate fields need a registration |
| Thresholds per artifact kind | Few settings | Bank lines and duplicate partners do not share counts |
| Thresholds per function with small-company minimums (chosen) | Fits each function | One more declaration per function |
| Generic evidence table (chosen) | One shape for every kind | Polymorphic artifact references, checked by invariants |
| Reuse `agent_promotion_evidence` | No new table | Its columns are agent-specific; widening it changes an accepted table |
| Automatic demotion to the version in force before (chosen) | Fails toward known behavior | A noisy month can demote; thresholds need tuning |
| Signal only, as for agent types | A person decides | A drifting artifact keeps acting until someone reads the item |
| AI-written code through the repository only (chosen for Phase 1) | Reviewed, tested, versioned | Company-specific functions wait for a developer |
| Sandboxed extension functions now | Fast customization | Runtime, ABI and review gate not designed; the author's decision |
