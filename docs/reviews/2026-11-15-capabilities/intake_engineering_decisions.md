# Architect decisions: ADR-0057 Document intake and extraction (multimodal); ADR-0062 Product engineering workflow (DS-57 part) (2026-11-15)
Source: research_multimodal_masterdata.md (recommendations 1-18 accepted unless stated); capability_check.md (3, 4). Author approved designing these; agentic best practice is thin, so the design follows IDP practice plus the existing safety model.

ADR-0057
1. Reader ladder, run by a system job (not an agent run): identify by bytes (not extension), then try readers in order, first valid record wins: structured XML (package readers: VN e-invoice in l10n_vn chosen by schema version; CII/Factur-X and UBL as core-neutral readers, later if not needed), XML embedded in PDF, QR/vCard, spreadsheet cells, PDF text layer cross-checked with OCR, OCR words with positions, vision model last.
2. One document_extraction record per attachment and purpose, with extraction_field rows: value, evidence (xpath | cell | char span | page + normalized region + OCR word ids), method (parsed, ocr, vision_aligned, vision_unaligned, computed), raw and calibrated confidence, rule results, is_untrusted, verified_by/at. Append-only: a correction adds a row superseding the earlier one.
3. Vision grounding: the vision model returns per field value + OCR word ids + status (found, not_found, illegible); code checks the value appears at those words (numbers exact). Unaligned values are greyed suggestions, never prefill a draft. Totals and tax always recomputed by code.
4. Validation rules override confidence: arithmetic (lines, tax, totals), check digits, buyer tax ID equals the company's, duplicates (file hash, then seller tax ID + series + number, then near-duplicate over full history), bank details on a document never change partner master data (existing bank-account proposal rule).
5. A verification screen in the ERP (ADR-0040 note): page beside fields, risky fields first, keyboard-first, machine-checked vs human-confirmed shown apart. Person corrections become per-supplier mapping rules (rules as data, proposal-bound; ADR-0059 level 2).
6. Taint: two kinds. Instruction taint (free text from outside narrows a run to the subject partner, drafts only) stays as designed. Value trust: typed fields that passed validation (parsed or deterministic with all rules passing) do not taint a run that reads only those fields; vision-extracted values stay unverified until a person confirms; a failed e-invoice signature or a hidden-text flag forces full human review. Note this is a reading of spec 03 rule 1 and add it to the existing open question for the author (interim: as stated, because it narrows rather than widens: only deterministically parsed and validated typed fields).
7. Injection defenses: the reader/vision model has no tools and returns only the typed schema; it reads a rendered page image, not the PDF text layer; text in the layer but not on the rendered page sets hidden_text_suspected; datamarking (spotlighting) on any text passed; injection classifiers add a signal only.
8. Personal data: photos, business cards, delivery notes, voice and inquiry attachments are labelled personal as a whole. A new seat class extraction_vision_personal (image/PDF reading, personal allowed). It is designed but disabled until the author enables a permitted provider (consistent with the disabled local adapter, ADR-0050 B3, and with Decree 356/2025 cross-border rules: open question). EXIF and location metadata stripped from derived images. A redacted image is never treated as non-personal.
9. Phase 1 intake: (a) supplier-invoice mailbox: XML -> ImportEInvoiceRecord by system with signature, authority code and arithmetic checks (the VN reader is l10n_vn package data/code; the e-invoice provider connection stays the DS-24 add-on); (b) PDF-only invoices: deterministic text layer/OCR extraction + full human verification, no automatic posting; vision only if the seat is enabled; (c) business card -> contact change proposal: QR/vCard deterministic first; image reading only via the personal vision seat when enabled; (d) inquiry attachments: spreadsheets read deterministically into extraction rows a person can turn into quotation lines; drawings/PDF RFQs: stored, shown, not read in Phase 1 unless the seat is enabled.
10. Later: delivery-note photo extraction, drawing and PDF RFQ reading, per-supplier straight-through after golden sets, Vietnamese voice notes (local ASR, transcript with audio timestamps as evidence).
11. Legal references: e-invoice rules now Decree 254/2026/ND-CP and Circular 91/2026/TT-BTC (effective 1 July 2026); the package reader selects by XML schema version; the format annex is unverified (open question, DS-40). Update stale references by notes where the design cites Decree 123/70.
12. Ownership: document_extraction in module `documents` or `attachments` (decide by ADR-0022 layering; readers are pure functions registered by packages through the hook pattern).

ADR-0062 Product engineering workflow
13. One product_engineering agent workflow with entry points: a person's own note (untainted), a person's own spreadsheet (import_batch scope), and an outside drawing/RFQ/spreadsheet (via ADR-0057 extraction). Interim (strict reading, consistent with the CPQ path A1): outside content never starts a configuring/drafting run directly; a person verifies the extraction, then starts the run on their own note that references the verified extraction. Add to the tainted read scope open question the reviewer's proposal (tainted runs may call matching queries returning id, code, name, unit, category, status only) as an author decision.
14. Resolve components before creating: exact code -> barcode -> supplier code -> manufacturer part number -> rank_candidates with blocking; the model sees at most k candidates and picks one or says new_item_needed with evidence; never writes a code, standard time, rate or price unless it appears in its source.
15. New items as CreateProduct/CreateItem change proposals; non-intelligent numbering by sequence; category drives required attributes; description generated from attributes; each proposal lists rejected duplicate candidates and why.
16. Draft BOM and routing revisions (existing commands); GetBillOfMaterialsRevisionCheck plus per-category readiness rules; CreateCostEstimate listing missing rates/times as gaps (never zero) with delta to the previous estimate; one evidence pack (sources, matching decisions, checks, estimate, effectivity).
17. Release only through an approved change proposal; the approver is not the person whose request started the run; a draft BOM may reference proposed items but release is blocked until they are approved. ECO in Phase 1 = new revision + proposal with impact evidence (where-used, open orders, stock disposition, cost delta).
18. The model drafts quantity structure only; never a cost. Later: ECR vs ECO, EBOM from CAD/PLM (STEP AP242/CSV) linked to MBOM, drawing title block reading, similar-drawing search, embedding-based duplicates.
19. BOM/routing import templates for migration (ADR-0044 note).
