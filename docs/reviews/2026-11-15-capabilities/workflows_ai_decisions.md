# Architect decisions: ADR-0058 Configurable workflows (spec 16) and ADR-0059 AI tuning and development of deterministic functions (2026-11-15)
Source: research_workflows_ai_rules.md (W1-W12, A1-A12, X1-X13), capability_check.md (1, 2). Author approved the split. Global core: any regime-specific value is package configuration only.

ADR-0058 Configurable workflows
1. (W1) Three configuration tiers only, all company data: (a) parameters (typed, registered settings); (b) typed decision tables; (c) event-condition-action automation rules whose actions are only: create a draft through a registered command marked automation-allowed, raise a work item, send an internal notification, start a registered agent type (where the agent type declares the trigger kind), set a hold through a registered interface. Vocabulary (event types, condition fields, actions) is code (registry); composition is configuration. No scripting in Phase 1.
2. (W2) No BPMN or orchestration engine in Phase 1: approvals stay in policy (ADR-0043) and pools (ADR-0055); waiting in the work queue; asynchrony in the outbox. Document lifecycles and agent workflow steps stay code.
3. (W3) Every configuration artifact (decision table, automation rule) is versioned, immutable once active, effective-dated, activated through a change proposal after validation and stored tests pass; each evaluation records the artifact version.
4. (W4) Decision tables: hit policy unique or monotone-combine only (no order dependence); validation proves completeness/overlap per declared inputs.
5. (W5) Loop guards in the dispatcher: causation chain on every event and command with depth cap 3; the same rule never acts twice on the same target within one chain; triggers on declared field changes, not any write; cycle check at activation over the rule graph; circuit breaker (disable after N failures in a window, raise a work item); idempotency keys derived from (rule version, event id).
6. (W6/W7) Tests stored with each artifact; before activation the candidate is replayed over recorded events (a window) and shown as a diff against the active version; each execution leaves an automation_execution record agents can read.
7. (W8) Configuration references only versioned registry items; every upgrade re-validates and replays all active configuration; failures deactivate the artifact with a work item, never break silently.
8. Actor (Q1): automation rules run as system on behalf of the rule owner; the owner must hold every permission the actions need, re-checked at each execution (failure -> execution refused and logged, circuit breaker counts it); actions inherit taint from the triggering subject (tainted subject -> drafts only).
9. Agent triggers become configuration: which registered agent type a company starts on which declared trigger kind is an automation rule (replacing hard-wired wake-ups where the agent type declares the trigger kind as configurable).
10. Later: expression language (CEL or FEEL subset), durable orchestration with pinned versions when two real long processes need it (Q4: that is the justification test), environments/pipelines, visual designer.

ADR-0059 AI tuning and development of deterministic functions
11. Three levels: L1 parameter sets (versioned per company: thresholds, scores, windows of deterministic functions that declare tunable parameters with bounds), L2 rules as data (decision tables, matching rule sets, pricing/validation rules, report and analysis definitions, extraction mapping rules), L3 new code functions. AI may draft L1 and L2 artifacts; L3 is not done by AI in production in Phase 1 (A6): AI-written code may only be proposed as a source change through the normal repository review (outside the running system). Sandboxed pure extension functions (WebAssembly/microVM, tests-first review) are after Phase 1 (A10) and an author decision (open question).
12. (A1) One lifecycle for every AI-produced (or human-produced) L1/L2 artifact: draft -> backtested -> shadow -> assisted -> active; rollback = pointer move to the previous active version; the agent-type ladder of ADR-0050 is the same pattern (note).
13. (A2) Promotion needs a frozen evidence bundle: backtest on a later time window than the drafting window (no look-ahead), comparison with the current version, held-out golden set results the generator never saw, a sample of changed decisions for human inspection. Thresholds per artifact kind are company settings with neutral core defaults (flagged values).
14. (A3) Matching (bank, partner, item) uses deterministic rule passes, each marked confirm or suggest; ambiguity always suggests; AI proposes rules and tolerances; proposer is never approver.
15. (A4) Two calibrated thresholds per scorer (show suggestion, act); acting is off by default; LLM self-reported confidence is never a gate.
16. (A5) Report and analysis definitions are declarative specs over the query and analysis layers (ADR-0049, ADR-0060), never SQL.
17. (A7) Monitoring: override rate and outcome drift per active artifact; automatic demotion to shadow (and a work item) beyond a threshold.
18. Golden sets (Q3): labelled by people holding the area's approve permission; labels are company data with labeller and date; the core ships synthetic golden sets only.
19. Retention (Q2): decision and evaluation records follow the audit retention of ADR-0038; a regime may set a longer minimum (package configuration).
20. Bank matching (Q5): Phase 1 LLM contribution is suggest-only (already); deterministic auto-post stays off by default and only via the evidence rule of ADR-0051.
21. Cross-cutting confirmations (X1-X10): note on ADR-0050 that agent-type versions pin model snapshot and prompts (X7, already near), typed tools with side-effect class and preconditions (X2), information-flow labels as the taint model's direction (X3, flag later), approvals on diffs (X4), budgets and breakers (X6), OpenTelemetry-compatible traces linked to command ids (X8), one registry of agent types and decision artifacts (X9), state-based graders before model graders (X10). Only add what is not already in ADR-0050/0051.
