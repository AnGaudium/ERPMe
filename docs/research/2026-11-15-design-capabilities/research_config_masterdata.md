# Research: configurable master-data conventions and generated narrative

Date: 2026-11-15. Scope: six open questions (product numbering, unit names, purchase-return value, analysis narrative, barcode interpretation, near-duplicate invoices), surveyed as generic, global best practice. Localization is separate later work; every setting below is designed so that any country package can seed or constrain it. The author's direction is to follow surveyed best practice, keep hard locks to a minimum, and make choices settings that each customer fixes at implementation, with country rules only in localization packages.

How to read it: each section gives what vendors do, then a recommendation table (setting, scope, safe default, bounds, who changes it, what stays fixed). Vendor facts come from vendor documentation where it could be reached and from community sources otherwise. Those are marked "(community)". Nothing here decides a legal matter.

**Scope levels** used below: *installation* (one deployment), *regime package* (a country localization package seeds or forces a value), *company*, *product category*. **Change authority** is written as a role idea, not an ERPMe role name. Every setting change should be a human-only command with a reason, recorded in the audit log, and should take effect from a stated date, never retroactively.

## 1. Product codes (DS-20, DS-57; ADR-0062 rule 9)

**What vendors do**
- **SAP.** Number ranges are kept per *group of material types* (MMNR). Each group can hold one internal and one external interval at the same time. Material type configuration (OMS2) decides which one applies. Internal numbers are numeric only, while external numbers may be alphanumeric. External numbers can be entered "without check" against the interval, and a KBA notes that MM01 accepts numbers outside the external interval ([SAP community, MMNR](https://community.sap.com/t5/enterprise-resource-planning-blog-posts-by-members/material-number-ranges-mmnr/ba-p/13415700); [KBA 3496337](https://userapps.support.sap.com/sap/support/knowledge/en/3496337)). The material number does not change once created.
- **Dynamics 365.** The product number is either generated by a number sequence or entered manually. Sequences carry *Manual*, *Continuous* (gapless) and scope flags ([Product identifiers](https://learn.microsoft.com/en-us/dynamics365/supply-chain/pim/product-identifiers); [continuous sequences](https://learn.microsoft.com/en-us/dynamics365/guidance/techtalks/finance-operations-continuous-number-sequence-performance-improvements)). Common practice is to use non-continuous sequences for master data, because continuous sequences cost throughput and serve no legal purpose there ([Stoneridge, community](https://stoneridgesoftware.com/five-best-practices-for-number-sequence-setup-in-dynamics-365-finance-and-operations/)).
- **Odoo.** Core Odoo has no automatic `default_code`. Customers add an `ir.sequence` in a module, often one per category, that fills the code only when it is empty ([forum](https://www.odoo.com/forum/help-1/how-to-make-product-internal-reference-sequential-odoo-11-enterprise-134812); [Viindoo per-category module](https://apps.odoo.com/apps/modules/18.0/to_product_code_sequence); [OCA product_sequence](https://pypi.org/project/odoo11-addon-product-sequence)).
- **NetSuite.** Auto-generated numbers cover transactions, entities and custom records, with an *Allow Override* box. Oracle warns that override brings duplicates and gaps ([Auto-generated numbers](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/bridgehead_4340447524.html)). I found no native auto-numbering for item records. That is unverified.

**Pattern.** All four make the choice between automatic and manual a setting per product class. None requires product codes to be gapless. Prefixes are optional. Uniqueness is always enforced, and SAP never changes a number once it is in use.

| | Recommendation |
|---|---|
| Setting | `master_data.product_code.assignment`: `sequence` / `manual` / `sequence_or_manual`; `master_data.product_code.prefix_source`: `none` / `category_short_code`; `master_data.product_code.pad_width` |
| Scope | Company, overridable per product category, mirroring SAP's per-material-type ranges |
| Safe default | `sequence`, key `product`, no fiscal year, no branch, gaps allowed (not continuous), category short code as prefix if set. This matches ADR-0062 rule 9's interim, so accept the interim as the default |
| Bounds | Code length 1–40 (SAP S/4HANA's length), character set `A–Z 0–9 - _ .`, upper-cased, no spaces. Pad width 0–12 |
| Who changes | Master-data administrator. A category override is set by the category owner |
| Fixed | Unique per company. Never reused after deletion, the same way barcodes are retired. Immutable once any document refers to it. Not used to carry meaning that code reads (no rule may parse the prefix). Issued at proposal execution, so an abandoned proposal burns no code |

## 2. Unit names, translations and e-invoice unit codes (ADR-0056 rules 2, 18)

**What vendors do**
- **SAP.** T006 holds the internal unit and its ISO code, with a *primary* flag when several internal units share one ISO code. T006A holds language-dependent texts per unit: a 3-character commercial unit (MSEH3), a 6-character technical unit (MSEH6) and a long text. EDI uses the ISO code, never the text ([help.sap.com, units](https://help.sap.com/saphelp_470/helpdata/EN/2a/fa0122493111d182b70000e829fbfe/content.htm); [T006A](https://leanx.eu/sap/table/t006a/); [ISO-to-SAP FM](https://www.se80.co.uk/sapfms/u/unit/unit_of_measure_iso_to_sap.htm)).
- **Odoo.** `uom.uom.name` is `translate=True` ([source](https://raw.githubusercontent.com/odoo/odoo/18.0/addons/uom/models/uom_uom.py)). For UBL and CII, `account` maps unit XML IDs to UN/ECE codes and falls back to `C62` ([source](https://sources.debian.org/src/odoo/18.0.0%2Bdfsg-2/addons/account/models/uom_uom.py)). OCA `uom_unece` adds an explicit code field ([OCA](https://pypi.org/project/odoo-addon-uom-unece/)).
- **EN 16931 / Peppol.** BT-130 `unitCode` must come from UN/ECE Rec 20 with the Rec 21 package codes (prefixed `X`). Violation is fatal under BR-CL-23 ([Peppol](https://docs.peppol.eu/poacc/billing/3.0/syntax/ubl-invoice/cac-InvoiceLine/cbc-InvoicedQuantity/unitCode)). Most structured e-invoice formats carry a code, not a text; a format that carries the unit text instead needs a length setting, which a country package can supply.

**Pattern.** Every system keeps a code and language-dependent names apart. The printed text is a translation, while the code is what crosses systems. ADR-0056 rule 2's split (core English names translated by the core i18n catalog, plus statutory names supplied by a country package) matches SAP's T006/T006A split. I recommend **accepting the interim**: keep statutory names in the package's per-row CSV with a basis per row, since a per-key basis is needed and the terminology JSON has none.

| | Recommendation |
|---|---|
| Settings | (a) `documents.unit_name_max_length` (regime, empty = no limit); (b) `documents.unit_name_source`: `statutory_then_translation` (regime); (c) `documents.e_invoice_unit_code_scheme`: `none` / `unece_rec20_21` (regime), with a package mapping file from ERPMe unit to scheme code, so an `x-carton` company unit can map to `XCT` |
| Scope | (a)–(c) regime package. Company units' own names stay company data (`data_translation`) |
| Safe default | Core: no limit, translation as source, no unit-code scheme. A country package sets real values only after its own verification; until then (a) stays empty |
| Bounds | Max length 1–255. Unit codes validated against the shipped Rec 20/21 list |
| Who changes | Package maintainer, through a package release. A company may add mappings for its own `x-` units, but may not edit core-unit mappings |
| Fixed | Never silently truncate a unit name on a statutory output. A name over the limit is a typed issue at product-unit save (warning) and at e-invoice issue (blocking). Core units keep their Rec 20 code as their identity. The core holds no country's statutory names |

## 3. Value of a purchase return (DS-09, DS-19, DS-11, DS-22; ADR-0020 rule 5; ADR-0021 rule 3)

**What vendors do**
- **SAP.** A return delivery (122) with reference to the PO and goods receipt is valued from the PO and receipt, mirroring the GR/IR it reverses. Reversals with PO reference "are valuated with the value determined from the purchase order" ([SAP Learning](https://learning.sap.com/courses/inventory-management-and-physical-inventory-in-sap-s-4hana/posting-cancellations-return-deliveries-and-returns)). A returns PO item (161) is valued at the returns PO price, and with moving average price the average adjusts ([SAP help, movement types](https://help.sap.com/saphelp_46C/helpdata/EN/fc/6cec6eb435d1118b3f0060b03ca329/content.htm); [KBA 2919831](https://userapps.support.sap.com/sap/support/knowledge/en/2919831); [KBA 3252447](https://userapps.support.sap.com/sap/support/knowledge/en/3252447)). One known side effect: a return at a value far from the current average pushes the moving average price of the remaining stock.
- **Dynamics 365.** The return line is *marked* against the original receipt or invoice transaction, so the issue carries the original cost after inventory close. Creating the return from the invoice ("credit note") copies the original prices and charges and limits the quantity to what was received ([Create vendor returns](https://learn.microsoft.com/en-us/training/modules/process-purchase-orders-dyn365-supply-chain-mgmt/7-create-vendor-returns); [costing FAQ](https://learn.microsoft.com/hr-hr/dynamics365/supply-chain/cost-management/inventory-costing-faq)). Without marking, the costing model's own cost applies.
- **Odoo (AVCO).** The return leaves stock at the **current average**, while the vendor refund is at the purchase price. The difference goes to the price-difference account under Anglo-Saxon accounting ([Odoo 19 doc](https://www.odoo.com/documentation/19.0/applications/finance/accounting/get_started/avg_price_valuation.html)). Code for returns that reference their origin move takes the origin's unit cost in some versions ([commit](https://git.coopdevs.org/coopdevs/odoo/OCB/-/commit/8981428103eea35c083e44d51a34633bc714d83a)), so behaviour depends on the version.
- **NetSuite.** A vendor return fulfillment posts at the item's cost under its costing method. The difference to the vendor credit goes to a configurable *Vendor Return Variance* account ([Items/Transactions preferences](https://docs.cloud.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N1387022.html)). Details are partly (community).

**Pattern.** Two real options exist, and leading products ship both:
- **document value**, the reversal view (SAP 122, D365 marking);
- **current cost**, the issue view (Odoo AVCO, NetSuite, D365 without marking), where a variance account absorbs the difference to the credit.

Landed cost follows the document: SAP reverses planned delivery costs proportionally, and D365 credit notes copy charges.

| | Recommendation |
|---|---|
| Setting | `movement_type.purchase_return.valuation`: `document_value` / `current_cost`. `movement_type.purchase_return.include_landed_cost`: true/false. `movement_type.purchase_return.reporting`: `negative_receipt` / `issue`. `accounts.purchase_return_variance` (required when `current_cost`) |
| Scope | Regime package seeds it (a statutory chart may prefer one). Company may change it, effective only from the start of a fiscal period |
| Safe default | `document_value` (the GR/IR debit of the positions returned, as the interim seed says), `include_landed_cost` true for a return that references a receipt with allocated landed cost, `negative_receipt` |
| Bounds | Enum only |
| Who changes | Controller or finance lead, before the first posting of the period |
| Fixed | Return quantity ≤ received quantity minus earlier returns of that receipt. GR/IR of the PO line always clears at the PO value whichever option is chosen, and only the stock side differs. Any difference posts to a named account, never into the average silently. Stock value never goes negative: the clamp rule of ADR-0020 stands. The chosen option is stamped on each movement, so history replays the same way |

## 4. Generated narrative in analysis (DS-34; ADR-0060 rule 23)

**What vendors do**
- **Power BI.** The classic *Smart narrative* is template NLG with dynamic values bound to the model and refreshed on filter, with no LLM ([doc](https://learn.microsoft.com/power-bi/visuals/power-bi-visualization-smart-narrative)). The *Copilot narrative* is free LLM prose over the page's visuals. Microsoft states "accuracy … may be limited", offers custom prompts and a manual refresh, and needs tenant admin enablement and paid capacity ([doc](https://learn.microsoft.com/en-us/power-bi/create-reports/copilot-create-narrative)). It does not guarantee numbers.
- **Tableau Pulse.** Insights are found by statistical models. AI only words the summary, and "there are checks to ensure that no numbers change in the insight summaries". The setting "Tableau Pulse: Summarises key metric insights" is off by default, separate from turning Pulse on, and can be limited to groups ([Pulse setup](https://help.tableau.com/current/online/en-gb/pulse_set_up.htm)).
- **ThoughtSpot (Sage, now Spotter).** The LLM produces search tokens or a semantic query (AgentQL), and ThoughtSpot compiles deterministic, governed SQL. The semantic query is the verifiable artifact ([AgentQL docs](https://docs.thoughtspot.com/cloud/26.9.0.cl/agentql); [security](https://thoughtspot.com/blog/secure-data-processing-with-llm)). Numbers come from SQL. I found no documentation of a narrative toggle (unverified).
- **Arria; Narrative Science Quill.** Both are rule- and template-driven data-to-text systems: analytics rules choose the facts, and templates insert the values ([Arria](https://www.wikipedia.org/wiki/Arria_NLG); [Quill patent](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11561986)). Narrative Science was acquired by Salesforce in 2021 and folded into Tableau.
- **Oracle Analytics.** *Auto Insights* and *Explain* are ML-selected visuals. The *Language Narrative* visualization writes text with tone (factual by default, business, casual) and detail-level settings. Generative features need a configured GenAI service ([doc](https://docs.oracle.com/en/cloud/paas/analytics-cloud/acubi/language-narrative-visualization.html); [AI Assistant](https://docs.oracle.com/en/cloud/paas/analytics-cloud/acabi/oracle-analytics-ai-assistant-features.html)).

**Answers to the brief**
- **Free LLM prose?** Only Power BI Copilot and Oracle's GenAI assistant allow it, and both carry an accuracy disclaimer.
- **Number guarantees?** The products that guarantee numbers do it structurally: code selects the facts and code renders the values (Tableau's deterministic insights plus its number checks, ThoughtSpot's compiled SQL, Arria and Quill templates).
- **Toggles?** Toggles are admin-level, off by default for GenAI (Tableau, Power BI tenant), scoped to groups, with a disclaimer shown to users.

ERPMe's Phase 1 claim plan is stricter than every vendor, and that suits an ERP where a wrong number is costly. Keep it.

| | Recommendation |
|---|---|
| Setting | `analysis.narrative_mode`: `facts_only` / `claim_plan` / `free_prose` |
| Scope | Installation sets the maximum. A company may lower it, never raise it (as ADR-0060 rule 11). Per agent type version |
| Safe default | `claim_plan`. `free_prose` cannot be selected until the evaluation suite shows the acceptance-rate threshold (e.g. ≥ 80% of ordinary sentences accepted and 0 accepted sentences with an unbacked number, rank or direction) for that language and model version |
| Bounds | Enum. Threshold 0.8–1.0 for acceptance. The unbacked-claim rate is fixed at 0 |
| Who changes | Installation administrator, after the evaluation result is recorded. A company administrator may only lower it |
| Fixed | Every number shown is a key fact rendered by code, in every mode. `free_prose` is shown beside the key facts, labelled as model-written, with a disclaimer, as Tableau and Power BI do. Any numeral or number word in prose must resolve to an offered fact (Tableau's "no numbers change" check), otherwise the prose is dropped and the claim plan is shown. Abstention stays typed |

## 5. Barcode interpretation choices (DS-20, DS-42; ADR-0061 rules 3, 5, 17)

**What vendors make configurable**
- **Dynamics 365.**
  - Prefixes per GS1 symbology (FNC1, DataMatrix and QR characters).
  - The group-separator substitute (e.g. `~`).
  - An *Unknown application identifier policy*: *Error* or *Skip the data element*.
  - Per menu item, which AIs fill which fields, with *Allow overwriting*.

  It expects scanners to be configured to send AIM identifiers and a printable GS ([GS1 bar codes](https://learn.microsoft.com/en-us/dynamics365/supply-chain/warehousing/gs1-barcodes)).
- **Odoo.** The GS1 nomenclature rules are editable regexes, and the FNC1 separator is a configurable alternation, default `Alt029|#|\x1D` ([GS1 nomenclature](https://www.odoo.com/documentation/16.0/applications/inventory_and_mrp/barcode/operations/gs1_nomenclature.html)). Lots keep expiration, best-before (`use_date`), removal and alert dates as separate fields.
- **Day 00.** The GS1 General Specifications say day 00 "SHALL be interpreted as the last day of the noted month" for the expiry-type dates ([GS1 Sweden notice](https://gs1.se/en/news/change-of-date-format-for-regulated-healthcare-products/)). For regulated healthcare, GS1 has forbidden day 00 since 1 January 2025 ([GSCN 21-040](https://www.gs1.org/docs/barcodes/GSCN_21-040_HealthcareExpDate.pdf); [GS1 UK](https://www.gs1uk.org/insights/news/change-of-date-format-for-regulated-healthcare-products)). I could not verify GS1's text for (11) and (13), so ERPMe's first-day reading for those is a design choice.
- **Best before vs expiry.** These are different facts: quality versus safety. Odoo and most WMS store them apart. Filling expiry from (15) is not a GS1 rule.

| Setting | Scope | Safe default | Bounds | Who changes |
|---|---|---|---|---|
| `barcode.gs_substitute` (exists) | Company, overridable per scanner profile | `~` | One printable character outside GS1 set 82 | Warehouse administrator |
| `barcode.gs1.day00_expiry_type` for (12), (15), (16), (17) | Company, overridable per product category | `last_day` (GS1 rule) | `last_day` / `reject` | Quality or warehouse administrator. Healthcare categories set `reject` |
| `barcode.gs1.day00_production_type` for (11), (13) | Company | `first_day` (interim) | `first_day` / `last_day` / `reject` | Same |
| `barcode.gs1.best_before_fills_expiry` | Product category | **false**, a change from the interim of rule 17: store (15) as the lot's best-before date | true / false | Category owner |
| `barcode.unknown_ai_policy` | Company | `report_and_ignore` (as `gs1_element_ignored`) | `reject` / `report_and_ignore` | Warehouse administrator |
| `barcode.separator_suspect` | Scanner profile | `stop_and_confirm` (interim) | `stop_and_confirm` / `trust_transport` (only for profiles proven to send GS) | Warehouse administrator, after a test scan |

**Fixed.**
- The check digits, the generated AI table, the predefined-length rules, the century window computed from the business date, and character sets are fixed, because they are the standard, not a preference.
- Digital Link URIs are never fetched.
- A retired code is never reassigned to another owner.
- Day-precision is recorded (`day_precision: month`), so a later policy change can be audited.
- Each parse result stamps the policy values it used.

## 6. Near-duplicate invoice detection (DS-36; ADR-0057 rule 15)

**What vendors do**
- **SAP.** The MIRO check compares vendor, currency, company code, gross amount, reference (invoice number) and invoice date. OMRDC can switch off company code, reference and date per company code, but not vendor, currency or amount. In FI, the amount is compared only when no reference is entered. Whether message M8108 is a warning or an error is configurable ([SAP blog](https://blogs.sap.com/2013/01/28/duplicate-invoice-check-part-2/); [help.sap.com](https://help.sap.com/saphelp_fra110/helpdata/en/c5/107d5307e86655e10000000a423f68/content.htm)). SAP's checks are exact matches. One KBA says the amount is not a key field ([KBA 3774533](https://userapps.support.sap.com/sap/support/knowledge/en/3774533)), so sources conflict.
- **Oracle Fusion.** An optional "enhanced" check uses supplier, invoice type, amount, currency and date regardless of the number, and puts matches on a duplicate hold ([doc](https://docs.oracle.com/en/cloud/saas/financials/25d/fappp/how-can-i-find-duplicate-invoices-without-considering-the.html)). The older Oracle report matched numbers within a character length and dates within a range ([doc](https://docs.oracle.com/cd/A60725_05/html/comnls/us/ap/duplinv.htm)).
- **D365.** "Check for invoice numbers used" applies per vendor against posted invoices, as an error or a warning ([AX 2012 parameters](https://learn.microsoft.com/en-us/dynamicsax-2012/accounts-payable-parameters-form); [D365 EMEA](https://learn.microsoft.com/en-us/dynamics365/finance/localizations/europe/emea-edit-invoice-id-sales-orders)).
- **NetSuite.** The *Duplicate Number Warnings* preference applies to vendor plus exact bill number, with no normalization (community: [Dokka](https://dokka.com/duplicate-invoice-detection-issues-netsuite/)).
- **Coupa.** Coupa argues that exact supplier + number + date + amount checks miss duplicates and uses ML ([blog](https://www.coupa.com/blog/technology-innovation/finding-duplicate-invoices-flight-ai)). I found no public settings.
- **Basware.** Basware says it validates every invoice for duplicates. Its rule settings are not public. A comparable AP product (Tungsten/ReadSoft) always compares supplier and number, and makes date and amount optional toggles ([Tungsten](https://docshield.tungstenautomation.com/RSPIT/en_US/7.3.3/help/PROCESSIT/topics/config_duplicate_invoice_number.html)).
- **Celonis.** Celonis exposes a date range (up to 30 days) and a fuzzy-score threshold ([Celonis](https://docs.celonis.com/en/algorithm-and-default-search-patterns-for-the-object-centric-duplicate-invoice-checker.html)).

**Pattern.**
- An exact key (partner plus normalized number) is always checked.
- A near key (amount plus date window) can be switched on or off.
- The outcome is a hold or warning that a person resolves, never deletion.
- The number is normalized: case, punctuation and leading zeros.

ERPMe's interim (gross within one minor unit and dates within 7 days, or equal number digits) sits well inside this range.

| | Recommendation |
|---|---|
| Settings | `intake.duplicate.date_window_days`; `intake.duplicate.amount_tolerance_minor_units`; `intake.duplicate.number_normalization`: `digits_only` / `alnum_casefold` / `exact`; `intake.duplicate.near_check`: on/off; `intake.duplicate.outcome`: `review` / `block` |
| Scope | Company. A country package may add an exact statutory key (for example a legally unique combination of seller tax ID, invoice series and number, where a country defines one) |
| Safe default | Window 7 days, tolerance 1 minor unit, `digits_only`, near check on, outcome `review` (payment held until resolved) |
| Bounds | Window 0–90 days. Tolerance 0–100 minor units (or ≤ 0.5% of gross, whichever is smaller). Normalization enum |
| Who changes | AP lead or controller |
| Fixed | The exact key (partner + normalized number, plus the statutory key where a package defines one) is always checked and cannot be switched off. Every entry channel (intake, manual, API, agent) runs the same check. A match is never auto-deleted or auto-rejected without a person. A confirmed "not a duplicate" decision is recorded with its reason |
