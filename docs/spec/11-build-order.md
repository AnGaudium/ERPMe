# Build order

The goal is to build each layer once, never building and fixing at the same time. Rework usually comes from five sources: changing the data model after modules depend on it, building features before the accounting core is proven correct, building UI before commands are stable, building frameworks before a real need, and learning customer requirements too late. The principles and order below block each source.

## Build principles

Cite these as "Build principle B5" and so on.

- **B1 · Decide early what is expensive to change.** The ADR list below is decided before the first line of code.
- **B2 · Build inside out.** Each layer passes its gate before the layer above is built. A lower layer changes its contract only for a measured reason.
- **B3 · Commercial documents are a thin layer that emits core commands.** Sales orders, goods receipts and invoices only emit stock and journal commands already verified in the lower layer. Adding a new document never changes the core.
- **B4 · Reference results exist before code.** Golden scenarios, invariants and the synthetic dataset exist before or alongside the corresponding layer, so each layer is built right the first time.
- **B5 · Synthetic dataset from the first month, but no customer commitment.** The synthetic dataset is our own: fictional companies whose transactions a seeded simulator feeds to the system day by day, as in real operation (see [Synthetic dataset](12-testing.md#synthetic-dataset)). Odoo's demo data is used only as a checklist of what kinds of data to prepare; nothing is copied. Build against this data; the pilot is chosen only when the platform is complete.
- **B6 · Hand-built UI and agents always come later.** While building, use the schema-generated UI to operate and test. Hand-built screens come only after the module's commands pass their gate. An agent comes only after its manual path works.
- **B7 · No frameworks before need.** Policy engine, approval and extensibility are built exactly as far as the first concrete case requires; generalize at the second or third case.
- **B8 · Change the schema freely before go-live; freeze it 4 weeks before go-live.** Without real data, schema changes are nearly free, so concentrate risky changes there. After go-live every schema change needs a migration of real data.

## Decide by ADR before writing code

- ID model; precision of quantity, unit price, company currency, foreign currency.
- Document date, posting date, recording timestamp, time zone.
- Command envelope: `actor`, `on_behalf_of`, idempotency key, `plan_hash`, schema version.
- Document lifecycle and versioning, numbering, posting periods.
- Universal journal and its dimensions (canonical list in the universal journal row of [05-accounting-inventory-core.md](05-accounting-inventory-core.md)); material documents separate from accounting documents; transaction key × valuation class × valuation area → operational account.
- Costing model: price control per item, period-end actual costing, movement types table, GR/IR clearing account.
- Multi-currency: transaction, company and optional group currency; rate types (transaction, book, revaluation, customs); FX rules inside the accounting regime.
- Landed cost: a cost that arrives in the same open period is added to the receipt value before period-end costing; a cost that belongs to an earlier, closed period is posted in the current period and allocated by the quantity each consumer took (stock on hand, transfers to other warehouses, COGS, production). Linked to the customs declaration and cost documents.
- Analytical dimensions from the canonical list, and bins and warehouse management ([ADR-0023](../adr/0023-warehouse-management.md)), and reserved columns for catch weight.
- Outbox event format.
- Localization package structure, the system chart and many-to-one mapping rules, i18n with English source.

## Steps and gates

| Step | What to build | Gate before the next step |
| --- | --- | --- |
| 0 · Preparation | ADRs above. Repo, CI with pyright strict, test server, invariant-checking harness. Edge-case catalog v1 and the first version of the business simulator (fictional Vietnamese companies: a trading company and a manufacturing company), which emits a versioned business-event log; per-step adapters translate events into the commands that exist at that step. First golden scenarios | ADRs decided. The simulator produces the small synthetic dataset for the Vietnamese trading company and for the manufacturing company |
| 1 · Ledger | Two-tier chart (system and operational) and the localization package mechanism, Vietnam package with the TT99 regime and FX rules, daily rate table, universal journal posting in transaction and company currency, i18n with English source, append-only journal, reversal, numbering, posting periods, command envelope, audit log, outbox, REST and MCP generated from schemas; the open-item core of [ADR-0026](../adr/0026-open-item-core.md) (tables, catalog, clearing and the posting path; [open-questions.md](../open-questions.md), decided 2026-11-19) | Invariants green on random transaction sequences, foreign currency included. Trial balance correct |
| 2 · Master data | Partners, items, UoM groups per item with fixed factors (stock, purchase, sales unit), warehouses, currencies, valuation classes, account determination table (transaction key × valuation class × valuation area → operational account) | Master data of the synthetic dataset imports through command batches |
| 3 · Inventory, costing, landed cost | Movement types table; material documents for receipts, issues, transfers; lots and serials tracked in stock movements, with no cost of their own; stock count with differences; the warehouse core of [ADR-0023](../adr/0023-warehouse-management.md) (bins, putaway, reservations, pick release, counts by bin); stock posting serialized per (item, warehouse); period-end actual costing across warehouses (existing periodic-average engine ported; BOM levels at step 4b, the production core); landed cost by the rule above; valuation posts journal lines | Matches golden scenarios, including imports with later costs, and the independent recomputation. No negative stock. Putaway, picking, short pick and count flows pass their edge cases |
| 4 · Sequential replay of the synthetic dataset | Sequential import of the medium synthetic dataset (Vietnamese company) through core commands, day by day with month-end closes: opening balances including foreign currency and opening open items per invoice, journal lines and stock movements | The medium synthetic dataset (Vietnamese company, one year) replays day by day through core commands, called through REST and MCP, with every invariant green after every simulated day. Costing, FX and balances match the golden scenarios and the naive recomputation. The coverage report shows every edge case for steps 1–3 exercised |
| 4b · Production core | The production core of [ADR-0032](../adr/0032-phase-1-scope-with-production.md) (Phase 1). It starts after step 4's gate and may run beside step 5; no dates are set (author, 2026-11-19) | The production core passes the independent naive recomputation |
| 5 · Commercial documents | Quotation, sales order, delivery, sales invoice; purchase request, PO, goods receipt, purchase invoice, including foreign currency, via the GR/IR clearing account and three-way match on quantity and price; customs declaration with its own customs rate; purchase cost documents allocated by value, quantity or weight, following the step 3 landed cost rule; returns, discounts, promotions, credit limit; minimal CRM (partners, contacts, interaction timeline, email intake). | 5b · Planning and multi-level MRP | The later planning slice of [ADR-0024](../adr/0024-planning.md) rule 26 (forecast methods by backtest, service-level safety stock, the further action messages) and multi-level MRP of [ADR-0036](../adr/0036-multi-level-mrp.md) (DS-43, DS-54): bill of materials explosion with low-level codes, dependent demand, lead-time offsetting, planned production orders, the capacity check, conversion. It starts after the gates of steps 5 and 4b and may run beside steps 6 and 7; no dates are set | On the manufacturing company of the synthetic dataset, the planning run's planned orders, pegging and exceptions equal an independent naive recomputation; every planning edge case assigned to the step passes; a rerun on unchanged data changes nothing |
| 6 · Cash and AR/AP | Cash receipts and payments, cash count, bank statement import, manual matching, open items per invoice, netting, advances, expenses without a PO, general journal entries with approval; foreign-currency payments, book rate, realized FX differences | AR/AP subledgers match the receivable and payable control accounts (131, 331 in TT99) in both transaction and company currency. Cash and bank books match |
| 7 · Tax and e-invoicing | Date-effective tax rates, import VAT, 01/GTGT XML; outgoing e-invoices via BKAV and incoming e-invoices are an add-on designed after the core (author, 2026-11-15; DS-24 in the [backlog](../design/backlog.md)), built on the core seam | Tax amounts on the synthetic dataset match the independent tax recomputation; the 01/GTGT return matches a hand-built golden return |
| 8 · Period close and reports | Period-close checklist (including prepaid expense amortization and provisions), period-end FX revaluation, closing entries, Vietnamese books, B01, B02, B03, print templates as configuration | Period close on the synthetic dataset matches the golden scenarios and the naive recomputation, FX differences included |
| 9 · Hand-built UI and warehouse app | 6 most-used entry screens, warehouse screens with barcode | An outside accountant enters one day of documents from the synthetic dataset, no slower than MISA |
| 10 · Platform completion | Replay the large synthetic dataset (several companies, the manufacturing company and the US company included, several years, about 100,000 documents a year) through commercial documents (not only core commands), fix every difference, add the TT133 regime to the Vietnam package; write the AI skill for localization packages and use it to build the basic US package; write deployment documentation | The large dataset passes every invariant and reference comparison, and the coverage report shows every edge case exercised. This is the platform-complete milestone; pilot selection starts here |
| 11 · Pilot selection and go-live rehearsal | Select the pilot, build the reader for their current system if it does not exist yet (e.g. MISA for a Vietnamese pilot), load their real data on staging, replay their latest month, freeze the schema | The rehearsal month matches the customer's books in their current system. The chief accountant agrees to go live |

Steps 0–4 correspond to Phase 0; steps 4b and 5–11, including 5b, are the Phase 1 build before go-live. Step 4 comes before commercial documents on purpose: the core is proven correct on the synthetic dataset before any layer depends on it. The step 11 rehearsal runs on staging; it is not a production parallel run with the old software.

Agents are not a separate step. Each agent is built right after its manual path passes its gate: the assistant and analysis after step 5, bank matching after step 6, purchase invoices and the vision reader after step 7, and planning after step 5b. All six are done before the platform counts as complete; data migration, quotation, the auto-post advisor and the other agents come after Phase 1 ([ADR-0078](../adr/0078-agent-simplification-for-phase-1.md)).
