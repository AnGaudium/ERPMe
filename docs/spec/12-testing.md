# Continuous testing

Stand up the test server as each part is built, with a model running scenarios continuously to find defects, especially in posting and data handling. Same principle as the product: **the model only proposes scenarios; deterministic code judges right and wrong.** The model never computes expected results.

**Three layers of reference results:**

1. Synthetic dataset replayed in sequence: fictional companies simulated day by day through the public commands (see [Synthetic dataset](#synthetic-dataset) below), with every invariant checked after each simulated day.
2. Golden scenarios with hand-built spreadsheets: average cost with transfers, returns, backdated documents, purchase costs allocated after goods were partly sold, a USD import with import duty paid at a different rate, period-end FX revaluation, discounts, rounding.
3. An independent naive recomputation written from the specification without reading the core code, e.g. periodic average computed straight from raw transactions.

**Invariants checked after every scenario** (named INV-xx in the DS-16 catalog):

- Every journal entry balances in each transaction currency, in company currency and in group currency; the trial balance sums to zero. Rounding differences from conversion go to a rounding line on a defined system account (DS-02 and DS-06 decide which).
- Balances of inventory-type system accounts (152, 155, 156 in TT99) equal the inventory valuation report; receivable and payable control accounts (131, 331 in TT99) equal the sum of open items.
- No negative stock; no gaps in document numbers; posted documents never change.
- Reversing a document nets to zero.
- Retrying a command with the same idempotency key returns the identical result.
- The executed result equals the simulated result (`plan_hash`).

**Operation:**

- The model generates unusual but realistic business situations. Add random transaction sequences generated with Hypothesis, which are cheaper and cover more ground.
- Every defect found is frozen into a regression scenario in CI.
- Run nightly and after every deploy, within a budget ([ADR-0003](../adr/0003-build-operating-rules.md) R6). Defects go to the issue tracker, deduplicated (R7); the work queue holds business work only.

**Outside this approach's reach, handled separately:**

- Concurrency defects, when two commands write the same (item, warehouse): dedicated parallel tests.
- Misreading regulations: have an accountant or auditor review, and compare with real books when a business provides them.
- Data-entry speed in the UI: measure with real users.

## Synthetic dataset

The test data is our own: fictional companies generated by a business simulator. No third-party data is copied. Odoo's demo data serves only as a checklist of which kinds of records a test set needs (partner types, product types, taxes, journals, price lists, documents in each state).

1. **Simulate real operation.** The simulator runs a calendar day by day for each fictional company and calls the public commands in the order a real business would: purchase requests, POs, goods receipts, invoices, sales, deliveries, payments, bank statements, stock counts, month-end and year-end closes. Nothing is inserted into tables directly. The simulator emits a versioned business-event log; per-step adapters translate events into the commands that exist at that build step, so the same log drives every step from step 0 on.
2. **Reproducible.** Each run is driven by a seed and a dataset version; the same seed produces the same transactions, so any failure can be replayed exactly.
3. **Fictional and multilingual.** Names, tax IDs and addresses are generated, never taken from real businesses. The Vietnamese company gets Vietnamese names and VND; the US company, which joins the large dataset at step 10, gets English names and USD; imports use foreign currencies.
4. **Input files too.** The simulator also writes the files agents read in real life (e-invoice XML, bank statement files, emails with quotation requests), so agent workflows are tested on the same flow.
5. **Three sizes:**

| Size | Content | Used in |
| --- | --- | --- |
| Small | 1 Vietnamese company (TT99), 3 months, a few hundred documents, every edge case at least once | CI on every commit |
| Medium | 1 Vietnamese company (TT99), 1 year, about 10,000 documents | Nightly; step 4 gate |
| Large | Several companies, the US company included, several years, about 100,000 documents a year | Load tests; step 10 gate |

6. **Edge-case catalog.** A versioned list of edge cases (EC-xx), each injected by the simulator at a known frequency, with a coverage report per run. Version 1 includes: backdated documents in an open period; postings attempted in a soft-locked period; partial deliveries, receipts and invoices; returns of partly invoiced goods; negative-stock attempts; concurrent issues of the same item and warehouse; transfers between warehouses with different average costs; landed cost arriving after goods were partly sold and after the period closed; USD imports with a customs rate different from the book rate; partial foreign-currency payments at a different rate; month-end FX revaluation; netting of receivables and payables; credit limit exceeded; price below cost; a tax-rate change mid-period (e.g. VAT 10% → 8%); replaced and adjusted invoices; rounding over many small lines; UoM conversions (carton to bottle); lot and serial movements; stock count differences; command retries with the same idempotency key; year-end close.
7. **Expected results stay independent.** The simulator records what happened in business terms (quantities, prices, payments, rates). The naive recomputation turns that into expected balances without using core code; golden scenarios cover the cases a person must check by hand.
